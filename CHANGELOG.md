# Changelog

Notable changes to Open MCP Portal, one entry per release. Design notes for each phase are in [`docs/`](docs/), and
[`docs/status.md`](docs/status.md) records what was verified.

The project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0, minor releases may include
breaking changes; the entry says how to adapt.

## Unreleased

- Shared connection review hardening (#26): metadata-only destination preflight, committed local revocation before best-effort upstream HTTP, and user-first consent locking compatible with administrative suspension.

- **Breaking retirement in progress** (#68, decision 81): remove external agent-platform trust and person impersonation, including Pi Durable Platform. Existing relay credentials must be disabled/revoked rather than silently becoming ordinary service-account access. Historical records remain; normal MCP OAuth, API keys, service accounts, provider connections and outbound identity remain supported. #62/#63 were withdrawn, not verified.
- **Staged, not released:** credential scopes (#29), per-selection tool curation (#30), shared service connections (#26) and migration/runtime database roles (#44). Independent review, combined-tree fixes, browser checks and release gates are still in progress; see [status](docs/status.md).

## [0.3.3] - 2026-10-28

- **Kubernetes smoke harness:** own/reap the real port-forward process and wait for the evicted pod to disappear before recovery checks; deterministic lifecycle regressions run in CI.
- **Dependency security:** Go toolchain and pinned builder updated to 1.26.10; web test dependency Undici updated to 8.12.3 after release CI identified public advisories. Vulnerability gates remain enabled.
- **Browser sessions** (#37, decision 76). Account › Sessions lists browser/device, stored address, sign-in, activity and expiry, marks the current session, and lets a person sign out one or everywhere (optionally keeping this session). Platform admins can list and revoke a person's sessions; auditors and automation tokens cannot. Revocations cancel pending connect flows and write count-only audit events in the same transaction; connected apps, API keys and provider connections remain separate. Optional `SESSION_IDLE_TIMEOUT` defaults to `0` (off), accepts 5m through `SESSION_TTL`, and is checked on every browser session path and by cleanup. Activity writes are throttled to once a minute. Migration `00028_session_activity.sql` is expand-only and gives existing sessions an idle window from upgrade. OAuth refresh absolute lifetime (H-8) remains the separate, existing control.
- **Owner-set tool classification** (#28): team owners/admins classify tools as read, write or destructive, individually or in an atomic bulk edit. Server annotations remain suggestions; existing tools stay unclassified. Refresh preserves classes and disappearance clears them. Lowering a class returns published servers to review under `approval_required`; review digests bind to classes (`omp-review-v4`). Gateway lists overlay trusted read-only/destructive hints without rewriting stored definitions, and identity tokens/call records optionally carry the class. Session-only API; no automation-token permission expansion. Migration `00027`; [design](docs/tool-classification.md).
- **Backlog reconciliation:** [implementation order](docs/implementation-order.md) covers all 36 open issues, separates real-world verification from code work, and records external token-binding coordination plus staged lifecycle/audit dependencies.

## [0.3.2] - 2026-10-20

- **Each person's own key for a server** (#22, [decision 72](docs/decisions.md), [person-secrets.md](docs/person-secrets.md)). A new upstream auth mode, `person_secret` (the fourth; #24 adds `machine_oauth`, the fifth): the server's team says how a secret travels (a header, a bearer token or a query parameter, a name, an optional prefix, and the words for the page where it is entered) and each person pastes **their own** API key or token once (Account › My connections › Keys for servers, or the link a call returns). It is sealed per person and server, shown only as its last four characters, and sent only on that person's calls. It is bound to the server's origin (F-1 and F-3 extended): a new origin, another mode or another placement deletes everyone's keys (audited `mcp_server.person_secrets_reset`), a path edit keeps them. A call with no usable key gets the consent answer in the three shapes of decision 59 (a link to `/connect/secret/<id>`; class `secret_missing` or `secret_rejected`) and nothing is forwarded, with no fallback to another credential; a service account is refused (`-32010` `service_account`); a call an agent relays for a person uses their key only if they switched on **Let my agents use this key** and never gets a link (a tool error names My connections); an upstream 401 or 403 marks the key rejected and asks again; a suspended person's key is not used and is kept. Capabilities are read with the key of an editor who chose to (the server is created without reading them), and **scheduled health checks send nobody's key: a 401 or 403 counts as healthy**. The mode excludes a requirement and a static part that sets the same header, query parameter or `Authorization`. Six session-only operations (`listMyServerSecrets`, `setMyServerSecret`, `revokeMyServerSecret`, `getSecretRequest`, `adminListUserServerSecrets`, `adminRevokeUserServerSecret`; no automation token scope, so the token operation counts are unchanged); `McpServer`, `McpServerCreate` and `McpServerUpdate` gain `personSecret`; an automation token can't switch a server to the mode or send it. Migration `00024` (expand-only: two tables, nullable columns and a widened mode check that is added to the existing one, not written over it); `rotate-keys` re-seals `person_secrets.secret_cipher` and `secret_requests.id_cipher`; a rollback to 0.3.1 reads such a server as one with no credential. **Not browser-checked or run against a real third-party server.** **Not built:** shared team secrets and service-account use (#26), several keys per person and server, testing a key when it is pasted.
- **Tests (#22):** `TestPersonSecretSetupReadsCapabilitiesWithTheSetupKey`, `TestPersonSecretEachPersonSendsTheirOwn` (header, bearer, query), `TestPersonSecretMissingKeyIsAskedInEveryEra`, `TestPersonSecretRejectedKeyIsNotSentAgain`, `TestPersonSecretForbiddenMarksRejected`, `TestPersonSecretOriginBinding`, `TestPersonSecretModeAndPlacementChangesResetKeys`, `TestPersonSecretValidation`, `TestPersonSecretServiceAccountIsRefused`, `TestPersonSecretSuspensionBlocksAndKeepsTheKey`, `TestPersonSecretRelayedCalls`, `TestPersonSecretNeverLeaks`, `TestPersonSecretSpansCarryNoKey`, `TestPersonSecretTokenFieldRule`, `TestPersonSecretsMigration`, the authz matrix rows for the six operations, `TestColumnsCoverTheSchema` and `TestRotateKeys` with the two new columns, unit tests for placements, redaction, conflicts, reset reasons and the review digest, and the Vitest files `person-secrets.test.tsx` and `person-secrets-server.test.tsx`.
- **OAuth client credentials for servers that authenticate the portal itself** (#24, [decision 73](docs/decisions.md), [machine-oauth.md](docs/machine-oauth.md)). A server can use `authMode: machine_oauth`: the portal is an OAuth client of the server's authorization server, gets a token with the **client credentials grant** and sends it as `Authorization: Bearer` on every request to the server (discovery, Refresh, Test, scheduled health checks, forwarded calls), for every caller alike, **service accounts and relayed agent calls included**; the identity token moves to `MCP-Gateway-Identity`. Setup (Add server, Settings › Authentication › The portal's own OAuth client; `machineOAuth` on create and update): token endpoint, client ID and secret (sealed, never returned: only a hint), scopes, token method (`client_secret_basic` or `client_secret_post`), optional audience and resource; **Detect sign-in** also reports whether the authorization server lists `client_credentials`. Tokens are kept in memory per replica (60 s before expiry, one request for concurrent callers, no token in the database); a 401 renews the token once and retries the call once, then class `auth`; an unavailable token endpoint is `-32010` `machine_auth_unavailable` and the server is not contacted; the token request goes through the address guard (no redirects) and only an OAuth error code is ever kept. **F-1:** another token endpoint, client ID or server origin needs the secret entered again in the same request (`422 client_secret_required`). A new endpoint, client, scope, audience or resource sends a published server back to review (`upstream_auth_changed`; a new secret does not) and the review digest covers them. Editors may set it up; **an automation token may not** (`403 token_not_allowed`). Migration `00025` (expand-only: a table and one more `auth_mode` value); `rotate-keys` re-seals the new secret column; metric `omp_machine_token_requests_total{result}`. `cmd/fakeoauth` serves the grant (`-enforce-expiry`, `-machine-scopes`, `-no-client-credentials`). **Not run against a real authorization server** (Entra ID, Okta, Keycloak, Auth0) and not browser-checked. Not built: `private_key_jwt`, mTLS, token exchange, a cross-replica cache.
- **Tests (#24):** `TestMachineOAuthEndToEnd`, `TestMachineOAuthCreate`, `TestMachineOAuthSecretDoesNotFollowEndpointClientOrOrigin`, `TestMachineOAuthConcurrencyAndRenewal`, `TestMachineOAuthFailures`, `TestMachineOAuthTokenEndpointAddressRules`, `TestMachineOAuthDetect`, `TestMachineOAuthSentinels`, `TestMachineOAuthSecretIsBoundToItsServer`, `TestMachineOAuthMetricsAndSpans`, `TestMachineOAuthIsSessionOnlyForTokens`, `TestMachineOAuthMigration`, the token source's unit tests (`TestMachineToken*`), `TestReviewDigestCoversMachineClient`, the key-rotation test with the new column, and the Vitest file `machine-oauth.test.tsx`.
- **mTLS client certificates and a per-server CA for upstream connections** (#25, [decision 74](docs/decisions.md), [registry.md](docs/registry.md#tls-to-the-server), migration `00026`, expand-only). A server can have a **client certificate with its private key** and a **CA bundle**, saved as `tls` on create and update (Settings › TLS to the server). **The CA replaces the system roots for that server only** (so a public CA can't vouch for an internal host and the private CA vouches for nothing else); **there is no option to skip verification anywhere**, the host name is always checked (a certificate without it fails with an error that says so), TLS 1.2 is the minimum. The address rule is untouched: still one resolution, every address checked, the connection pinned, no redirects, no proxy, and a private address still needs an internal-network entry. The key is sealed with `ENCRYPTION_KEY` (AAD bound to the server and the field), never returned, logged, audited or captured, and rotated by `rotate-keys`. Validated at save (PEM only, size and certificate-count caps, no private key in a certificate field, no passphrase-protected key, the key belongs to the certificate, RSA 2048+, ECDSA P-256/384/521 or Ed25519, no MD5 or SHA-1 signatures, not expired): `422 invalid_tls` with `details.field` and `details.reason`. **F-1:** a URL on another origin never keeps the key or the CA (`422 tls_key_required`). **Review:** a new, changed or removed CA sends a published server back to review under `approval_required` (reason `upstream_tls_changed`); a new client certificate does not; the review digest is now `omp-review-v3` and covers both fingerprints, so **a review request open at the upgrade needs one reload**. A handshake failure is the new error class **`tls`** (migration `00026` replaces the enumerated `mcp_health_checks.error_class` check by a length bound), with a message for each case. **Expiry:** 14 days ahead the server's health shows a warning (`health.warnings`), the admin overview and the team's attention list it (`server_certificate_expiring`), and the hourly scan emits `key.expiring` with the new `keyKind` `server_certificate` to the team's owners, admins and editors. Neither kind of automation token can send `tls`. API: `McpServerCreate`/`McpServerUpdate`/`McpServer` gain `tls` (responses carry fingerprints, subjects, issuers and expiry, never the key), `McpErrorClass` gains `tls`, `PublishRequestedData.reason` gains `upstream_tls_changed`, `KeyExpiringData` gains `server_certificate` and `server`, and the attention kinds gain `server_certificate_expiring`. **Not built:** client certificates for the OAuth metadata and token endpoints (a server in `oauth` mode behind a private CA can't be set up), a platform-wide CA library, certificate issuance or renewal, passphrase-protected keys, CRL or OCSP. **Not run:** a real internal server behind a private CA or a real client-certificate proxy (the tests use `httptest` TLS servers that require and verify client certificates against throwaway CAs; the web card was not looked at in a browser). **Tests:** `TestTLSMutualDiscoverAndCall`, `TestTLSStreamedCall`, `TestTLSFailureClasses`, `TestTLSHostNameIsVerified`, `TestTLSMinimumVersion`, `TestTLSConnectionsAreNotSharedBetweenIdentities`, `TestTLSIsOrthogonalToTheAddressRule`, `TestTLSFailureLeavesTheEraCacheAlone`, `TestParseClientPair`, `TestParseCABundle`, `TestNoInsecureSkipVerifyAnywhere`, `TestUpstreamTLSEndToEnd`, `TestUpstreamTLSInputValidation`, `TestUpstreamTLSKeyDoesNotFollowOriginChange`, `TestUpstreamTLSChangedCASendsPublishedServerBackToReview`, `TestUpstreamTLSExpiryWarnings`, `TestServerCertificateExpiryScan`, `TestTLSKeyIsBoundToItsServerAndField`, `TestPlanTLS`, `TestReviewDigestCoversTLS`, `TestUpstreamTLSMigration`, `TestTokenFieldRules` (the `tls` cases), `TestColumnsCoverTheSchema` and `TestRotateKeys` (the new column), and the Vitest file `server-tls.test.tsx`. `internal/testutil` gained a throwaway PKI (`pki.go`) and an mTLS fake MCP server (`mtls.go`).
- **The three together** (#22, #24, #25). A server is in one of five modes (`none`, `static_header`, `person_secret`, `machine_oauth`, `oauth`) and may sit behind a private CA with a client certificate, in any of them; the web forms offer all five side by side. Migrations `00024` and `00025` each add their value to the `auth_mode` check as it stands in the catalog (either order, twice), and each Down removes only its own value (servers go back to `static_header` when they still have a static credential, else `none`). Leaving `person_secret` or `machine_oauth` deletes that mode's secrets; another origin discards every kind of secret unless replaced; automation tokens set none of them; one review digest (`omp-review-v3`) covers the CA, the person-secret placement and the machine client; the key rotation re-seals every new column. Leaving `person_secret` now shows the "everyone's keys are deleted" warning in whichever mode is chosen. A TLS 1.3 server that refuses the client certificate by closing the connection is class `tls` (it was sometimes `unavailable`, a race with the alert). **Limit:** TLS settings are for the MCP server's URL only, not for a token endpoint or sign-in metadata ([machine-oauth.md](docs/machine-oauth.md#with-tls-to-the-server-decision-74)). **Tests:** `TestAuthModeConstraintAcceptsEveryMode`, `TestEveryAuthModeWorksBehindAPrivateCAAndMTLS`, `TestSwitchingAuthModeCleansUpEverySecret`, `TestAnotherOriginDiscardsEverySecretUnlessReplaced`, `TestAChangedCAOrModeSettingSendsEveryModeBackToReview`, `TestAutomationTokensSetNoSecretTLSOrModeChange`, `TestRelayedCallsApplyEveryAuthMode`, `TestEverySecretKindNeverLeaksAnywhere`, `TestReviewDigestCoversEveryModeAndTLSTogether`, `TestColumnsIncludeEveryFeaturesSealedValues`, `TestTLSFailureConnectionClosedAfterHandshake`.

## [0.3.1] - 2026-10-20

A per-provider access list and narrower delegated tokens (roadmap #27, threat model H-5, [decision](docs/decisions.md) 69). Migration `00021` (expand-only).

- **Who may use an auth provider.** A platform provider is **open** (any team's server may require it) or **restricted** (only a server of a listed team, or a listed server). Every provider that exists at the upgrade **stays open**, and Admin › Auth providers flags it (an "Open to every team" badge); a provider created afterwards **starts restricted with nobody listed**, so nobody can require it until a platform admin lists teams or servers in the provider's new **Access** tab. The list is checked when a requirement is saved (`422 provider_not_allowed`, for a newly chosen provider; a server that already has one keeps it), when a person allows a server (a consent link, the consent callback, or Account › My connections › Allow servers: a server the list excludes is not offered and cannot be allowed) and **on every call**, an agent's relayed call included: `-32010` `provider_not_allowed`, recorded `denied`, no consent link, nothing sent to the server. Removing a team stops delivery on the next call; people's connections and allowances are kept. API: `GET` and `PUT /v1/admin/auth-providers/{id}/access` (`If-Match` on the provider's revision), **browser session only** (no automation token, so the token operation counts are unchanged), audited `auth_provider.access_update` with the list before and after; `GET /v1/auth-providers` takes an optional `team` (and `serverId`) so a server's requirement picker offers only what its team may use. The Access tab also lists the servers that still require a provider the list excludes.
- **Narrower tokens per call** (opt-in). A provider's new switch **Narrow tokens per call** (`narrowOnRefresh`, default off): a call carries a token refreshed with only the scopes it needs (RFC 6749 section 6), kept in memory per replica until a minute before it expires and never stored, logged or audited, instead of the stored token that holds every scope the person ever granted. A rotated refresh token is stored in the same transaction. It needs a refresh token (a connection without one keeps sending the stored token), and My connections shows which connections narrow (`narrowsScopes`; an "All granted scopes" badge otherwise). A provider that refuses the narrower scope (`invalid_scope`) is not worked around with the full token: the call is refused. **Only the Microsoft Entra ID preset pre-fills it**, from Microsoft's documentation (checked in October 2026, **not against a live tenant**); GitHub, Google, Atlassian, Slack and GitLab document no scope on refresh and stay off, and a provider that ignores `scope` returns its full token even with the switch on ([which preset supports what](docs/phase5-delegated-credentials.md#who-may-use-a-provider-and-narrower-tokens-decision-69-v031-h-5)). `cmd/fakeoauth` has `-honour-refresh-scope`, which is how it is tested.
- **Background refresh** (opt-in, `PROVIDER_REFRESH_INTERVAL`, default `0`: off, at least `1m`). One replica at a time (advisory lock) refreshes connected accounts whose token expires before the next pass and that were used in the last 7 days, so a grant the provider revoked turns `needs_reconsent` (the person is told) before a call finds out. A connection is never refreshed twice for one expiry.
- **Not built** (out of the issue's scope): one token per (person, provider, server), several accounts per provider, RFC 8693 token exchange, matching the provider account to the person. An oauth server that links a platform provider's client is not gated by the list (it shares the client, never the connections).
- **To act on after upgrading:** nothing breaks, but every existing provider is open: restrict the ones that should not be available to every team (Admin › Auth providers › the provider › Access). A provider you create after the upgrade needs its teams listed before any team can require it. **Not browser-checked or run against a real provider:** see the notes in [phase5-delegated-credentials.md](docs/phase5-delegated-credentials.md).
- **Tests:** `TestProviderAccessListGatesRequirements`, `TestProviderAccessListIsCheckedOnEveryCall`, `TestProviderAccessListGatesAllowingAServer`, `TestProviderAccessListGatesRelayedCalls`, `TestNarrowOnRefreshSendsOnlyTheScopesTheCallNeeds`, `TestNarrowOnRefreshNeedsARefreshToken`, `TestBackgroundRefresh`, `TestProviderAccessMigrationKeepsProvidersOpen`, the narrowing cache and preset unit tests, the authz matrix entries for both operations, and the Vitest file `admin-auth-provider-access.test.tsx`. The providers the existing tests create are opened with a helper; `FakeOAuth` gained `HonourRefreshScope` and `RefreshScopes()`.

- **A server's own credential as several parts** (#23, [decision 70](docs/decisions.md), [registry.md](docs/registry.md#a-servers-own-credential-parts)). Instead of one static header, a server's credential can be up to eight parts: headers, a bearer token, Basic user and password and a **query parameter** (`credentials` on create and update; Settings › Authentication › Static credential). Every value is sealed on its own and never returned, logged, audited or recorded; each part reaches every request to the server (discovery, Refresh, Test, health checks, forwarded calls). A saved URL with a query is still refused: the query part is added at request time, never stored in the URL, and redacted (also URL-encoded, and the Basic base64 string) from messages, logs and captured payloads. A URL on another origin needs **every part's value entered again** (`422 auth_value_required`, `details.field` `credentials[i]`). At most one part sets `Authorization`; then the identity token arrives in `MCP-Gateway-Identity`, also on calls an agent platform relays. The review digest covers part kinds and names (`omp-review-v2`: a review request open at the upgrade needs one reload), adding parts doesn't send a published server back to review, and an automation token can't change parts. Migration `00022` (expand-only, a new table): servers keep their one header in the old columns and read as one part until their credential is saved as a list; rolling back to 0.3.0 reads a server saved with parts as having no credential. **Not run:** a real third-party server that wants Basic or a query key (the fake MCP server in the tests does).

- **OpenTelemetry tracing, Grafana dashboards and Prometheus alert rules** (#34, decision 71, migration `00023`, expand-only; [deploy.md](docs/deploy.md#tracing)). Tracing is **off** unless `OTEL_EXPORTER_OTLP_ENDPOINT` (or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, or `OTEL_TRACES_EXPORTER=otlp`) is set, and then exports OTLP/HTTP spans: a server span per request (for `/mcp/{slug}` the MCP method, with children for authentication, gateway resolution, what the caller may use, the rate limit, the provider credential and one client span around the call to the server; the management API by route pattern) and a span per registry probe. Span attributes are a fixed allow-list (slugs, outcome, principal kind, classes, status): never a person, key, tool name, argument, result, header, path or address, and a test scans every span of a call made with sentinel secrets. The parent is the HTTP `traceparent`, else `_meta`; with the portal's span sampled, every server receives a `traceparent` naming the portal's span (baggage stays the client's; unsampled or off: the client's context passes unchanged, as before). Default sampler `parentbased_traceidratio` 0.1 (`OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG`). Logs carry `trace_id` and `span_id` for sampled requests, `mcp_calls.trace_id` (new nullable column; `McpCall.traceId`) keeps the ID, and `TRACE_LINK_TEMPLATE` makes it a link on a call's page. `doctor` reports the exporter; no new metric. New dependencies: the OpenTelemetry Go API, SDK and OTLP/HTTP trace exporter (and the protobuf types and gRPC packages that exporter imports). **Not built:** OTLP logs or metrics, exemplars, database spans, tracing the browser, a trace viewer.
- **Dashboards and alert rules as code.** Five Grafana dashboards in `deploy/grafana/dashboards/` (MCP traffic, servers, providers and tokens, notifications, platform) and `deploy/prometheus/omp-alerts.yaml` with 14 alerts and promtool unit tests, each alert with a runbook entry in [phase6-operations.md](docs/phase6-operations.md#alert-runbook); a `PrometheusRule` and an OTLP egress NetworkPolicy example in `deploy/kubernetes/overlays/example/` (validated by `make k8s-validate`, not in the overlay's resources). A test checks every metric and label the dashboards and rules use against the registry; `make prom-check` (also in CI) runs promtool.

## [0.3.0] - 2026-10-20

Calls from agents as the person's calls (roadmap #55 to #58 and #60, [decisions](docs/decisions.md) 65 to 68). Migration `00020` (expand-only).

- **Trusted agent platforms** (#55, [agent-platforms.md](docs/agent-platforms.md)). Platform admins trust an external agent platform (Pi Durable Platform) as an issuer of agent identity tokens: Admin › Trusted agent platforms (name, issuer, keys address, audience, on or off, the result of the last key fetch and its key IDs, and a **Test** that fetches the keys). A strict verifier accepts only ES256 tokens in the format of the platform's design note: no `none`, HS\* or RS\*, the key from the platform's JWKS only (fetched through the same address guard as MCP servers, no redirects, 5 s, 64 KiB, cached for at most 5 minutes, refetched at most twice a minute for an unknown `kid`, kept for 15 minutes past expiry while the platform is down), `iss`, `aud`, `principal_type: agent`, the claims and time limits, and a `jti` accepted once across replicas. A named person's `person.iss` must equal `OIDC_ISSUER`. API `/v1/admin/agent-platforms…`, session-only (no automation token can change or read them), audited as `agent_platform.*`.
- **Relay service accounts** (#56). A platform admin marks a team service account as a relay for a platform (`PUT /v1/admin/agent-platforms/{id}/relays/{serviceAccountId}`; audited `service_account.relay_set` and `relay_clear`). A call with that account's key may carry the platform's `MCP-Gateway-Identity` token. A token naming a person makes the call **the person's, limited to what the relay account could reach** (the gateways both can use, the lower of the two roles for minimum roles); the person is read on every call, so suspending them or removing them from a team applies to their agents at once; an unknown or suspended person is a tool error, never the account's own call. A token that fails any check on a relay's request refuses the request (HTTP 403); a token with any other credential is ignored, counted (`omp_agent_token_total`) and logged. A service account key alone behaves as before. The call log shows the person, the agent, the relay account and the platform (`McpCall.agent`).
- **No consent links in agent calls; require a present person** (#57). A relayed person call never gets `-32042`, a consent link or an `input_required` result: a missing connection, a server the person hasn't allowed, too few scopes and an upstream sign-in are tool errors naming the provider and saying to connect under Account › My connections (recorded `needs_authorization`, class `needs_connection`). New switch **Require a present person for calls from agents** on a server and an override on each capability (`PUT …/capabilities/{id}/present-person`; editors; default off): relayed calls whose token says `person_present: false` are refused (class `person_not_present`; calls that name nobody are refused too, see the review below). Turning it on needs no review; relaxing it sends a published server back to review under `approval_required`.
- **Allow a server from My connections** (#60, decision 68, [agent-platforms.md](docs/agent-platforms.md#delegated-credentials-and-agents-that-have-no-browser)). On Account › My connections, **Allow servers…** on a connection lists the servers that require that provider and that the person may use through a gateway now, each with its team, address, the scopes it asks for and **Allow**; allowing records the same grant as a consent link's confirm step, for the server's current address and the scopes it requires, with no call and no link, and **Take back** removes one server's allowance without disconnecting. A server that moved or now asks for more since the list loaded is refused (`409 server_changed`); an account without the scopes is sent to the provider (`409 connect_required`). An agent's `server_not_allowed` tool error now says to allow the server there (still link-free). API: `GET …/allowable-servers`, `POST …/allow-server`, `DELETE …/allowed-servers/{serverId}` under `/v1/me/connections/{id}`, browser session only, 20 a minute per person; audited `provider_connection.server_allow` (`viaRequest` false) and `provider_connection.server_revoke`. No migration.
- **`act` claim and the administrator's guide** (#58). The identity token for the MCP server behind the gateway keeps the person's `principal_type: user`, `sub`, `email` and `teams` on a relayed person call, sets `client` to the relay account's name and adds `act` (`sub`, `name`, `iss`, `principal_type: agent`, `person_present`), exactly on those calls ([upstream-identity.md](docs/upstream-identity.md#calls-from-agents)). `cmd/fakemcp`'s `whoami` shows it. [agent-platforms.md](docs/agent-platforms.md) walks through the setup and a manual end-to-end check; the [threat model](docs/threat-model.md#68-the-agent-platform-relay-decisions-65-to-67) has the relay trust boundary. **Not run:** a running Pi Durable Platform instance (see the contract fixtures below for what was checked against its real code).
- **Security review of the agent platform work, applied** ([agent-platforms.md](docs/agent-platforms.md#limits-you-should-know), [threat model](docs/threat-model.md#68-the-agent-platform-relay-decisions-65-to-67) AG-2, AG-3, AG-9, AG-10; decisions 65 to 67 edited with dated notes). Changes to behaviour that was never released:
  - **A token's `tool` claim is bound to the request** (M-1). On a `tools/call` the claim must be present and equal `params.name` (the name the portal exposes); on every other method it must be absent. A mismatch refuses the request like any bad relay token (`403`, nothing runs, `omp_agent_token_total{result="rejected_tool_mismatch"}`). PDP's recorded tokens fit the rule (tokens for a tool carry `tool`, the handshake token has none); what PDP's gateway puts in `tool` for a real call was not checked against a running PDP. **Accepted residual, documented:** the token is still bound only to the platform's audience, not to a relay or a gateway, so a token another PDP server received can be used with any relay key of that platform for a call of the same tool name; run PDP so that only platform admins set `identityAudience` and a team server never gets a token whose `aud` is a trusted portal audience. A per-gateway audience mode is not built.
  - **Require a present person also covers calls that name nobody** (M-2). Connected apps shows **Sign-in expires** (`OAuthGrant.expiresAt`). A refresh token presented again within the 30-second grace now gets the **same** new tokens instead of a second set; outside the grace it still revokes the grant.

  version is used. The era is cached in memory per server ID and URL for 5 minutes. The last negotiated `protocol`

  (`McpServer.protocol`; cleared when the URL changes).

### Security

Fixes from the [threat model](docs/threat-model.md) review (section 8). Two additive API changes need a client update:
approving now names what was reviewed. People re-consent once per server for provider tokens (F-3).

- **Another origin never keeps a server's stored header value (F-1).** A URL edit that changes scheme, host or port is
  refused with `422 auth_value_required` unless the same request sends a new `authValue` or removes the header; in `oauth`
  mode it erases the connections and sends the server back to the setup sign-in. The audit entry names `oldOrigin` and
  `newOrigin`. Path, trailing-slash and case edits are unchanged.
- **Approvals are bound to what the reviewer saw (F-2).** `McpServer.reviewDigest` is new and read-only. Approving a
  server (`adminReviewMcpServer`) must send it as `expectedDigest`, approving a capability (`adminApproveMcpCapability`,
  `approveTeamMcpCapability`) must send `expectedFingerprint`: `400 expected_digest_required` or
  `expected_fingerprint_required` without it, `409 changed_since_review` when the server or capability changed in
  between. Publishing accepts an optional `expectedDigest`. The web UI sends them; scripts that approve (such as
  `scripts/dev-seed.py`) read the digest first.
- **Provider tokens are bound to a server and its origin (F-3, decision 60).** A platform provider's token (GitHub,
  Google, ...) used to go to whichever server required the provider, at whatever URL it had, so an editor could make a
  server "require" GitHub, or re-point one, and receive teammates' tokens with no prompt. Now the token is sent only to
  a server the person **allowed**, at the origin (scheme, host, port) it had when they allowed it, for the scopes they
  were shown. A call without that gets consent with the new reason `server_not_allowed` (the same three answer shapes
  as before: `-32042`, the modern URL-elicitation request, or a tool error with the link), and nothing is forwarded.
  **After upgrading, every person consents once per server** the first time they call it (no backfill, on purpose: it
  would grandfather any malicious server). When the person's account already has the scopes, the consent page just
  asks "Allow <server> (<team>)" and records the grant without going to the provider. A server's grants end when its
  URL moves to another origin, it requires another provider, or it is deleted (a path-only edit keeps them);
  disconnecting deletes the account's. Migration `00017` (table `provider_server_grants`; two nullable columns on
  `provider_connect_requests`; a consent link made before the upgrade is refused as expired, run the tool again).
  API (additive): `POST /v1/connect/requests/{id}/confirm`, `ConnectRequest.server` and reason `server_not_allowed`,
  `ProviderConnection.allowedServers`; Account › My connections lists the allowed servers. **Not changed:** the token
  still holds the union of every scope the person granted, a server they allowed receives all of them, and there is no
  per-provider allow-list of teams or servers (H-5).
- **Sign-in `next` refuses control characters (F-4).** `/auth/login?next=/%09/evil.example` ended in a redirect to
  `//evil.example`; sign-in and the connect flow now share one path rule (`internal/safepath`).
- `serve` refuses an `ENCRYPTION_KEY` equal to the `API_KEY_PEPPER`; the main listener's `ReadHeaderTimeout` (10 s) and
  `IdleTimeout` are pinned by a test; CI runs `govulncheck` and `npm audit --audit-level=high` (none reported).

expiring keys (`omp_sa_`, two active for rotation).

and GitLab), server requirements and capability overrides, consent links (JSON-RPC `-32042`), each person's tokens
sealed, refreshed under a row lock and revocable, sent to servers in `MCP-Gateway-Provider-Token`. The Gmail example
server in `examples/mail-mcp`.

**Operations** (Phase 6). Rate limits shared by every replica (per person, credential, service account and gateway),
opt-in payload capture (redacted, truncated, sealed, audited views), retention, hourly usage rollups and reports,

`doctor`, a distroless image, a demo Compose file, a Kustomize base and overlay, and CI.

**Per-person OAuth to upstream servers** (Phase 7). Servers in `oauth` mode (such as GitHub's hosted MCP server):

sign-in that reads capabilities, each caller's own token with refresh and step-up, and a per-server `sendIdentity`

Gateway. Module `github.com/ncecere/open-mcp-portal`, binary `open-mcp-portal`, `OMP_*` environment variables, `omp_*`
