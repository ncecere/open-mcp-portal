# Product decisions

Status: requirements interview in progress. Nothing below is implemented yet.

## Purpose

A central, self-hosted place for the company to discover and access its many MCP servers. It is closer to
Arcade than to the MCP features in LiteLLM, Bifrost or the Docker MCP Gateway: the portal brokers who the
user is and what each tool may do on their behalf, not only network routing.

Not in scope: hosting or running agents (that is the separate `open-agent-platform` idea).

| 7 | Identity to upstream servers | Every forwarded call carries a short-lived JWT signed by the gateway (user, teams, gateway, tool); servers verify it against the gateway's published keys |

| 11 | Deployment | Like Grounded: Docker Compose for local development and small installs, Kubernetes (Kustomize) for production. One stateless Go binary that can run several replicas; PostgreSQL is the only required dependency (no Valkey at first: rate counters and tokens live in PostgreSQL) |
| 12 | Client authentication | Both: OAuth sign-in for interactive MCP clients (Claude Code, Claude Desktop, VS Code, Cursor) through the company IdP, and API keys (personal or team service-account) for headless agents, CI and scripts. | 13 | Gateways and access | Team gateways (team admins curate from their own servers plus catalog servers) and platform gateways (platform admins curate, shared with selected teams, users or SSO groups). Personal gateways later. A gateway exposes only the tools selected for it; access is granted to teams, users or SSO groups; a tool can require a minimum team role. Every call checks gateway tool list, caller access, server publish status and (later) the user's OAuth consent |
| 14 | Call records | Metadata always (caller, gateway, tool, server, outcome, latency, sizes). Argument/result capture is opt-in per server or gateway, truncated and redacted, with a retention period (platform default, team overrides, as in Grounded) and visible only to the owning team's admins and platform auditors |
| 15 | Phase 3 client credential | Personal API keys ship in Phase 3 (our own implementation; Grounded is only a reference). OAuth for MCP clients and service accounts stay in Phase 4 |
| 16 | Team gateway editing | Team owners and admins create, edit and delete team gateways (a gateway grants access); members read them and connect |
| 17 | Sharing team gateways | Team gateways are for the team's members only; cross-team sharing goes through platform gateways |
| 18 | Resources | Phase 3 exposes tools and prompts; resources and resource templates follow in a later step |
| 19 | Identity header | `Authorization: Bearer <jwt>` when the server has no static `Authorization` header; otherwise `MCP-Gateway-Identity: <jwt>` |
| 20 | Internal MCP servers | Platform admins maintain an allowlist of internal networks (CIDRs) and hostnames (exact or `*.suffix`) that MCP servers may use, each optionally allowing plain `http`. A deployment setting can add entries (read-only in the UI). Loopback, link-local (incl. cloud metadata), unspecified and multicast addresses stay blocked whatever the list says; everything not listed stays blocked as today |
| 21 | OAuth connections | One connection per gateway: an OAuth token is bound to one gateway (`resource` = its URL); connecting a client to several gateways means approving each, unless the client is trusted |
| 22 | Service account roles | A service account has a team role of `member` or `editor` (used for minimum-role checks); never owner or admin |
| 23 | Service accounts and platform gateways | Service accounts reach platform gateways only through grants to their team; no grants to individual service accounts |
| 24 | Trusted clients | The trusted-client allowlist (decision 12) starts with Claude, Claude Code and VS Code; platform admins can edit it |
| 25 | Auth providers *(accepted default)* | Platform admins configure auth providers: generic OAuth 2.0 authorization code with PKCE where the provider supports it, client ID, client secret (sealed with `ENCRYPTION_KEY`, never returned), authorization, token and optional revocation and userinfo endpoints, default scopes, extra authorize parameters. Presets (GitHub, Google, Microsoft Entra ID, Atlassian, Slack, GitLab) only pre-fill the form. Provider endpoints are dialled through the SSRF guard and the internal-network allowlist. No team-owned providers for now |
| 26 | Requirements *(accepted default)* | A server's team (editors and above) sets an optional requirement on the MCP server (provider + scopes) and optional per-capability overrides (none, or other scopes of the same provider). One provider per call. Requirements are part of review: under `approval_required`, a change to a published server's requirement that widens what is sent goes back to review, like a URL change |
| 27 | Delivery *(accepted default)* | For a call that needs a provider, the gateway sends the person's access token in `MCP-Gateway-Provider-Token` and the provider's slug in `MCP-Gateway-Provider`, alongside the identity JWT (decision 19 unchanged). The JWT gains a `provider` claim when a token is attached. Servers and capabilities without a requirement never get either |
| 28 | Missing consent *(accepted default)* | The call is not forwarded. The gateway returns JSON-RPC `-32042` (`URLElicitationRequiredError`, MCP 2025-11-25) with one URL elicitation to `<APP_URL>/connect/{provider}?request=<opaque id>`; the error message also carries the URL. The link works only in that person's browser session, expires after 10 minutes and is used once; afterwards the person retries the call |
| 29 | Tokens *(accepted default)* | One connection per person and provider: tokens sealed at rest, refreshed by the gateway before expiry, union of granted scopes tracked. A failed refresh marks the connection as needing re-consent. People see and revoke theirs on Account › My connections; platform admins see metadata and can revoke anyone's (auditors read). Suspended people keep connections, but their calls are refused as today. Service accounts can't use capabilities that require a provider (a clear error); those capabilities stay listed, with a note in management views |
| 30 | Audit *(accepted default)* | `auth_provider.create/update/delete` and `provider_connection.create/refresh_failed/revoke`; never a token or secret |

| 31 | Rate limits *(accepted default)* | Requests per minute on `/mcp/{slug}` per person (any credential), per personal API key or OAuth connection, per service account and per gateway, counted in PostgreSQL (fixed one-minute windows shared by every replica). Platform admins set defaults; for service accounts and gateways also a ceiling and team overrides (above or below the default, up to the ceiling); each gateway can set its own value. Over a limit: HTTP 429 with `Retry-After` and a JSON-RPC error, recorded as `rate_limited`. The per-process limiters (OAuth endpoints, connect start, and with them sign-in and `/v1`) move to the same store |
| 32 | Payload capture *(accepted default)* | Opt-in per gateway (team owners/admins for team gateways, platform admins for platform gateways) and per server (the server team's owners/admins); a call is captured if either is on. Arguments and result/content, each truncated to 16 KiB, with secret-looking values redacted (provider and bearer tokens, our key prefixes, common secret patterns, extra regexes set by platform admins). Readable only by the owners/admins of the team whose switch captured it, and platform admins and auditors; every view is audited. The identity JWT, provider tokens and client credentials are never captured |
| 33 | Retention *(accepted default)* | Platform periods with team overrides: call metadata 90 days, captured payloads 14 days (at most 90), audit log 400 days (platform only). A leader-elected loop deletes in batches. Legal holds are out of scope |
| 34 | Usage *(accepted default)* | Hourly rollups (calls, errors by outcome, p50/p95 latency, bytes) per gateway, server, capability, team and principal kind; dashboards for teams (their gateways, servers and service accounts) and platform admins (everything), ranges up to 90 days |
| 35 | Metrics *(accepted default)* | Prometheus on a separate listener (`METRICS_ADDR`, off by default); low-cardinality metrics (requests by method/outcome, latency by gateway and server slug bounded by registered objects, rate-limit rejections, token refreshes, health checks, DB pool). No user IDs in labels |
| 36 | Key rotation *(accepted default)* | `API_KEY_PEPPER_PREVIOUS` keeps keys and tokens valid during a pepper rotation (keys re-digested on use); `open-mcp-portal rotate-keys` re-encrypts stored secrets from `ENCRYPTION_KEY_PREVIOUS` to `ENCRYPTION_KEY` and reports counts; `doctor` reports what is still on the old key |
| 37 | CI *(accepted default)* | A GitHub Actions workflow: lint, generated-code check, Go unit and integration tests with a Postgres service, web typecheck/tests/build, `k8s-validate`, docker build. Validated locally with `actionlint`; images are published for `v*` tags by `image.yml` |
| 38 | Suspension blocks, doesn't disconnect *(accepted default)* | Suspending a person ends their browser sessions and refuses every later request at authentication, but keeps their OAuth connections (connected apps), API keys and provider connections, so reactivating restores them. This is the current behaviour, recorded because the user hasn't asked to change it |
| 39 | Upstream auth modes *(accepted default)* | An MCP server's upstream auth is `none`, `static_header` (as today) or `oauth` (per person). In `oauth` mode the person's token goes in `Authorization: Bearer` and the identity JWT moves to `MCP-Gateway-Identity` (decision 19's rule). `oauth` excludes a static `Authorization` header and a Phase 5 requirement on the same server: one credential per call |
| 40 | Server connections *(accepted default)* | An `oauth` server has a server-bound connection config: a provider row of kind `mcp_server`, bound to exactly that server, not listed among platform providers and not reusable. The server's team (editors and above) creates it, which is an exception to decision 25 because the client belongs to the server. It comes from automatic registration (DCR or CIMD) or a client ID and secret entered by hand (secret sealed, never returned). Alternatively the team links an existing platform provider whose endpoints match the discovered authorization server. Admin review (`approval_required`) shows the auth mode, authorization server and scopes; switching a published server to `oauth`, changing the authorization server or widening its scopes sends it back to review |
| 41 | Setup by discovery *(accepted default)* | Entering the URL and choosing "detect" probes the server: a 401 with `resource_metadata` fills in the authorization server, endpoints, `scopes_supported` and registration capability, and the UI shows what was found and what is still needed (a client ID and secret when there's no registration). Every discovery, registration and token request goes through the SSRF guard and the internal-network allowlist (as Phase 5). The `resource` parameter is sent on authorize and token requests (MCP spec), with a per-server switch to omit it for authorization servers that reject it |
| 42 | Discovery and health *(accepted default)* | Capabilities are read with the connection of the person who set the server up (they sign in once during setup, Arcade-style); the server shows "Capabilities read as <person>" and any editor can re-authorize as themselves. Scheduled health checks use nobody's token: an unauthenticated probe that gets the expected 401 challenge for this resource counts as reachable (healthy, "requires sign-in"); a manual Test uses the setup connection. If the setup connection lapses, refresh reports that it needs re-consent |
| 43 | Runtime *(accepted default)* | Every call to an `oauth` server needs the caller's own connection to that server; missing, expired or insufficient means the existing `-32042` consent-link flow (same `/connect` pages, same My connections, labelled with the server's name). An upstream 401 `invalid_token` gets one refresh attempt, then `needs_reconsent` and `-32042`; a 403 `insufficient_scope` asks for re-consent with the requested scope. Service accounts are refused (`-32010`). Tool lists come from discovery; the upstream may show each person different tools and still checks every call |
| 44 | Tokens and audit *(accepted default)* | Phase 5 storage, refresh, revocation and audit events (`provider_connection.*`) are reused, plus `mcp_server.auth_update`. Tokens never appear in logs, audit, call records or captured payloads; payload capture never records the `Authorization` header |
| 45 | Identity token to external servers | Per-server switch `sendIdentity` (default on, keeping decision 7). The UI recommends turning it off for servers run outside the company (for example GitHub's hosted MCP server), so names, emails and teams aren't sent to a third party. Accepted default chosen by the assistant |
| 46 | Name | The product is **Open MCP Portal** (short form OMP, after the full name), formerly Open MCP Gateway, so it no longer clashes with Open Model Gateway (OMG). Module `github.com/ncecere/open-mcp-portal`, binary `open-mcp-portal`, `OMP_*` environment variables, `omp_` metrics, key and token prefixes `omp_`, `omp_sa_`, `ompat_`, `omprt_`, `ompac_`, `ompcl_`, exposed resources `omp://`. Gateways stay the feature's name (curated tool sets at `/mcp/{slug}`), and so do the `MCP-Gateway-*` headers servers receive. Migration `00013_open_mcp_portal` |
| 47 | No stdio hosting | The portal never hosts or runs MCP servers (stdio or otherwise). Servers are remote and reached over Streamable HTTP. A team with a stdio server runs a bridge beside it and registers the bridge. Owner decision, 2026-10-17; supersedes the "later" in decision 10 |
| 48 | Tool-call approvals | In scope as a portal feature: a rule on a tool or gateway can require an approver's approval before a call runs. The call returns a multi-round-trip result (legacy clients: an error) with an approval link; named approvers approve in the portal; the person retries. Approvals expire, are single-use, bound to the arguments and audited. Not a workflow engine. Owner decision, 2026-10-17; who the approvers are is an open question in the roadmap |
| 49 | Tool scoping | Credentials, grants and clients can be limited to a tool class (read, write, destructive) or to named tools, and a gateway tool can constrain its arguments (fixed or allowed values) and be renamed or re-described. Classification is set by server owners; a server's own annotations only prefill it and are never trusted. Owner asked for "tool scoping"; this reading is to be confirmed (roadmap, open questions) |
| 50 | Content scanning later | Prompt-injection and data-loss scanning of tool arguments and results is wanted but not scheduled. Design it before building. Owner decision, 2026-10-17 |
| 51 | MCP spec currency | Support the MCP 2026-07-28 revision as a first-class protocol era alongside the earlier revisions in common use, chosen per request (no `Mcp-Session-Id`; `initialize` means legacy). New revisions are tracked, and features the spec deprecates (roots, sampling, logging, HTTP+SSE) are not added. Owner decision, 2026-10-17 |
| 52 | Who approves a sensitive call | Default approvers are the owners and admins of the server's team (they are accountable for the system the call touches). A rule may name specific people or SSO groups instead. The requester can never approve their own call, even as an owner. If no other eligible approver exists, platform admins approve. Gateway owners are not approvers by default (they decide who may use a tool, not whether a call is safe) but can be named. Owner delegated this to the assistant, 2026-10-17; built in v0.3 |
| 53 | Suspension blocks | Suspending a person blocks their sessions, keys, connected apps and connections while they are suspended; reactivation restores them. It does not delete or disconnect anything. Owner decision, 2026-10-17 (closes the open question in the roadmap) |
| 54 | Protocol versions | Keep accepting every revision currently accepted (2024-11-05 through 2025-11-25) and add 2026-07-28. Negotiation prefers the newest version both sides support. Owner decision, 2026-10-17 |
| 55 | Automation tokens | Two kinds, separate from MCP credentials in both directions (an MCP credential never authorizes `/v1`; an automation token never authorizes `/mcp`): **platform-admin tokens** (created by platform admins, scoped to platform read or write) and **team publisher tokens** (owned by a team, created by its owners and admins, scoped to read or write that team's servers). Mandatory expiry, shown once, revocable, audited. A token can't create tokens. Owner decision, 2026-10-17 |
| 56 | Notifications | Three channels: an in-app inbox (bell, read/unread, 90 days), email through the operator's SMTP (`SMTP_*`; off without `SMTP_HOST`; certificates always verified; plain-text `none` with credentials refused off loopback; reported by `doctor`) and webhooks (team destinations managed by team owners and admins, platform destinations by platform admins; `json` signed with HMAC-SHA256 over `timestamp.body` with a sealed, rotatable secret shown once, or unsigned Slack-compatible `slack`; URLs sealed and checked by the SSRF guard on every send: public https only, and internal destinations only through the operator's `NOTIFY_WEBHOOK_ALLOWED_NETWORKS`, never the MCP servers' allowlist). Eight stable events: `server.unhealthy` (3 failed checks, once per incident, reminder after 24 h), `server.recovered`, `capability.changed`, `publish.requested`, `publish.decided`, `connection.needs_reconsent`, `upstream_signin.lapsed`, `key.expiring` (7 days). Recipients come from live roles at delivery: team events to owners and admins (`server.*`, `capability.changed` and `upstream_signin.lapsed` also editors), platform events to platform admins, personal events to the person. Per-person preferences per event and channel (defaults on). Emitted in the transaction of the change, delivered at least once by a leader-elected outbox loop with retries; delivery failures are shown in the UI, never an event. Design: [notifications.md](notifications.md) |
| 57 | Admin overview and attention | `GET /v1/admin/overview` (platform admins and auditors) and `GET /v1/teams/{team}/attention` (team members) return counts and an attention list computed on request from existing data, each item with a link target (`type` + `id`) the UI routes on: failing and changed published servers, lapsed setup sign-ins, pending reviews with the oldest age, keys and tokens expiring in 14 days, connections needing re-consent, disabled gateways, rate-limited calls and notification failures. The 24 h call and error figures come from the usage rollups and use Admin › Usage's error definition. Members see only what they can already open. Design: [admin-overview.md](admin-overview.md) |
| 58 | Token scopes mechanism | An operation accepts automation tokens only if `api/openapi.yaml` annotates it with `x-omp-token-scopes` (any one listed scope suffices; `:write` includes `:read`); unannotated operations answer `403 token_not_allowed`, and token create/revoke answers `403 session_required`. A contract test enforces that exactly the annotated operations accept tokens. Platform tokens (`platform:read`: every admin `GET` except recorded payloads; `platform:write`: team, gateway, grant and limit provisioning) never decide or widen trust (no role changes, reviews, approvals, trust settings, deletes), and die with their creator's platform-admin role; team publisher tokens (`servers:read`/`servers:write`) outlive their creator, reach only their own team (`404` otherwise) and never delete, approve or touch gateways and members. Prefixes `ompadm_` and `omppub_` join the shared credential classifier and capture redaction. Design: [automation-tokens.md](automation-tokens.md) |
| 59 | Consent for modern clients without URL elicitation | A 2026-07-28 request from a client that did not declare URL elicitation never gets `-32042` (the revision forbids it): a tool call answers a tool result with `isError` and the link in its text, a prompt or resource read `-32010` with the link in the message. Clients that declared it get the `input_required` result; legacy clients keep `-32042`. Owner answered yes, 2026-10-18 |
| 60 | Provider tokens are bound to a server and its origin (F-3) | A platform provider's token (GitHub, Google, ...) is sent only to a server the person allowed, at the origin (scheme, host, port) it had when they consented, and for the scopes they were shown. A grant is a row per (connection, server) with the origin and scopes (`provider_server_grants`, migration `00017`); a call without one gets consent with the new reason `server_not_allowed`, through the same three answer shapes as decision 59. A consent link is for one server and its origin and names the server and its team; when the account already covers the scopes, confirming records the grant with no round trip to the provider, otherwise the provider callback records it. A server's grants are deleted when its URL's origin or its provider changes or it is deleted (a path-only edit keeps them); disconnect, provider delete and user delete cascade. `oauth`-mode providers are unchanged. **No backfill:** every person consents once per server after the upgrade, because a backfill would grandfather any malicious server. Not part of it, and still open (H-5): the token holds the union of every scope the person granted, a server they allowed receives all of them, and there is no per-provider list of teams or servers allowed to require a provider. Owner decided, 2026-10-18 |
| 61 | Test connection sends the identity token | A manual Test (not scheduled checks, not Refresh) of a server with `sendIdentity` on sends the identity token of the editor who pressed it, as a call would: `principal_type` `user`, their ID, email, name and team slugs, `aud` the server's URL, no `tool`, `prompt` or `resource`, `gateway` `omp:test` (not a possible slug) and `client` `Test connection`. A 401 or 403 that goes away on a second probe without the token is reported as a failure (class `auth`, the server's HTTP status) saying the server refuses the token and to turn Send identity token off or have the server accept it; both failing, or the first passing, is the ordinary result. Found with DeepWiki's public endpoint, which refuses any `Authorization` header on a call, while registration, Test, refresh and health checks all passed. **Limit:** a server that accepts the request and refuses only when a tool runs (HTTP 200 with `isError`, which is what DeepWiki does) still passes Test; the portal doesn't read or rewrite tool results to guess. An automation token has no person, so its Test sends no token. Refresh and scheduled checks stay tokenless so what is stored and monitored doesn't depend on who asked. Owner chose this option, 2026-10-18 |
| 62 | A trusted client asks once when it signs in from this computer (H-1) | A trusted client (decisions 12 and 24) still skips the consent screen, except the first time a person signs it in to a gateway with a **loopback redirect** (`http` on `localhost`, `127.0.0.1` or `::1`, any port): then `/oauth/authorize` sends them to the consent page in a *notice* variant ("Your administrators trust Claude Code. It doesn't normally ask, but this is its first sign-in to Support from you. After you continue, it receives the result on this computer, at localhost:54321"), with Continue and Cancel. Continue records the grant (audited `oauth.grant_confirmed`, metadata `how: confirmed`, in place of `oauth.consent`) and issues the code; Cancel sends `access_denied` and records nothing. The notice is per person, client and gateway, so it is asked again after the app is disconnected, for another gateway, and for another person; it is never asked for a trusted client with an `https` redirect, nor for one the person already connected (an upgrade asks nobody: existing grants are remembered). There is no per-client "silent even on first use" switch: it would remove the fix. No migration for it (the grant row is the memory). **What it does not do:** after the first confirmation a local process can still start a flow with the trusted client's ID and a loopback redirect without being asked, so it narrows the silent window to the person's first use rather than closing it; and a process that drives the person's real browser can click Continue. Chosen over accepting the risk (A) and over pinning redirect patterns with a `Sec-Fetch-User` check (C: headers can be spoofed by a local process that drives a browser). The owner delegated the decision and took the issue's recommendation (B), 2026-10-20 |
| 63 | Refresh tokens have an absolute lifetime, and a repeat inside the grace gets the same pair (H-8) | A grant's refresh tokens stop working `OAUTH_REFRESH_ABSOLUTE_TTL` after the person **last signed the app in** (default 180 days; `0` disables; accepts `180d` or `4320h`). The next refresh after that answers `invalid_grant` and revokes the grant with the reason `expired_absolute` (audited `oauth.revoke`); the app signs in again, which is a consent page unless the client is trusted (a trusted loopback client asks again once, decision 62). The lifetime is counted from `oauth_grants.authorized_at` (migration `00018`), not from the row's creation: it is set when the grant is created and again each time the person completes an authorization for a grant they had already allowed, so signing in again starts a new lifetime instead of failing at once on a remembered grant. **Upgrade rule:** every grant active when `00018` runs gets `authorized_at = now()`, so a grant created long ago keeps working and gets one whole window from the upgrade; nobody is signed out by it. Connected apps shows when each app's sign-in expires (`OAuthGrant.expiresAt`, null without a limit). **Inside the 30-second reuse grace** a refresh token that was already rotated gets the **same** access and refresh token again, not a second pair: the pair a rotation issues is derived from the presented refresh token with the pepper (`HMAC-SHA256(API_KEY_PEPPER, "oauth-successor:…" + token)`), so no token is stored in the clear and no extra column is needed; the repeat is audited `oauth.token_issue` with `repeat: true`, is refused if the pair was revoked or deleted, and is subject to the absolute lifetime too. Outside the grace, reuse revokes the grant as before. A token rotated by v0.2.1 in the seconds before the upgrade has a random successor, so a repeat of it inside the grace is refused (the client signs in again). Headless agents should use service accounts or API keys; a client on OAuth must be able to sign in again about twice a year. Chosen: B (absolute lifetime) with C (same pair in the grace) over leaving it (A). The owner delegated the decision and took the issue's recommendation (180 days), 2026-10-20 |
| 64 | Send identity token defaults to off for public servers with no sign-in | Partly reverses decision 45 (default on). When a server is registered with `authMode` `none` and no explicit `sendIdentity`, the portal looks at its host: a **public** host (every address it is or resolves to is a public address, and no internal-allowlist entry names it) gets `sendIdentity` **off**; an **internal** host (named by an allowlist entry, or a private address) gets it **on**; a name that **cannot be resolved** in time is treated as public and gets it **off** (nothing shows the server is the company's, and sending less is the safer mistake). `static_header` and `oauth` servers keep the default **on**. An explicit value, true or false, is always kept. Servers saved before the upgrade keep their stored value; nothing is migrated. The default is chosen once, at registration; the switch can be changed afterwards as before. The add form asks which default applies before saving (`POST …/mcp-servers/identity-default`, session only, no token scope) and says why in a sentence, and it sends the value it shows. Calls record whether the token went to the server (`mcp_calls.identity_sent`, migration `00019`: true, false, or empty when the call was not forwarded or was recorded before the field existed). The call's page shows it and `?identitySent=` filters on it, so a server that rejects the token only when a tool runs (DeepWiki) can be diagnosed from Calls. **Limit:** Test still cannot see that case; the portal does not read tool results to guess. Fixes the DeepWiki class (a public server that refuses any `Authorization` header) and sends less personal data to third parties by default. Cost: a public server that wants the token needs the switch turned on. The owner delegated the choice (issue #5) with "take the issue's recommendation": option B plus the call-record flag of option C. 2026-10-20 |
| 65 | Trusted agent platforms *(owner delegated to the assistant, 2026-10-20; roadmap #55)* | Platform admins trust an external agent platform (first: Pi Durable Platform) as an issuer of agent identity tokens: a name, its issuer (the `iss` of its tokens, an https URL compared exactly), its JWKS URL (default `<issuer>/.well-known/mcp-identity-jwks.json`, checked like an MCP server's URL, an internal address only when the allowlist of internal networks allows it, and **https always**, also for a host the allowlist lets reach over plain http (changed 2026-10-20 after the security review, L-1: plain http was accepted there; it is refused when saved and again before every fetch)) and the audience a token must contain (default `APP_URL`; the platform sets it as its servers' `identityAudience`). Tokens are verified by one strict verifier: ES256 only (never `none`, HS\* or RS\*; the key comes from the JWKS only, never from the token), `kid` and `typ` JWT required, a trusted and enabled `iss`, `aud` (a string or an array) containing the audience, `principal_type` `agent`, `sub`, `team.id` and `jti`, `exp`/`nbf`/`iat` with 30 seconds of skew and a lifetime of at most 10 minutes, and `jti` never seen before (shared by every replica, kept until `exp` plus the skew). ## Proposed build order

1. Foundations from Grounded: config, store, OIDC/dev sign-in, sessions, users, teams, platform admin, audit, UI shell.
2. Upstream server registry with discovery of tools, resources and prompts.
3. Gateways, access policy and the `/mcp/{slug}` endpoint, with signed identity on every upstream call.
4. Client authentication for MCP clients (OAuth for Claude Code, VS Code and similar; API keys for headless agents).
5. Auth providers, per-user token vault and the "authorize this tool" flow.
6. Usage, rate limits, health and execution history.
7. Per-person OAuth to MCP servers that are themselves OAuth-protected (GitHub's remote server).
