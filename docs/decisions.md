# Product decisions

Product decisions and accepted defaults. Release notes and [status.md](status.md) record what has shipped;
[implementation-order.md](implementation-order.md) records the current unreleased work. A decision is not by
itself a claim that its feature is implemented.

## Purpose

A central, self-hosted place for the company to discover and access its many MCP servers. It is closer to
Arcade than to the MCP features in LiteLLM, Bifrost or the Docker MCP Gateway: the portal brokers who the
user is and what each tool may do on their behalf, not only network routing.

MCP clients, including coding assistants and automation, use ordinary portal credentials. Hosting agents and
trusting external platforms to impersonate people are out of scope (decision 81).

| 62 | A trusted client asks once when it signs in from this computer (H-1) | A trusted client (decisions 12 and 24) still skips the consent screen, except the first time a person signs it in to a gateway with a **loopback redirect** (`http` on `localhost`, `127.0.0.1` or `::1`, any port): then `/oauth/authorize` sends them to the consent page in a *notice* variant ("Your administrators trust Claude Code. | 63 | Refresh tokens have an absolute lifetime, and a repeat inside the grace gets the same pair (H-8) | A grant's refresh tokens stop working `OAUTH_REFRESH_ABSOLUTE_TTL` after the person **last signed the app in** (default 180 days; `0` disables; accepts `180d` or `4320h`). The next refresh after that answers `invalid_grant` and revokes the grant with the reason `expired_absolute` (audited `oauth.revoke`); the app signs in again, which is a consent page unless the client is trusted (a trusted loopback client asks again once, decision 62). The lifetime is counted from `oauth_grants.authorized_at` (migration `00018`), not from the row's creation: it is set when the grant is created and again each time the person completes an authorization for a grant they had already allowed, so signing in again starts a new lifetime instead of failing at once on a remembered grant. **Upgrade rule:** every grant active when `00018` runs gets `authorized_at = now()`, so a grant created long ago keeps working and gets one whole window from the upgrade; nobody is signed out by it. Connected apps shows when each app's sign-in expires (`OAuthGrant.expiresAt`, null without a limit). **Inside the 30-second reuse grace** a refresh token that was already rotated gets the **same** access and refresh token again, not a second pair: the pair a rotation issues is derived from the presented refresh token with the pepper (`HMAC-SHA256(API_KEY_PEPPER, "oauth-successor:…" + token)`), so no token is stored in the clear and no extra column is needed; the repeat is audited `oauth.token_issue` with `repeat: true`, is refused if the pair was revoked or deleted, and is subject to the absolute lifetime too. A token rotated by v0.2.1 in the seconds before the upgrade has a random successor, so a repeat of it inside the grace is refused (the client signs in again). Headless agents should use service accounts or API keys; a client on OAuth must be able to sign in again about twice a year. Chosen: B (absolute lifetime) with C (same pair in the grace) over leaving it (A). The owner delegated the decision and took the issue's recommendation (180 days), 2026-10-20 |
