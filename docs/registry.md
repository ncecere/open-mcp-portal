# MCP server registry

Teams register the remote MCP servers they run. The portal discovers each server's **tools, resources, resource templates and prompts**, keeps track of its health, and publishes it to the company **catalog** under the platform's publishing policy ([decisions](decisions.md) 9 and 10, [SPEC](../SPEC.md) §5 and §7 phase 2). Gateways (phase 3) will build on this catalog.

Code: `internal/registry` (servers, capabilities, publishing, health loop), `internal/upstream` (guarded MCP client, SSRF guard), `internal/netpolicy` (the address policy and allowlist), `internal/secrets` (header value encryption), migrations `00003_registry.sql` and `00007_network_allowlist.sql`. Adapted from Grounded's `internal/mcpclient`.

## Servers

| Field | What it is |
|---|---|
| Slug | Unique across the platform and **immutable**: `^[a-z0-9](?:[a-z0-9-]{0,46}[a-z0-9])?$`. Gateways will name tools `slug__tool` |
| Name, description | 1–100 and up to 2000 characters |
| URL | The Streamable HTTP endpoint (see [Security](#security)). Problems return `422 url_not_allowed` with `details.reason` (`invalid`, `too_long`, `userinfo`, `query`, `fragment`, `scheme`, `private_address`, `blocked_address`) |
| Header and value | Optional static header, such as `Authorization: Bearer …` or `X-API-Key: …`. The value is sealed with `ENCRYPTION_KEY` (AES-256-GCM, bound to the server's ID). It is never returned, logged or audited. Responses show only `hasAuth`, the header name and `authValueHint` (the last 4 characters, and only when the value has at least 8). When you update the server, leaving `authValue` out keeps the stored value, and `authHeaderName: ""` removes both. The names `MCP-Gateway-Identity`, `MCP-Gateway-Provider` and `MCP-Gateway-Provider-Token` are reserved (`400 invalid_auth_header`) |
| Auth mode | `authMode`: `none`, `static_header` (the header above) or `oauth`: each person signs in to the server itself, which is an OAuth resource server (GitHub's hosted MCP server). Detect it first (`POST …/mcp-servers/detect-auth`), then save with `oauth` (registration `auto`/`dcr`/`cimd`/`manual`/`platform_provider`, scopes, `sendResource`); the portal discovers again on save, registers its client for DCR, and skips the first discovery (`setupRequired`): an editor signs in with `POST …/{serverId}/oauth/authorize-setup` and capabilities are read as them. `oauth` excludes a static `Authorization` header and a requirement (`422 auth_conflict`). See [phase7-upstream-oauth.md](phase7-upstream-oauth.md) |
| Send identity | `sendIdentity`: off, no identity token is sent to the server (decision 45). **Default (decision 64):** when it is left out at registration, it is **off** for `authMode` `none` on a public host (or a name that cannot be resolved), and **on** for an internal host (an internal-allowlist entry or a private address) and for `static_header` and `oauth` servers. An explicit `true` or `false` is always kept, and servers saved before this change keep their value. The add form shows the default for the address, and why, before you save (`POST /v1/teams/{team}/mcp-servers/identity-default {url}`, session only). Turn it on for a public server that expects the token. Each call record says whether the token went to the server (`identitySent`; see Calls). The token is sent as `Authorization: Bearer …` on every real call and on a manual **Test** (decision 61; not on Refresh, discovery or scheduled checks), so a public server that refuses any Authorization header (found with DeepWiki's `https://mcp.deepwiki.com/mcp`: "Authentication is not allowed on the public DeepWiki endpoint") would fail on its calls while this is on; since decision 64 it starts off for such a server, and servers registered before that keep their value. Test catches a server that refuses the request itself (see Health); **it does not catch one that accepts the request and refuses only when a tool runs** (DeepWiki answers `initialize` and `tools/list` normally and fails the tool call, an HTTP 200 result with `isError`), so a passing Test is not proof that calls work. Turn it off for servers outside the company |
| Requires a present person | `requiresPresentPerson` (default off; editors and above) refuses calls an agent platform relays for a person when the platform says the person is not present (scheduled or background work); each capability can override it (`PUT …/capabilities/{id}/present-person`: `inherit`, `required`, `not_required`; the capability's value wins). Calls not relayed for a person are never affected. Turning it on needs no review; relaxing it (a capability that required a present person no longer does) sends a published server back to review under `approval_required` (reason `requirement_changed`, audit `mcp_server.publish_request`). An automation token can't change it. See [agent-platforms.md](agent-platforms.md) |
| User authorization | Optional `requirement` (an auth provider and scopes) whose user token calls receive, with per-capability overrides (`PUT …/capabilities/{id}/requirement`). A change that widens what is sent sends a published server back to review under `approval_required` (reason `requirement_changed`). See [phase5-delegated-credentials.md](phase5-delegated-credentials.md) |
| Timeout | 1–120 s (default 30). It bounds the whole exchange |
| Enabled | A disabled server is skipped by the health loop, can't be published and drops out of the catalog |

Creating a server runs discovery straight away. The server is created even if discovery fails; in that case `refreshError` and `lastRefreshError` say why. Changing the URL or the header deletes the server's stored health checks. Changing the URL of a published server under `approval_required` sends it back to `pending` (audited as `mcp_server.publish_request` with reason `url_changed`): it leaves the catalog until a platform admin reviews the new endpoint. Under `self_publish` it stays published. A URL on another **origin** (scheme, host or port) never keeps the stored header value: `422 auth_value_required` unless the same request sends a new `authValue` or removes the header (in `oauth` mode it resets every connection and sends the server back to the setup sign-in); the audit entry has `oldOrigin` and `newOrigin`. Any URL change also clears `refreshedAt` and reads the capabilities again from the new endpoint at once (a failure is stored as `lastRefreshError`); a platform admin can't approve a server whose capabilities haven't been read from its current URL (`409 not_refreshed`). Switching a published server to `oauth`, another authorization server, or a scope not asked for before also sends it back (reason `upstream_auth_changed`); narrowing scopes, changing the client or leaving `oauth` doesn't.

## Discovery and change detection

**Refresh** connects and lists every kind the server advertises. It reads every page, accepts at most 500 entries per kind, and gives up after 500 pages or on a repeated cursor. Each response is at most 1 MiB. Titles are clipped to 200 characters and descriptions to 10,000. Names and URIs can be up to 1000 characters; longer or invalid entries are skipped. A definition over 64 KiB fails discovery. A kind that the server advertises but answers with "method not found" counts as empty. Discovery never calls a tool, and the portal offers no roots, sampling or elicitation to a server it reads (calls forwarded for a client that declared elicitation are another matter: [mcp-protocol.md](mcp-protocol.md#relaying-a-servers-elicitation)).

**Protocol era.** The portal tries the newest protocol first and falls back to the older handshake only when the server isn't a 2026-07-28 server; the full rule, the cache and what it records are in [mcp-protocol.md](mcp-protocol.md#the-portal-as-a-client-of-your-servers). A refresh, a test and a health check that read the server store the era (`legacy` or `modern`) and version they negotiated on the server (`protocol` in the API: `era`, `version`, `negotiatedAt`; null until the first successful read; cleared when the URL changes). A failing check leaves what was stored.

Each capability stores its **definition**: the listed object as canonical JSON (sorted keys, numbers kept exactly) without `_meta`, which servers use for data that changes between calls. Its **fingerprint** is the SHA-256 of that JSON.

- **approved** means `approved_fingerprint = fingerprint` and the capability is still listed. A gone capability is never approved.
- **changed** means the capability was approved before, its definition is different now, and the server is published. A changed capability drops out of the catalog straight away, without anyone touching it.
- A capability the server stops listing is marked **gone**, and its approval is withdrawn. If the server lists it again later, it needs approval like a new one.
- **Approval is bound to what was reviewed.** `McpServer.reviewDigest` is a SHA-256 over the server's URL, auth mode and requirement and every listed capability's kind, name and fingerprint. (and the server's requires-a-present-person switch when it is on). Approving a server sends it back (`expectedDigest`), approving a capability sends the capability's `expectedFingerprint`; a refresh or edit between reading and clicking changes them, and the approval fails with `409 changed_since_review` (details `currentDigest` or `currentFingerprint`) without approving anything. Publishing under `self_publish` takes an optional `expectedDigest` with the same check.
- A refresh never approves anything. On a published server, **new** capabilities stay unapproved too. `pendingChanges` counts every listed capability whose current definition isn't approved: changed ones **and new ones**.

The result reports `listed`, `added` (a returning capability counts as added), `changed` and `gone`, and is audited with those counts.

## Publishing

States are `private`, `pending`, `published` and `rejected`. The **effective policy** is the team's override if one is set, otherwise the platform default (`approval_required` out of the box).

| Action | Who | Effect |
|---|---|---|
| Publish (`note` optional) | team owners and admins | `approval_required`: the server becomes `pending`. `self_publish`: it is `published` straight away and its current capabilities are approved. Errors: `409 not_refreshed`, `disabled`, `already_published`, `already_pending` |
| Review approve (`expectedDigest` required) | platform admins | `pending` only: the server becomes `published` and its current capabilities are approved, if the server's `reviewDigest` is still the one the admin read (`409 changed_since_review`; `400 expected_digest_required`) |
| Review reject | platform admins | `pending` or `published`: the server becomes `rejected`. Anything else is `409 invalid_state` |
| Unpublish | team owners and admins | `pending`, `published` or `rejected`: the server becomes `private`. A private one gets `409 not_published` |
| Approve a capability | platform admins; team owners and admins only under `self_publish` (otherwise `403 approval_required`) | Published servers only (`409 not_published`). Also `409 not_changed` and `409 capability_gone`. The body names the fingerprint the approver read (`expectedFingerprint`, required: `400 expected_fingerprint_required`); another one now is `409 changed_since_review` and approves nothing |

Publishing actions bump the server's revision. A platform admin sets the default with `PUT /v1/admin/settings/publishing` and a team override with `PUT /v1/admin/teams/{team}/publishing`. Both need `If-Match`; the team override uses the team's revision and bumps it.

**Changing the policy doesn't change any server's state.** Servers already `pending` stay pending, in the review queue, until a platform admin reviews them or the team withdraws them (unpublish); nothing is approved or dropped on their behalf. Under `self_publish` (a new default or an override) a pending server's owners and admins can simply publish it: it is published at once with its current capabilities approved, as from `private`. Moving back to `approval_required` leaves published servers published. The policy in force when an action happens is the one that applies (for example, a URL change on a published server goes back to review only under `approval_required`).

The **catalog** lists servers that are published and enabled and whose team is active, and shows only their approved, listed capabilities. Its counts cover only those capabilities. Its health has a status, a time and an error class, but no message. Any active signed-in person can read it.

|---|---|---|---|---|---|
| team member | ✓ | | | | |
| team editor | ✓ | ✓ | | | |

| platform auditor | ✓ (any team, plus admin routes) | | | | |
| platform admin | ✓ (any team, plus admin routes) | | | admin route | ✓ |

Platform roles never change servers through the team routes. People outside the team get `404`, as in phase 1. Archived teams are read-only (`409 team_archived`), and their servers are unavailable everywhere until the team is unarchived: they leave the catalog and gateway-options, the health loop skips them, and gateways show their capabilities as `team_archived` ([phase3-gateways.md](phase3-gateways.md)). Archiving changes no data, so unarchiving restores everything.

## Health

For a server in `oauth` mode, Test and Refresh use the setup connection (`readAs`; Refresh answers `409 setup_reconsent_required` when it lapsed, or its person is no longer an editor), and scheduled checks send an unauthenticated `initialize`: the expected `401` Bearer challenge for the server's resource metadata is healthy with `signInRequired` ("requires sign-in"). Test, refresh and the background loop each store a check: ok or failed, latency, trigger (`manual` or `scheduled`), error class, HTTP status, and a short message with the header value and anything secret-looking redacted. The server keeps its latest 100 checks. `statusSince` carries over while the outcome stays the same, so a "failing since" time survives pruning. Error classes: `unavailable`, `auth`, `not_found`, `rate_limited`, `bad_request`, `bad_response`, `config` (the header can't be decrypted), `timeout`, `too_large`, `not_allowed` (a blocked or unallowed address, or a redirect).

**What Test sends (decision 61).** Test behaves like a call as far as the server can see: when the server's **Send identity** is on, it sends the identity token of the editor who pressed the button ([upstream-identity.md](upstream-identity.md#what-a-test-sends)). If the server answers `401` or `403` to that, the portal reads the server once more without the token; when only that second read works, the Test fails with class `auth`, the server's HTTP status and the message "The server accepts the portal's requests without its identity token but refused them with it. Turn off Send identity token for this server, or have the server accept the token." (stored as the manual check like any failed Test). If both fail, the ordinary failure is shown, and if the first read passes, so does the Test. The token is never returned, logged or audited. Refresh and the scheduled loop send no token: Refresh stores what a server lists, which shouldn't depend on who asked, and the loop has no caller. An automation token that runs a Test has no person, so it sends none. Honest limit: Test lists capabilities and calls no tool, so a server that refuses the token only at tool execution still passes it.

The loop runs at start-up and then every `HEALTH_CHECK_INTERVAL` (default `5m`, `0` turns it off, minimum `30s`). It tests enabled servers of active teams four at a time. Only one replica runs a pass at a time (PostgreSQL advisory lock `omp.mcp-health-checks`), and any server checked within the last 90% of the interval is skipped, so replicas taking turns don't check it twice.

## Security

- **Addresses** (code: `internal/netpolicy`, `internal/upstream/guard.go`). Every address is in one of three classes:
  - **Always blocked**, whatever the allowlist says: loopback (`127.0.0.0/8`, `::1`), link-local (`169.254.0.0/16` including the cloud metadata address `169.254.169.254`, `fe80::/10`), unspecified (`0.0.0.0`, `::`), `0.0.0.0/8`, multicast (`224.0.0.0/4`, `ff00::/8`), broadcast (`255.255.255.255`), other metadata endpoints (`168.63.129.16`, `100.100.100.200`, `fd00:ec2::254`), and the IPv4-mapped (`::ffff:a.b.c.d`), IPv4-compatible (`::a.b.c.d`) and NAT64 (`64:ff9b::/96`) forms of those. Zoned IPv6 addresses too. `localhost` and `*.localhost` are refused by name.
  - **Public**: allocated public unicast. Allowed, over https only (as before).
  - **Private**: everything else (RFC 1918, CGNAT, ULA, documentation, benchmarking and reserved ranges). Allowed only when (a) the URL's host is a literal address inside a `cidr` entry, (b) the URL's host matches a `host` entry, or (c) the host name resolves to it and it is inside a `cidr` entry. Otherwise `422 url_not_allowed` with reason `private_address` when saving a literal address, or error class `not_allowed` when dialling.
- **Allowlist entries.** `cidr`: an IPv4 or IPv6 prefix, canonicalised (`10.20.3.4/16` is stored as `10.20.0.0/16`, a bare address as `/32` or `/128`, an IPv4-mapped prefix as its IPv4 form); a prefix entirely inside an always-blocked range is refused (`always_blocked`). `host`: an exact host name (`mcp.corp.example.com`) or `*.suffix`, which matches subdomains only (`*.corp.example.com` matches `a.corp.example.com` and `a.b.corp.example.com`, not `corp.example.com` or `evilcorp.example.com`). Host names are lower-cased, lose a trailing dot, and must be ASCII letter-digit-hyphen labels (use punycode, `xn--…`, for international names); no scheme, port, path, address or `localhost`. URL hosts are compared the same way (case and a trailing dot don't matter; the port is not part of the host). Each entry has `allowHttp` and an optional `note` (at most 200 characters). Problems are `422 invalid_entry` with `details.index` and `details.reason` (`invalid_kind`, `invalid_cidr`, `invalid_host`, `non_ascii`, `ip_as_host`, `always_blocked`, `invalid_note`, `duplicate`, `too_many`).
- **Where entries come from.** Platform admins manage up to 100 in **Admin › Internal networks** (`GET`/`PUT /v1/admin/settings/network`, `If-Match` on its own revision, audited as `settings.network_update` with the lists before and after). The deployment adds entries with `UPSTREAM_ALLOWED_NETWORKS` (comma-separated; kind inferred; an `http:` prefix sets `allowHttp`, for example `10.20.0.0/16,http:*.svc.cluster.local,mcp.corp.example.com`); an invalid one fails configuration loading, and the UI shows them read-only. Both lists apply together.
- **Plain http** is allowed only when the URL's host matches a `host` entry with `allowHttp`, or is a literal address inside a `cidr` entry with `allowHttp`. A name that merely resolves into an http-allowed network still needs https. Everything else must be https (reason `scheme`).
- **When it's checked.** **When the server is saved**: the URL's shape, the scheme, literal addresses and `localhost`. **Before every exchange** (refresh, test, health check, forwarded call): the stored URL against the current policy. **Every time the portal dials**: every address the host resolves to must be allowed (one blocked or unallowed address refuses the connection, so DNS rebinding to `169.254.169.254` is refused even for a host entry), and the connection is pinned to the checked addresses. Redirects are never followed. Proxy environment variables are ignored. URLs can't contain user info, a query or a fragment: credentials belong in the header.
- **Changes are live.** Dials read a cached copy of the admin entries that is refreshed at most every **30 seconds**; the replica that saves a change applies it at once, other replicas within 30 seconds. If the database can't be read, the last copy stays in force. Changing the entries never edits servers: a server outside the new policy fails its next exchange with error class `not_allowed`, and its health shows failing.
- **Checking a URL.** `POST /v1/admin/settings/network/check` with `{url}` (platform admins and auditors) applies the same rules with this replica's copy: it resolves the host (at most 3 seconds) but never connects, and returns `allowed`, a `reason` (`public`, `cidr_entry`, `host_entry`, `development`; or `blocked_address`, `private_address`, `dns_failed`, or a URL problem such as `scheme`), a `message`, the `matchedEntry` and each resolved address with its own verdict.
- **Development:** when `DEV_AUTH=true` with a loopback `APP_URL`, plain `http://` to loopback hosts and private, loopback and link-local addresses are allowed, as before (allowlist entries also apply). This allowance never exists in production.
- **Secrets:** `ENCRYPTION_KEY` is required by `serve`. Outside loopback, the server refuses to start with the example key from `.env.example`. `ENCRYPTION_KEY_PREVIOUS` still decrypts values sealed with the old key; re-entering a value re-seals it with the current key. The audit log records only `authValueChanged`.
- **Untrusted text:** descriptions and schemas are prompts a model will read. Review them before you approve, and treat annotations as hints only.

## Local fake server

`make fake-mcp` starts `cmd/fakemcp` on `http://127.0.0.1:8091/mcp`. It has tools `check_outage`, `search_tickets`, `create_ticket`, and for gateways `whoami`, `provider_token` and `echo` (see [upstream-identity.md](upstream-identity.md); `-gateway-tools=false` leaves them out), the resource `status://services`, the template `status://services/{service}` and the prompt `incident_summary`. `-header`/`-value` make it require a header. `-describe tool=text` (or `FAKEMCP_DESCRIBE`, with entries separated by `;`) changes a tool's description, so the next refresh sees a change. `-protocol legacy|modern|both` makes it speak one protocol era only (a legacy server answers a modern probe with a plain-text `400`; a modern one is stateless and refuses `initialize`), `-mrtr-tools` adds `ask_form`, `ask_url` and `ask_sampling` (they answer `input_required`) and `-stream-tools` adds `progress` and `block` and answers with SSE.
