# MCP server registry

Teams register the remote MCP servers they run. The portal discovers each server's **tools, resources, resource templates and prompts**, keeps track of its health, and publishes it to the company **catalog** under the platform's publishing policy ([decisions](decisions.md) 9 and 10, [SPEC](../SPEC.md) §5 and §7 phase 2). Gateways (phase 3) will build on this catalog.

Code: `internal/registry` (servers, capabilities, publishing, health loop), `internal/upstream` (guarded MCP client, SSRF guard), `internal/netpolicy` (the address policy and allowlist), `internal/secrets` (header value encryption), migrations `00003_registry.sql` and `00007_network_allowlist.sql`. Adapted from Grounded's `internal/mcpclient`.

## Servers

| Field | What it is |
|---|---|
| Slug | Unique across the platform and **immutable**: `^[a-z0-9](?:[a-z0-9-]{0,46}[a-z0-9])?$`. Gateways will name tools `slug__tool` |
| Name, description | 1–100 and up to 2000 characters |
| URL | The Streamable HTTP endpoint (see [Security](#security)). Problems return `422 url_not_allowed` with `details.reason` (`invalid`, `too_long`, `userinfo`, `query`, `fragment`, `scheme`, `private_address`, `blocked_address`) |
| Credential (header and value, or parts) | The server's own static credential. **One header** (the original form): `authHeaderName` and `authValue`, such as `Authorization: Bearer …` or `X-API-Key: …`; leaving `authValue` out of an update keeps the stored value and `authHeaderName: ""` removes both. **Parts** (decision 70, [below](#a-servers-own-credential-parts)): `credentials`, a list of up to eight parts (a header, a bearer token, Basic user and password, a query parameter). Every value is sealed with `ENCRYPTION_KEY` (AES-256-GCM, bound to its row), never returned, logged or audited; responses show `hasAuth`, `credentials` (kind, name and a hint of the last 4 characters when the value has at least 8) and, for a server still on the single header, `authHeaderName` and `authValueHint`. The names `MCP-Gateway-Identity`, `MCP-Gateway-Provider` and `MCP-Gateway-Provider-Token` are reserved (`400 invalid_auth_header`) |
| TLS | `tls` (`caPem`, `clientCertPem`, `clientKeyPem`, `clear`): a private CA for this server and a client certificate for mTLS; see [TLS to the server](#tls-to-the-server). Responses carry facts about the certificates, never the key |
| Auth mode | `authMode`: `none`, `static_header` (the credential above, one header or parts), `person_secret` (each person's own key, below), `machine_oauth` (the portal's own OAuth client, below) or `oauth`: each person signs in to the server itself, which is an OAuth resource server (GitHub's hosted MCP server). Detect it first (`POST …/mcp-servers/detect-auth`), then save with `oauth` (registration `auto`/`dcr`/`cimd`/`manual`/`platform_provider`, scopes, `sendResource`); the portal discovers again on save, registers its client for DCR, and skips the first discovery (`setupRequired`): an editor signs in with `POST …/{serverId}/oauth/authorize-setup` and capabilities are read as them. `oauth` excludes a static `Authorization` header and a requirement (`422 auth_conflict`). See [phase7-upstream-oauth.md](phase7-upstream-oauth.md) |
| Person secret | `authMode: person_secret` with `personSecret` (`placement`, `name`, `prefix`, `label`, `help`): each person enters their own key under Account › My connections and their calls carry it as a header, a bearer token or a query value. Keys are sealed per person, server and origin and never returned. See [Each person's own key](#each-persons-own-key-person_secret) and [person-secrets.md](person-secrets.md) (decision 72) |
| Machine OAuth | `authMode: machine_oauth` with `machineOAuth` (token endpoint, client ID and secret, scopes, optional audience and resource): the portal gets its own token with the client credentials grant and sends it as the bearer on every request, for every caller. The secret is sealed and never returned; a new token endpoint, client or server origin needs it entered again. See [machine-oauth.md](machine-oauth.md) (decision 73) |
| Send identity | `sendIdentity`: off, no identity token is sent to the server (decision 45). **Default (decision 64):** when it is left out at registration, it is **off** for `authMode` `none` on a public host (or a name that cannot be resolved), and **on** for an internal host (an internal-allowlist entry or a private address) and for `static_header` and `oauth` servers. An explicit `true` or `false` is always kept, and servers saved before this change keep their value. The add form shows the default for the address, and why, before you save (`POST /v1/teams/{team}/mcp-servers/identity-default {url}`, session only). Turn it on for a public server that expects the token. Each call record says whether the token went to the server (`identitySent`; see Calls). The token is sent as `Authorization: Bearer …` on every real call and on a manual **Test** (decision 61; not on Refresh, discovery or scheduled checks), so a public server that refuses any Authorization header (found with DeepWiki's `https://mcp.deepwiki.com/mcp`: "Authentication is not allowed on the public DeepWiki endpoint") would fail on its calls while this is on; since decision 64 it starts off for such a server, and servers registered before that keep their value. Test catches a server that refuses the request itself (see Health); **it does not catch one that accepts the request and refuses only when a tool runs** (DeepWiki answers `initialize` and `tools/list` normally and fails the tool call, an HTTP 200 result with `isError`), so a passing Test is not proof that calls work. Turn it off for servers outside the company |
| User authorization | Optional `requirement` (an auth provider and scopes) whose user token calls receive, with per-capability overrides (`PUT …/capabilities/{id}/requirement`). A change that widens what is sent sends a published server back to review under `approval_required` (reason `requirement_changed`). See [phase5-delegated-credentials.md](phase5-delegated-credentials.md) |
| Timeout | 1–120 s (default 30). It bounds the whole exchange |
| Enabled | A disabled server is skipped by the health loop, can't be published and drops out of the catalog |

Presence controls have been [retired](platform-retirement.md). They are absent from the active contract and review digest. Digest version `omp-review-v6` (v5 plus the sensitivity and lifecycle, see [Governance](#governance)) forces pending reviewers to reload; classification and security-review gates remain.

### Auth modes

Five modes say how the portal authenticates to a server; each has its own secrets, and a server is in exactly one. TLS to the server ([below](#tls-to-the-server)) is separate and works with every mode.

| `authMode` | Whose credential | Sent as | Secret kept (sealed with `ENCRYPTION_KEY`) | Docs |
|---|---|---|---|---|
| `none` | none | The identity token in `Authorization: Bearer` (unless `sendIdentity` is off) | none | [upstream-identity.md](upstream-identity.md) |
| `static_header` | the team's | The static credential (`credentials`, or one header) with every request; the identity token moves to `MCP-Gateway-Identity` when a part sets `Authorization` | each part's value | [A server's own credential](#a-servers-own-credential-parts) |
| `person_secret` | each person's own key | The key as a header, a bearer token or a query value, in the placement the team chose; static parts that don't clash stay | one key per person and server (`person_secrets`), bound to the origin it was entered for | [person-secrets.md](person-secrets.md) |
| `machine_oauth` | the portal's | Its own OAuth token (client credentials grant) in `Authorization: Bearer`, the identity token in `MCP-Gateway-Identity` | the client secret (`mcp_server_machine_oauth`); tokens only in memory | [machine-oauth.md](machine-oauth.md) |
| `oauth` | each person's own sign-in | The person's token in `Authorization: Bearer`, the identity token in `MCP-Gateway-Identity` | each person's tokens (`provider_connections`) | [phase7-upstream-oauth.md](phase7-upstream-oauth.md) |

`person_secret`, `machine_oauth` and `oauth` each send one credential per call and so exclude a user authorization `requirement` (`422 auth_conflict`); `oauth` and `machine_oauth` also exclude a static `Authorization` part, and `person_secret` a static part that sets the same header or query parameter as its placement.

**Switching modes cleans up the old mode's secrets** (audited). Leaving `person_secret` deletes everyone's keys (`mcp_server.person_secrets_reset`, reason `mode_changed`); leaving `machine_oauth` deletes the client and its secret and drops the cached token (`mcp_server.auth_update`, `machineOAuthRemoved`); leaving `oauth` deletes the connections. The static credential and the TLS settings are not a mode's, so they stay. **A URL on another origin (F-1)** never carries any secret along: static parts (`422 auth_value_required`), the machine client secret (`422 client_secret_required`) and the TLS client key (`422 tls_key_required`) must be entered again in the same request, and every person's key is deleted. A published server goes back to review under `approval_required` when it enters `person_secret`, `machine_oauth` or `oauth`, or changes what a reviewer approved in one (placement, token endpoint, client, audience, resource, a new scope) or its CA; the review digest (`omp-review-v6`) covers all of it. Automation tokens set none of these fields (`403 token_not_allowed`: `personSecret`, `machineOAuth`, `tls`, or a switch of `authMode` into a secret mode, on create and update). `ENCRYPTION_KEY` rotation re-seals every secret above.

**Migrations.** `00024` (`person_secret`) and `00025` (`machine_oauth`) each read the check `mcp_servers_auth_mode_check` as it stands in the catalog and *add* their value to it, so they apply in either order and twice, and the check keeps every mode (`TestAuthModeConstraintAcceptsEveryMode`). Each Down removes only its own value and never fails because servers of another mode exist: a server in the removed mode goes back to `static_header` when it still has a static credential of its own (a legacy header or parts), else to `none`, and the secrets of the removed mode go with their tables. `00026` widens a different check (`mcp_health_checks.error_class`, for class `tls`) and touches no mode.

### A server's own credential (parts)

*(Decision 70; roadmap #23; migration `00022`.)* A server's static credential is an ordered list of at most **eight parts**, saved with `credentials` on create and update:

| Part | Sent as | Fields |
|---|---|---|
| `header` | the header `name` with `value` | `name` (a valid header name; not a name the portal owns: `Host`, `Content-Type`, `MCP-Gateway-*`, …), `value` |
| `bearer` | `Authorization: Bearer <value>` | `value` |
| `basic` | `Authorization: Basic base64(user:password)` | `value` (the user name, no colon), `secondary` (the password) |
| `query` | the query parameter `name=value` added to the request | `name` (`^[A-Za-z0-9_.-]{1,64}$`, never `mcp-*`), `value` (URL-encoded when sent) |

Every part is sealed on its own (AAD `mcp_server_credential:<id>`; a Basic password under `…:<id>:secondary`, so the two can't be swapped), never returned, logged, audited or recorded; `hint` is the last four characters of a value of eight or more (of the password for Basic). A server has at most one part of a kind and name (name without case; one bearer, one basic), and **at most one part that sets `Authorization`** (a header named `Authorization`, a bearer or a basic part): `422 auth_conflict` (`details.reason` `authorization_twice`); in `oauth` mode none (`static_authorization`, decision 39), though other parts may stay. Errors carry `details.field` `credentials[i]`: `400 too_many_credentials`, `invalid_credential_kind`, `invalid_auth_header`, `invalid_auth_query`, `invalid_auth_value`, `invalid_credential`.

**An update sends the whole list.** `credentials: [...]` replaces the credential: a part with `keep: true` (and its `kind` and `name`) keeps its stored values, any other part has its values entered again, a part left out is removed, `[]` removes the credential (the mode then follows: none). Omit `credentials` to keep it. `authHeaderName` and `authValue` can't be sent with it (`400`), and can't edit a server that has been saved with the list (`422 credentials_in_use`). Renaming a part is removing one and adding another (its value is entered again). A request that keeps every part in order writes nothing (no revision, no audit entry).

**Where it is stored.** `mcp_server_credentials` (one row per part). The legacy columns `mcp_servers.auth_header_name`, `auth_value_cipher` and `auth_value_hint` are not rewritten by the migration: a server that has no rows there keeps its one header in them and the registry reads it as a single `header` part (it shows in `credentials` too). Saving the list moves the credential into the table and clears the legacy columns in the same transaction, so it lives in one place, never both (a kept legacy header is opened and sealed again under its new row). Folding the legacy columns in is a later contract migration. A rollback to the previous release reads a server with parts as one with no credential (it ignores the table), so roll back only with that in mind, or save such servers' credential as one header first.

**The query part.** A saved URL with a query is still refused (`422 url_not_allowed`, reason `query`): `upstream.NormalizeURL` is unchanged. A query part is added **at request time**, on a copy of the request in the transport (`internal/upstream/credentials.go`): merged into any query the request has (a parameter of the same name is replaced, the others are kept as they are), and never in the stored URL, the era cache key, the audit entries or the messages. The request the SDK and `net/http` see carries no query, and the response's request is put back to it, so nothing that prints a URL (the SDK's errors included) can show the value. Redaction covers what a server may repeat back: every part's value, the Basic password and the base64 string, the identity token, each also **URL-encoded** (`+` and `%20` forms), in error messages and the health message (`upstream.SafeMessage`, which takes a list), in the log lines built from them and in captured payloads (`capture.Redactor`). A query value is only as private as the server that receives it (servers and proxies often log addresses), so the form warns and a header is better whenever the server accepts one.

**Origin rule (F-1) for every part.** A URL on another origin never keeps a stored value: the request must send `credentials` with **every part's values entered again** (no `keep`; a Basic part needs the user and the password), or `[]`, or `authMode` none; otherwise `422 auth_value_required` with `details.field` `credentials[i]`, `details.kind` and `details.name`. Checked before any request to the new host and again under the row lock. A query value is sent only to the origin it was entered for, like a header. The review digest (`reviewDigest`) covers the **kind and name** of every part (never a value), so a part added after a reviewer looked makes their approval stale (`409 changed_since_review`); adding, changing or removing parts does **not** send a published server back to review by itself (decision 70: nothing new is sent to a new origin).

**Calls.** Every request to the server carries every part: discovery, Refresh, the manual Test, the scheduled health check and forwarded calls. When a part sets `Authorization`, the caller's identity token arrives in `MCP-Gateway-Identity`, as with a static `Authorization` header ([upstream-identity.md](upstream-identity.md#where-the-token-arrives)). The first update to the audit entry (`mcp_server.update`, `mcp_server.create`, `mcp_server.delete`) names each part's kind and name under `credentials`, never a value. An automation token can't send `credentials` for a server that has a credential (`403 token_not_allowed`, [automation-tokens.md](automation-tokens.md)). The editor is Settings › Authentication › Static credential; `ENCRYPTION_KEY` rotation re-encrypts both ciphers (`rotate-keys`).

### Each person's own key (`person_secret`)

*(Decision 72; roadmap #22; migration `00024`; [person-secrets.md](person-secrets.md).)* With `authMode: "person_secret"` and `personSecret: {placement, name, prefix, label, help}` the server's credential is not the team's: each person enters their own key (Account › My connections), sealed per person, server and origin, and their calls carry it as a `header`, `bearer` or `query` value. It excludes a requirement and a static part that sets the same header, query parameter or `Authorization` (`422 auth_conflict`). Other static parts may stay and are sent with everyone's calls. A new origin, mode or placement deletes everyone's keys (audited `mcp_server.person_secrets_reset`); capabilities are read with an editor's own key, and scheduled health checks send none (a `401` or `403` is healthy).

### TLS to the server

*(Decision 74; roadmap #25; migration `00026`.)* An internal MCP server often sits behind a private CA and wants a **client certificate** (mTLS). A server can have both, saved with `tls` on create and update (Settings › TLS to the server): paste PEM text or choose a file.

| Field | What it is |
|---|---|
| `caPem` | PEM certificates only: the CA that signed the server's certificate, with any intermediates (at most 10 certificates, 64 KiB; a private key block is refused). `""` removes it |
| `clientCertPem` | The certificate chain the portal presents when the server asks for one, leaf first. `""` (with no key) removes the certificate and its key. Sent alone, it must belong to the stored key (a renewal) |
| `clientKeyPem` | One **unencrypted** PKCS#8, PKCS#1 or SEC1 PEM key that belongs to the first certificate. Write-only |
| `clear` | Removes everything; not with other fields |

**The CA replaces the system roots for that server.** With a CA set, this server's certificate must chain to it, and nothing else is trusted for it: a public CA can't vouch for an internal host, and the private CA vouches for no other server, because each exchange builds its own trust pool. There is no "system roots plus this CA" mode. **Verification can't be turned off:** the host name in the URL is always checked against the certificate's Subject Alternative Names (a common name alone does not count), the minimum is TLS 1.2 (1.3 when both sides speak it), and no field, setting or environment variable skips any of it. A certificate without the host name fails with an error that says so (`class tls`: "The server's certificate isn't valid for the host name … it lists … in its Subject Alternative Names"). The address rule is a different layer and is unchanged: the dialer still resolves once, checks every address and pins the connection, a private address still needs an internal-network entry, redirects are refused and the proxy is never used; TLS runs over the connection it returns.

**Validation when saved (`422 invalid_tls`, `details.field` `tls.caPem`, `tls.clientCertPem` or `tls.clientKeyPem`, `details.reason`).** PEM only, with nothing around the blocks (`not_pem`); sizes (`too_large`, `too_many_certificates`); a private key in a certificate field (`private_key_in_certificate_field`); a key that is passphrase-protected (`encrypted_key`: remove the passphrase first, for example `openssl pkey -in key.pem -out key-plain.pem`), is not a private key (`not_a_private_key`) or can't be read (`invalid_key`); a key that is not the first certificate's (`key_mismatch`); the client certificate expired or not yet valid (`expired`, `not_yet_valid`) or, when it names its uses, not for client authentication (`not_for_client_authentication`); RSA below 2048 bits, an ECDSA curve other than P-256, P-384 and P-521, or another key type (`weak_key`); an MD5 or SHA-1 signature, unless self-signed (`weak_signature`); a CA bundle in which every certificate has expired (`expired`; one expired root next to valid ones is fine, as in a rotation). A certificate without its key, or a key without its certificate, is refused (`key_required`, `key_without_certificate`). The messages never quote the input.

**The key.** Sealed with `ENCRYPTION_KEY` in `mcp_server_tls.client_key_cipher` with the AAD `mcp_server_tls:<server id>:client_key` (bound to the server and the field: a ciphertext moved to another row, or opened as a header value, does not open); `rotate-keys` re-seals it. It is never returned, logged, audited or captured; the audit entries (`mcp_server.create`, `.update`, `.delete`) carry whether each part is set and the **fingerprints** (`caSha256`, `clientCertSha256`) and expiry, and `tlsCaChanged` and `tlsClientCertChanged` say what changed. A stored key that no longer opens (the `ENCRYPTION_KEY` was lost) is class `config`: upload the certificate and key again.

**What responses show.** `McpServer.tls`: for the CA the fingerprint of the bundle and each certificate's subject, issuer, fingerprint and validity; for the client certificate the same, `chainLength`, `hasKey` and a `status` (`valid`, `expiring` within 14 days, `expired`) with `daysLeft`. The public catalog shows none of it.

**Origin rule (F-1).** A URL on another origin never keeps the stored key or CA: `422 tls_key_required` (`details.field` `tls.clientKeyPem`) unless the same request sends a new client certificate and key, removes the certificate (`clientCertPem: ""`) or clears. A CA stored with no key is dropped with the origin (audited as `tlsDroppedForOrigin`; the next read then fails with class `tls` and says the CA isn't trusted until it is set again). Checked before any request to the new host and again under the row lock.

**Review.** A new, changed or removed CA is a trust change: under `approval_required` a published server goes back to review (`mcp_server.publish_request`, reason `upstream_tls_changed`; the platform admins' `publish.requested` carries the same reason). A new client certificate does not. The review digest (`omp-review-v6`) covers the CA bundle's and the certificate's fingerprints (only when set), so an approval made before either changed is refused (`409 changed_since_review`). Any change to the TLS settings forgets the stored health and reads the capabilities again at once, like a URL change.

**Failures.** Error class **`tls`**: the server's certificate isn't trusted (with a hint to add the private CA, or that the bundle must include the signing CA), isn't valid for the host name, or has expired; the server refused the portal's client certificate (or wants one); the server doesn't speak TLS 1.2 or newer, or doesn't answer with TLS at all. It shows in the health, in Test and Refresh, in the first read of a new server and in call records (`errorClass` `tls`). Handshake errors are never a reason to fall back to anything weaker, and the era cache is not involved (a failed handshake is not remembered).

**Expiry.** The client certificate's expiry shows in the server's health (`health.warnings`: `tls_certificate_expiring` within 14 days, `tls_certificate_expired` after), on the Overview tab, in the admin overview and the team's attention (`server_certificate_expiring`: info, a warning within 3 days, critical once expired), and the hourly scan emits `key.expiring` with `keyKind` `server_certificate` once per certificate 14 days ahead to the team's owners, admins and editors ([notifications.md](notifications.md)). A renewed certificate warns again when its turn comes.

**Connections.** Every exchange builds its own HTTP transport, so no connection, HTTP/2 session or TLS session is shared between two servers, or between two identities of one server; there is no connection pool to key. **Tokens.** An automation token can't send `tls` (`403 token_not_allowed`, `details.field` `tls`), and on a server that holds a client key it can't change the URL. **Limits.** The TLS settings are for the MCP server's own URL only. The sign-in discovery (protected-resource and authorization-server metadata) and the token endpoints are **not** read with the server's CA or client certificate (out of scope for #25): a server in `oauth` mode behind a private CA can't be set up yet, and the token endpoint of a `machine_oauth` server must be reachable with the system roots and no client certificate. Its calls to the server itself do use the CA and certificate, in every mode: `none`, `static_header`, `person_secret` (an editor's setup read and every person's call), `machine_oauth` (the token is sent to the server over the CA and mTLS; the token request is not) and `oauth`.

Creating a server runs discovery straight away. The server is created even if discovery fails; in that case `refreshError` and `lastRefreshError` say why. Changing the primary URL or its header deletes the stored primary health checks (additional-endpoint history stays identified separately). Changing the URL of a published server under `approval_required` sends it back to `pending` (audited as `mcp_server.publish_request` with reason `url_changed`): it leaves the catalog until a platform admin reviews the new endpoint. Under `self_publish` it stays published. A URL on another **origin** (scheme, host or port) never keeps a stored credential value (of the header, or of any part): `422 auth_value_required` unless the same request sends a new value for every part (or a new `authValue`), or removes the credential (in `oauth` mode it resets every connection and sends the server back to the setup sign-in); the audit entry has `oldOrigin` and `newOrigin`. Any URL change also clears `refreshedAt` and reads the capabilities again from the new endpoint at once (a failure is stored as `lastRefreshError`); a platform admin can't approve a server whose capabilities haven't been read from its current URL (`409 not_refreshed`). Switching a published server to `oauth`, another authorization server, or a scope not asked for before also sends it back (reason `upstream_auth_changed`); narrowing scopes, changing the client or leaving `oauth` doesn't.

## Additional replicas (v0.8.0)

**Shipped and independently verified in v0.8.0; #33 closed.** [Decision85/upstream-failover](upstream-failover.md)
adds `endpoints` to owner/admin session-only create/update and Settings. The primary remains `url`; at most
**two ordered extras** each have a stable UUID, URL, enabled flag and independently entered credential parts.
Omission retains them; `[]` clears them. Null lists/elements/optional fields are refused rather than interpreted
as clearance. No editor or automation-token authority is added, even for null/empty payloads. General platform
staff review/read but do not mutate through foreign-team routes.

Only effective `none`/`static_header`, **without any provider requirement or TLS settings**, support extras.
Upstream OAuth, each person's key, machine OAuth and personal/shared/linked provider credentials refuse them.
Remove extras before selecting incompatible auth/CA/client-certificate settings; disabled entries still retain
credentials and must be compatible. Static values never inherit from the primary. A changed endpoint origin
requires every value explicitly again, not hints/keep. A sealed versioned credential list binds endpoint UUID
(AAD), server UUID and canonical origin, checks the public shape and participates in rotation. Reordering keeps
IDs and associated envelopes stable. Corrupt encrypted state fails closed; explicit `[]` can remove it.

Changing URL/order/enabled/credential shape changes the review digest and resubmits a published server under
`approval_required` (`endpoints_changed`); reviewers see destinations and placement without values or clickable
untrusted URLs. No-extra servers retain the prior base digest. Audits contain origins/IDs/shape, not private
paths/query, secret values or hints. Authority changes are journaled under the same private owner-definer fence.

Ordinary forwarding uses primary then enabled extras, at most **three total iterations**, one original deadline
and the existing server quota/lease/breaker. Each fresh iteration checks current authority/quota; fallback
advertisements must match the stored offered kind/name/fingerprint. Identity is freshly signed for the actual
full URL using that destination's own Authorization placement. Trusted reads retain bounded transient retries;
ordinary writes switch only on positively observed unsent dial/TLS handshake failure, never generic TLS/network
labels,503, ambiguous sends, progress/continuation or local/auth/business refusals. **Governed/NoReplay remains
primary-only** even before operation send. It never restores/transfers a spent exact-call receipt.

Test and scheduled checks discover enabled extras with their own credentials and record endpoint UUID/position,
including a capability-mismatch failure. Manual identity uses the actual URL; scheduled checks use no person's
identity. Primary health/protocol/catalog remains canonical and drives scheduler recency. Endpoint deletion/
reorder does not relabel old checks; history retains original identity/position and pruning is per endpoint.
Drain all older serving/workers before relying on the policy: old-image schema47 compatibility is not endpoint
routing/review/rotation/health enforcement. See the [upgrade notes](releases/v0.8.0.md).

## Discovery and change detection

**Refresh** connects and lists every kind the server advertises. It reads every page, accepts at most 500 entries per kind, and gives up after 500 pages or on a repeated cursor. Each response is at most 1 MiB. Titles are clipped to 200 characters and descriptions to 10,000. Names and URIs can be up to 1000 characters; longer or invalid entries are skipped. A definition over 64 KiB fails discovery. A kind that the server advertises but answers with "method not found" counts as empty. Discovery never calls a tool, and the portal offers no roots, sampling or elicitation to a server it reads (calls forwarded for a client that declared elicitation are another matter: [mcp-protocol.md](mcp-protocol.md#relaying-a-servers-elicitation)).

**Protocol era.** The portal tries the newest protocol first and falls back to the older handshake only when the server isn't a 2026-07-28 server; the full rule, the cache and what it records are in [mcp-protocol.md](mcp-protocol.md#the-portal-as-a-client-of-your-servers). A refresh, a test and a health check that read the server store the era (`legacy` or `modern`) and version they negotiated on the server (`protocol` in the API: `era`, `version`, `negotiatedAt`; null until the first successful read; cleared when the URL changes). A failing check leaves what was stored.

Each capability stores its **definition**: the listed object as canonical JSON (sorted keys, numbers kept exactly) without `_meta`, which servers use for data that changes between calls. Its **fingerprint** is the SHA-256 of that JSON.

- **approved** means `approved_fingerprint = fingerprint` and the capability is still listed. A gone capability is never approved.
- **changed** means the capability was approved before, its definition is different now, and the server is published. A changed capability drops out of the catalog straight away, without anyone touching it.
- A capability the server stops listing is marked **gone**, and its approval is withdrawn. If the server lists it again later, it needs approval like a new one.
- **Approval is bound to what was reviewed.** `McpServer.reviewDigest` is a SHA-256 over the server's URL, auth mode and requirement and every listed capability's kind, name and fingerprint. (and the server's requires-a-present-person switch when it is on). Approving a server sends it back (`expectedDigest`), approving a capability sends the capability's `expectedFingerprint`; a refresh or edit between reading and clicking changes them, and the approval fails with `409 changed_since_review` (details `currentDigest` or `currentFingerprint`) without approving anything. Publishing under `self_publish` takes an optional `expectedDigest` with the same check.
- A refresh never approves anything. On a published server, **new** capabilities stay unapproved too. `pendingChanges` counts every listed capability whose current definition isn't approved: changed ones **and new ones**.

The result reports `listed`, `added` (a returning capability counts as added), `changed` and `gone`, and is audited with those counts.

## Owner-set tool classification

On a server's **Capabilities** tab, team owners and admins can classify tools individually or with **Classify
tools…**: read, write, destructive, or unclassified. **Use suggestions** explicitly accepts the current server
hints; a refresh never accepts them automatically. Editors and members read classes; platform admins review
them but cannot change them without an owner/admin role in the server's team. Automation tokens cannot classify.

Suggestions are untrusted: `readOnlyHint: true` suggests read; otherwise explicit `destructiveHint: false`
suggests write; absent or malformed hints suggest destructive. A different suggestion from a saved class shows
**Class differs from suggestion**. Check what the tool really does rather than accepting the badge as proof.

A refresh keeps the saved class, even when a definition changes. A tool that disappears loses its class and
must be classified again if it returns. Lowering a class (including unclassified → read/write) returns a published
server to review under `approval_required`; raising or clearing does not. The review digest covers the class
(`omp-review-v4`), so an approval opened before the upgrade needs one reload. Both classification endpoints
require the server's `If-Match`; bulk updates are atomic, at most 500 unique tools.

Gateway tool lists overlay read-only and destructive annotations from the owner class, without changing the
stored upstream definition. Identity tokens and call records optionally carry the class. Existing credentials
are not restricted by classification alone; scopes, approvals and retries are separate follow-up work.
See [tool-classification.md](tool-classification.md) for the API and security boundary.

## Publishing

States are `private`, `pending`, `published` and `rejected`. The **effective policy** is the team's override if one is set, otherwise the platform default (`approval_required` out of the box).

| Action | Who | Effect |
|---|---|---|
| Publish (`note` optional) | team owners and admins | `approval_required`: the server becomes `pending`. `self_publish`: it is `published` straight away and its current capabilities are approved. Errors: `409 not_refreshed`, `disabled`, `already_published`, `already_pending` |
| Review approve (`expectedDigest` required) | platform admins | `pending` only: the server becomes `published` and its current capabilities are approved, if the server's `reviewDigest` is still the one the admin read (`409 changed_since_review`; `400 expected_digest_required`) |
| Review reject | platform admins | `pending` or `published`: the server becomes `rejected`. Anything else is `409 invalid_state` |
| Unpublish | team owners and admins | `pending`, `published` or `rejected`: the server becomes `private`. A private one gets `409 not_published` |
| Approve a capability | platform admins; team owners and admins only under `self_publish` (otherwise `403 approval_required`) | Published servers only (`409 not_published`). Also `409 not_changed` and `409 capability_gone`. The body names the fingerprint the approver read (`expectedFingerprint`, required: `400 expected_fingerprint_required`); another one now is `409 changed_since_review` and approves nothing |

Publishing actions bump the server's revision. A platform admin sets the default with `PUT /v1/admin/settings/publishing` and a team override with `PUT /v1/admin/teams/{team}/publishing`. Both need `If-Match`; the team override uses the team's revision and bumps it.

**Changing the policy doesn't change any server's state.** Servers already `pending` stay pending, in the review queue, until a platform admin reviews them or the team withdraws them (unpublish); nothing is approved or dropped on their behalf. Under `self_publish` (a new default or an override) a pending server's owners and admins can simply publish it: it is published at once with its current capabilities approved, as from `private`. Moving back to `approval_required` leaves published servers published. The policy in force when an action happens is the one that applies (for example, a URL change on a published server goes back to review only under `approval_required`).

The **catalog** lists servers that are published and enabled and whose team is active, and shows only their approved, listed capabilities. Its counts cover only those capabilities. Its health has a status, a time and an error class, but no message. Any active signed-in person can read it.

## Governance

Decision 88 (#40) names who is accountable for a server and what happens as it ages or is retired. Everything below is data on `mcp_servers` (migration `00049`, expand-only; `00050` adds the sensitivity confirmation below) plus one table for transfers; the previous release ignores all of it, so **drain older serving and worker replicas before relying on ceilings, sunsets, transfers or the loop**.

| Field | Meaning |
|---|---|
| `owner` | The accountable person: an active editor, admin or owner of the server's team (`422 invalid_owner`). The person who registers a server is named by default (an automation token names nobody). A server is **ownerless** when none is named or the owner left the team, lost the editor role, was suspended or was deleted; a published ownerless server shows in attention lists (`server_ownerless`) |
| `oncallContact` | Whom to page: an email address, an `http(s)` or `tel:` link, or a channel (`#oncall`, `@team`), at most 200 characters (`422 invalid_oncall_contact`). Shown as selectable plain text (never an automatic link) to the team and platform staff, never in the catalog. It does not send pages or notifications |
| `sensitivity` | `public`, `internal` (default), `confidential`, `restricted`. A label nobody sets stays `internal`; the card says so, and `sensitivityConfirmed` (below) says whether anyone checked it |
| `sensitivityConfirmed` | Read-only and optional in the API (team and platform views, never the catalog): `true` once an owner or admin of the team has confirmed the label. Every server starts `false`, existing ones included. See [Sensitivity confirmation](#sensitivity-confirmation) |
| `lifecycle` | `active`, `deprecated` (still served; a banner everywhere; owners of gateways that select it are told), `sunset` (served by nobody). `deprecatedAt` is set when the server leaves `active`; `sunsetAt` (must lie ahead, `422 sunset_in_past`; moving to `sunset` without one sunsets now); an optional `replacement` (a published server or one of the same team, not itself sunset, never pointing back: `422 invalid_replacement`). A deprecated server whose `sunsetAt` has passed is reported as `sunset` |
| `lastReviewedAt`, `reviewDueAt` | Every approval (publish under self-publish, a platform admin's approval, a re-review) stamps `lastReviewedAt`; `reviewDueAt` is that plus the platform's interval for the server's label (none: `null`) |

**Who.** The team's owners and admins edit governance (`PATCH …/mcp-servers/{serverId}` with a `governance` object; `403 governance_role` for an editor), in a browser session. An automation token sending `governance` at all gets `403 token_not_allowed` (`details.field governance`), even on a server with no credentials and although a publisher token holds the admin role in its team; tokens also cannot ask for or answer a transfer, set a gateway's ceiling or read or change the platform's review settings. None of the new operations has `x-omp-token-scopes`, so the token counts of [automation-tokens.md](automation-tokens.md) do not move.

**Sensitivity confirmation.** `internal` is the column's default, so a stored `internal` alone cannot say whether a team chose it. `sensitivity_confirmed_at` (migration `00050`; nullable, no backfill: **no existing server is treated as confirmed**, and nothing is inferred from the label, earlier edits or publication) records that someone did. **Only** a governance edit by a team owner or admin in a browser session that **sends `sensitivity`** sets it, also when the value equals the stored one (the server page's **Confirm sensitivity** button sends exactly the label it shows, bound to the revision it shows with `If-Match`; the edit dialog has a tick-box for the same, and choosing another label confirms it). Omitting `sensitivity`, every other governance field, an empty `governance` object, ordinary edits of the server, publish, unpublish, review, health checks, refresh, registration and automation tokens never confirm; an editor, a member and a token are refused as for any governance change. Confirming is one transaction: the marker, one revision bump (`If-Match` on a stale revision is `412`) and the `mcp_server.governance_update` audit entry (`before`/`after` carry `sensitivityConfirmed`, the metadata `sensitivityConfirmed: true`); repeating it, with the current revision, writes nothing. The first confirmation date is kept by later edits. It is **bookkeeping only**: it is not an authority input (it is not in the approval journal's column list, so it does not move the approval epoch; the revision bump does, as for any governance edit), no gateway ceiling, approval, publication or review rule reads it, and confirming sends nothing to review. A published server nobody confirmed shows in the team's and the platform's attention lists as `server_unlabelled` (informational; at most 20 listed per kind, exact total; private, pending and archived-team servers and confirmed ones, `internal` included, are absent). Nothing is unpublished or blocked for it. A binary older than `00050` that changes a label leaves the server unconfirmed, which is the conservative reading.

**What it decides.** Two of the fields decide whether a capability is served and are part of `gateways.Availability`:

- A gateway's `maxSensitivity` (default `restricted`: no ceiling; the setting is on the gateway's Settings tab, changed by the team's owners and admins or platform admins for a platform gateway, never by a token). A server above it is `sensitivity_exceeds_gateway` and never served, also a team gateway's own private server. Raising the ceiling or lowering the label restores it. The ceiling applies to gateways only for now; credential ceilings (unverified OAuth clients) come later with #29's follow-up.
- A server whose lifecycle is `sunset`, or whose `sunsetAt` has passed, is `sunset` in every gateway at that moment. There is no sweeper: the rule reads the clock. `GatewayStats` (the gateway list's unavailable count) and `ApprovalRequesterLive` (the final check of a spent approval) are SQL mirrors; `TestGatewayStatsMirrorsAvailability` compares all three over every label, ceiling and lifecycle. Both inputs are in the approval authority journal (migration 49 re-registers `mcp_servers` and `gateways`), so an approval cannot outlive a change of them; the other fields are not authority.

**Review.** Raising the sensitivity of a **published** server sends it back to review under `approval_required` (`mcp_server.publish_request`, reason `sensitivity_raised`); under `self_publish` the team approves its own change; lowering never does. The review digest is **`omp-review-v6`**: it adds the label and the lifecycle (not the owner, contact, dates or replacement), so an approval read before either changed is `409 changed_since_review`, and a review request open at the upgrade needs one reload. **Re-review.** The platform sets days between reviews per label (`GET`/`PUT /v1/admin/settings/governance`, own revision; defaults 0 public and internal, 180 confidential, 90 restricted; 0 never) and whether an overdue review also returns the server to review (**off by default**). An overdue review tells the team (`server.review_due`, once per due date) and shows in attention lists (`review_due`); the server **stays published**. With the setting on, under `approval_required` the governance loop sends it back to review (reason `review_due`, a system audit entry); nothing is ever unpublished, disabled or deleted automatically. The team asks again with Publish (a pending request under `approval_required`, an in-place confirmation `mcp_server.review_confirm` under `self_publish`; never an automation token); a platform admin can approve an overdue published server in place with the usual digest.

**Transfer between teams.** `POST …/mcp-servers/{serverId}/transfer` (owners and admins of the server's team) offers it; the receiving team's **owner** accepts (`POST /v1/teams/{team}/mcp-server-transfers/{transferId}/accept`, `If-Match` on the transfer's revision; `403 owner_required` for an admin); either side can withdraw or decline (`DELETE …/{transferId}`); platform admins force a move (`POST /v1/admin/mcp-servers/{serverId}/transfer`, ownerless afterwards, any open offer cancelled). One open transfer per server (`409 transfer_pending`), answers are compare-and-set (`409 transfer_closed`), and the server must be as it was when offered (`409 changed_since_request`: withdraw and ask again). The move keeps everything keyed by the server: capabilities, gateway selections and grants, people's provider grants and person secrets, the sealed credential (its AAD is the server's ID). It **moves the server's approval rules to the receiving team** (otherwise the old team could loosen them), names the accepting owner as owner, and under the receiving team's `approval_required` sends a published server back to review (reason `transferred`); gateways of the old team keep their selection, which is then a catalog selection and unavailable (`not_published`) until it is approved again. It is refused (`422 provider_not_allowed`) when the server requires a restricted auth provider that lists neither the receiving team nor the server, because decision 69 would stop its calls. Audited as `mcp_server.transfer_request`, `.transfer`, `.transfer_cancel`; owners of the receiving team see pending offers in their attention list (`server_transfer_pending`) and on the Servers page.

**The loop.** `Service.GovernanceLoop` takes the advisory lock `omp.governance` every 5 minutes (leader gauge `omp_loop_leader{loop="governance"}`), handles at most 50 servers or gateway pairs per kind per run, each in its own transaction, and records each notice in `server_governance_notices` in the transaction of its event: a retry, a second replica or a purged event (events are kept 14 days; a deprecation lasts longer) never tells anyone twice. See [notifications.md](notifications.md).

## Health

For a server in `oauth` mode, Test and Refresh use the setup connection (`readAs`; Refresh answers `409 setup_reconsent_required` when it lapsed, or its person is no longer an editor), and scheduled checks send an unauthenticated `initialize`: the expected `401` Bearer challenge for the server's resource metadata is healthy with `signInRequired` ("requires sign-in"). Test, refresh and the background loop each store a check: ok or failed, latency, trigger (`manual` or `scheduled`), error class, HTTP status, and a short message with the header value and anything secret-looking redacted. The server keeps its latest 100 checks per primary/additional endpoint, with historical endpoint UUID/position on extra checks; the canonical status and protocol use primary checks only. `statusSince` carries over while the outcome stays the same, so a "failing since" time survives pruning. Error classes: `unavailable`, `auth`, `not_found`, `rate_limited`, `bad_request`, `bad_response`, `config` (the header can't be decrypted), `timeout`, `too_large`, `not_allowed` (a blocked or unallowed address, or a redirect), `tls` (the TLS handshake failed: an untrusted or wrong-name certificate, or a refused client certificate; see [TLS to the server](#tls-to-the-server)). A client certificate that is about to expire shows as a warning with the health (`health.warnings`).

**What Test sends (decision 61).** Test behaves like a call as far as the server can see: when the server's **Send identity** is on, it sends the identity token of the editor who pressed the button ([upstream-identity.md](upstream-identity.md#what-a-test-sends)). If the server answers `401` or `403` to that, the portal reads the server once more without the token; when only that second read works, the Test fails with class `auth`, the server's HTTP status and the message "The server accepts the portal's requests without its identity token but refused them with it. Turn off Send identity token for this server, or have the server accept the token." (stored as the manual check like any failed Test). If both fail, the ordinary failure is shown, and if the first read passes, so does the Test. The token is never returned, logged or audited. Refresh and the scheduled loop send no token: Refresh stores what a server lists, which shouldn't depend on who asked, and the loop has no caller. An automation token that runs a Test has no person, so it sends none. Honest limit: Test lists capabilities and calls no tool, so a server that refuses the token only at tool execution still passes it.

The loop runs at start-up and then every `HEALTH_CHECK_INTERVAL` (default `5m`, `0` turns it off, minimum `30s`). It tests enabled servers of active teams four at a time. Only one replica runs a pass at a time (PostgreSQL advisory lock `omp.mcp-health-checks`), and any server checked within the last 90% of the interval is skipped, so replicas taking turns don't check it twice.

## Security

- **Addresses** (code: `internal/netpolicy`, `internal/upstream/guard.go`). Every address is in one of three classes:
  - **Always blocked**, whatever the allowlist says: loopback (`127.0.0.0/8`, `::1`), link-local (`169.254.0.0/16` including the cloud metadata address `169.254.169.254`, `fe80::/10`), unspecified (`0.0.0.0`, `::`), `0.0.0.0/8`, multicast (`224.0.0.0/4`, `ff00::/8`), broadcast (`255.255.255.255`), other metadata endpoints (`168.63.129.16`, `100.100.100.200`, `fd00:ec2::254`), and the IPv4-mapped (`::ffff:a.b.c.d`), IPv4-compatible (`::a.b.c.d`) and NAT64 (`64:ff9b::/96`) forms of those. Zoned IPv6 addresses too. `localhost` and `*.localhost` are refused by name.
  - **Public**: allocated public unicast. Allowed, over https only (as before).
  - **Private**: everything else (RFC 1918, CGNAT, ULA, documentation, benchmarking and reserved ranges). Allowed only when (a) the URL's host is a literal address inside a `cidr` entry, (b) the URL's host matches a `host` entry, or (c) the host name resolves to it and it is inside a `cidr` entry. Otherwise `422 url_not_allowed` with reason `private_address` when saving a literal address, or error class `not_allowed` when dialling.
- **Allowlist entries.** `cidr`: an IPv4 or IPv6 prefix, canonicalised (`10.20.3.4/16` is stored as `10.20.0.0/16`, a bare address as `/32` or `/128`, an IPv4-mapped prefix as its IPv4 form); a prefix entirely inside an always-blocked range is refused (`always_blocked`). `host`: an exact host name (`mcp.corp.example.com`) or `*.suffix`, which matches subdomains only (`*.corp.example.com` matches `a.corp.example.com` and `a.b.corp.example.com`, not `corp.example.com` or `evilcorp.example.com`). Host names are lower-cased, lose a trailing dot, and must be ASCII letter-digit-hyphen labels (use punycode, `xn--…`, for international names); no scheme, port, path, address or `localhost`. URL hosts are compared the same way (case and a trailing dot don't matter; the port is not part of the host). Each entry has `allowHttp` and an optional `note` (at most 200 characters). Problems are `422 invalid_entry` with `details.index` and `details.reason` (`invalid_kind`, `invalid_cidr`, `invalid_host`, `non_ascii`, `ip_as_host`, `always_blocked`, `invalid_note`, `duplicate`, `too_many`).
- **Where entries come from.** Platform admins manage up to 100 in **Admin › Internal networks** (`GET`/`PUT /v1/admin/settings/network`, `If-Match` on its own revision, audited as `settings.network_update` with the lists before and after). The deployment adds entries with `UPSTREAM_ALLOWED_NETWORKS` (comma-separated; kind inferred; an `http:` prefix sets `allowHttp`, for example `10.20.0.0/16,http:*.svc.cluster.local,mcp.corp.example.com`); an invalid one fails configuration loading, and the UI shows them read-only. Both lists apply together.
- **Plain http** is allowed only when the URL's host matches a `host` entry with `allowHttp`, or is a literal address inside a `cidr` entry with `allowHttp`. A name that merely resolves into an http-allowed network still needs https. Everything else must be https (reason `scheme`).
- **When it's checked.** **When the server is saved**: the URL's shape, the scheme, literal addresses and `localhost`. **Before every exchange** (refresh, test, health check, forwarded call): the stored URL against the current policy. **Every time the portal dials**: every address the host resolves to must be allowed (one blocked or unallowed address refuses the connection, so DNS rebinding to `169.254.169.254` is refused even for a host entry), and the connection is pinned to the checked addresses. Redirects are never followed. Proxy environment variables are ignored. URLs can't contain user info, a query or a fragment: credentials belong in the header.
- **Changes are live.** Dials read a cached copy of the admin entries that is refreshed at most every **30 seconds**; the replica that saves a change applies it at once, other replicas within 30 seconds. If the database can't be read, the last copy stays in force. Changing the entries never edits servers: a server outside the new policy fails its next exchange with error class `not_allowed`, and its health shows failing.
- **Checking a URL.** `POST /v1/admin/settings/network/check` with `{url}` (platform admins and auditors) applies the same rules with this replica's copy: it resolves the host (at most 3 seconds) but never connects, and returns `allowed`, a `reason` (`public`, `cidr_entry`, `host_entry`, `development`; or `blocked_address`, `private_address`, `dns_failed`, or a URL problem such as `scheme`), a `message`, the `matchedEntry` and each resolved address with its own verdict.
- **Development:** when `DEV_AUTH=true` with a loopback `APP_URL`, plain `http://` to loopback hosts and private, loopback and link-local addresses are allowed, as before (allowlist entries also apply). This allowance never exists in production.
- **TLS to the server.** A server's own CA bundle replaces the system roots for that server only, a client certificate can be presented, and verification is always on: see [TLS to the server](#tls-to-the-server). The address rule above is not part of it and is not relaxed by it.
- **Secrets:** `ENCRYPTION_KEY` is required by `serve`. Outside loopback, the server refuses to start with the example key from `.env.example`. `ENCRYPTION_KEY_PREVIOUS` still decrypts values sealed with the old key; re-entering a value re-seals it with the current key. The audit log records only `authValueChanged`.
- **Untrusted text:** descriptions and schemas are prompts a model will read. Review them before you approve, and treat annotations as hints only.
