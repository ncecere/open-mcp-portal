# Open MCP Portal v0.5.0

Sensitive-call approvals for exact MCP tool calls (#31, decision 82). Ordinary MCP clients and service accounts remain supported; external-platform
impersonation stays retired.

## What changed

- **Explicit approval policies.** Team owners/admins manage rules for their servers and gateways;
  platform admins manage platform-gateway rules. Server rules outrank gateway rules, and a specific
  capability outranks a class within that tier. Equal-priority ambiguity fails closed. Unclassified
  tools match destructive rules for approval only: their class and credential scopes do not change.
- **Separated human review.** Named active users/exact SSO groups or the server team's owners/admins
  review calls. A non-requester platform-admin fallback applies only when the primary set is empty.
  Human self-approval is never allowed. A requesting service account's owners/admins are excluded
  unless its rule explicitly permits them. Gateway ownership alone grants no review authority.
- **Exact-call, single-attempt authorization.** Requests bind merged fixed arguments, tool definition,
  exposed name, requester, destination, rule revision and live authority context. Identical pending or
  approved requests deduplicate without extending deadlines. Denial requires explicit browser renewal.
  Approval is spent immediately before one actual tool transport, not during negotiation. A committed
  spend is never restored or automatically replayed; a lost response may mean duplicate effects if the
  caller starts another attempt. Governed calls cannot continue upstream elicitation exchanges.
- **Private receipts and notices.** Session-only browser APIs and an approval queue expose redacted,
  sealed previews only to authorized requesters/reviewers. Platform metadata oversight does not imply
  preview access. Private notifications and eligible attention items link to receipts without arguments,
  previews or digests; approval notices cannot be sent to webhooks. Automation tokens cannot review
  calls. New call outcome: `needs_approval`.
- **Client compatibility.** URL-capable modern clients receive `input_required`; other modern tool
  callers receive an error result with a browser link; legacy clients receive `-32042`. Service accounts
  can request approval for humans to review without impersonating a person.
- **Retention and rotation.** Pending lifetime defaults to 24 hours, approved validity to 15 minutes,
  capped by the pending expiry. There are at most 20 pending requests per requester. Terminal previews
  are inaccessible immediately and cleared within 24 hours; receipt metadata is retained for 90 days,
  independently of audit retention. A stable sealed binding key preserves deduplication, denial memory,
  renewal and single consumption through encryption-key rotation.

## Upgrading

1. Back up, then apply migrations **`00035` through `00042`** using the normal owner migration step.
   Never rewrite applied migrations or downgrade the schema to roll back an image.
2. Complete the application rollout and drain every older serving image **before enabling approval
   rules**. v0.4.0 is schema-compatible but does not enforce approvals. An image rollback while rules
   remain active is not a safe enforcement rollback; keep governed execution blocked until supported
   serving images are restored.
3. Preserve the owner/runtime separation. Protected context, journal and binding-key storage live in
   the owner-controlled `omp_private` schema. Serving roles get usage, not schema creation, and cannot
   reset protected state. The migration step reconciles grants; do not supply serving replicas with the
   owner URL to work around a startup check.
4. Use the **new binary's** key-rotation utility after migrating; older utilities do not know the new
   ciphertext columns. Back up the database and encryption keys together. Rotation rewraps the stable
   approval binding root rather than replacing it.
5. Review approver eligibility and separation of duties before enabling a rule. Rules add a human gate;
   they never grant missing gateway, tool-scope or provider access. See [tool approvals](../tool-approvals.md).

## Verification

Local generation, lint/build, generated-code freshness, deployment validation, all 836 web tests and the
full required-PostgreSQL normal/race suites passed in both legacy and genuinely authenticated split-role
modes. Follow-up release-version, exact-Unicode, rotation, authorization and concurrent-refresh regressions
also passed. Independent correctness/security reviews and actual unmodified-v0.4.0 strict-role startup,
HTTP readiness and a journaled authority write against schema 42 were exercised. The normal CI-pinned
advisory checks passed: zero reachable Go vulnerabilities and zero npm advisories. GitHub Actions records
main CI, both smoke CNIs, image scans/signing and publication; see [status](../status.md) for outcomes.

An owned disposable split-role browser fixture exercised rule creation, modern URL approval, redacted
review, actual MCP dispatch and spent receipts, metadata-only auditor access, and preserving a request
across the private-schema relocation. At 390px the checked queue, receipt, rules and editor pages have
no horizontal overflow and axe reports zero violations/incomplete checks. The scrollable preview is
keyboard-accessible. These checks are not real-provider, IDE or whole-product accessibility acceptance.

## Known limitations

Classification and human approval do not prove what an upstream tool will do. `used` means authorization
was spent, not that the upstream effect succeeded. A coarse authority epoch conservatively invalidates
unrelated pending approvals after authority changes. Short governed transitions fail closed if their
writer fence is busy; load/latency behavior still needs measurement. Normal calls with no matching rule
and non-spending transport checks use read-only snapshots and do not acquire that writer fence.

Real client/provider reports, long wall-clock refresh/expiry evidence, broader deployment/load validation
and a team pilot remain separate work. See [implementation order](../implementation-order.md). Report
vulnerabilities privately using [SECURITY.md](../../SECURITY.md).
