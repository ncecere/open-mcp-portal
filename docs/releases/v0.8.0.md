# Open MCP Portal v0.8.0

This is the separate endpoint-failover stage of #33 (decision85), following verified
[v0.7.0](v0.7.0.md). Local validation and previous-image compatibility passed; publication and independently
verified artifact/runtime evidence are recorded in [status](../status.md) when available. A local version or
these notes alone do not establish publication. v1.0.0 remains the owner's decision.

## What changes

- **Explicit additional replicas.** The primary URL remains canonical. Server-team owners/admins may configure
  at most two ordered additional endpoints, with independent URL/enabled/credential settings. Omitted
  configuration retains it; an empty list clears it. Session-only, audited, revision-checked mutations gain
  no editor/publisher-token capability. Catalog review/digests cover actual destinations, order, enabled
  state and credential placement. Disabled extras retain secrets and must still be mode-compatible.
- **Independent origin-bound credentials.** Initially support effective no-auth or static multipart header/
  bearer/Basic/query credentials, without any provider requirement or TLS override/client identity. Upstream
  OAuth, each person's key, personal/shared/linked provider credentials, machine OAuth, mTLS and private CAs
  refuse additional endpoints. Mode is not the only check: provider/TLS state is independent. Remove extras
  before selecting an incompatible configuration. Static extras require their own explicitly entered values,
  never implicit primary inheritance. A changed origin requires every value again; keep/hints cannot authorize
  it. The sealed versioned envelope binds endpoint UUID, server UUID and canonical origin, validates public
  shape against decrypted parts and participates in key rotation. No plaintext is returned or audited.
- **One bounded operation.** Ordinary failover shares the existing original timeout, caller deadline, server
  quota and replica-local lease/breaker. At most three forwarding iterations total, primary first and enabled
  extras in order; endpoints do not multiply the retry budget. Each iteration freshly checks authority and
  quota before network. A write/destructive/unclassified operation switches only after positively identified
  pre-request dial/TLS-handshake failure and no operation write, not on a generic TLS/network label or 503.
  Trusted reads retain v0.7.0's transient-response policy. No continuation/progress/streamed/partial,
  auth/business/local-refusal/cancelled or ambiguous-send replay. A read-class503 is not proof of no effect.
- **Primary-only sensitive calls.** Governed/NoReplay calls do not fail over, including negotiation failure.
  Their approval binds the primary origin and may spend before dial. No receipt or committed authorization
  is restored, reused or silently transferred to a second origin. This deliberately favors exact approval
  semantics over availability; reviewing an endpoint list does not widen an exact-call receipt.
- **Trusted definitions and actual identity.** A fallback must advertise the offered stored kind/name/
  fingerprint before its operation is sent. Discovery never silently replaces canonical catalog definitions
  or owner classification. Its independently built target cannot inherit primary provider/bearer/TLS/query
  credentials or a primary JWT. Outbound identity uses the actual full URL and that endpoint's Authorization
  placement. Era/session caches remain URL-aware, and every exchange repeats live address/dial guards.
- **Visible review and health.** Settings explain mode refusals, independent entry, the shared budget and
  primary-only approvals; reviewers see destinations/credential shape, never values or executable URL links.
  Health checks identify the primary or additional endpoint and detect capability mismatch. Primary status/
  protocol remains canonical. Deleted endpoints retain historical check identity/position; pruning remains
  bounded per endpoint. One logical call/capture remains, with prior-dispatch/cancellation metadata preserved.

## Upgrade and rollback

1. Back up the database and its matching keys consistently; do not reset/reseed an existing instance or
   regenerate keys for its encrypted data. No old configuration or fixture is restored implicitly.
2. Apply new expand-only migration **47** using the migration owner. It adds endpoint/encrypted-envelope
   storage, endpoint health identity and owner-definer journal/fence participation. Runtime reconciliation
   retains least privileges; no owner URL belongs in serving containers. Existing primary rows and permanent
   data remain. Historical migrations42/46 and earlier are not edited.
3. **Drain every older serving/background-worker replica before enabling or relying on extra endpoints.**
   An old image may preserve expanded-schema data, but does not understand routing/endpoint review/new
   ciphertext rotation or endpoint-aware health. Expanded-schema compatibility is not enforcement.
4. Configure only genuine replicas with matching trusted capabilities and explicitly entered independent
   credentials. Review the actual origins before approving catalog exposure. No extras are added by default.
5. Do not downgrade the schema for an image rollback. An older image uses the primary only and does not enforce
   the new endpoint policy or rotate its new cipher column. Pause affected execution or remove/disable extras
   deliberately, preserving history/matching keys; follow all earlier expiry/approval rollout requirements.

No new application dependency, environment variable, cross-replica concurrency lease, request queue or load
balancing is introduced. Existing v0.7.0 quota/cap/breaker defaults and v0.6.0 access expiry semantics remain.
