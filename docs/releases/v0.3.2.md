# Open MCP Portal v0.3.2

Credentials wave 2 of the v0.3 line, after [v0.3.1](v0.3.1.md): three new ways for the portal to authenticate to an MCP server, and TLS client certificates with a private CA. It adds three migrations (`00024` to `00026`, all expand-only). **Nothing changes for existing servers**; each feature is something a team opts into on a server.

## What changed

- **Each person's own key for a server** (#22, decision 72). A new auth mode, `person_secret`: every person pastes their own API key or token for a server once (Account › My connections › Keys for servers), sealed per person and server, shown only as a hint, revocable, and sent as a header, a bearer token or a query-string key. Setting it up needs an editor's own key first (so the server's tools can be read). A URL change to another origin, or a change of where the key goes, deletes everyone's keys. A relayed agent call uses a person's key only if that person turned on **Allow agents** for the server (off by default), and never gets a link: it gets a tool error saying where to enter the key. Scheduled health checks send no key, and a `401` or `403` counts as healthy. Admin › Users shows which servers a person has keys for (never the keys).
- **OAuth client credentials for servers that authenticate the portal itself** (#24, decision 73). A server can use `machine_oauth`: the portal is the OAuth client, fetches a token with the client-credentials grant from the server's authorization server and sends it as the bearer, caching it in memory with expiry skew and one fetch at a time. The client secret is sealed and never shown, and is discarded when the server's origin, endpoint or client changes. Editors may set it up; an automation token may not, even on a server with no credentials.
- **mTLS client certificates and a per-server CA** (#25, decision 74). A server can present a client certificate to its upstream and trust a private CA **instead of** the system roots, for that server only. The key is sealed and never shown; hostname verification is always on (there is no skip-verify option); TLS 1.2 is the minimum; each exchange uses its own connection, so nothing is shared across servers or identities. Certificate expiry shows on the server's Health page, in the admin overview and as a `key.expiring` notification. Changing the CA or the client certificate sends a published server back to review.
- **The three together.** A server is in one of five modes (`none`, `static_header`, `person_secret`, `machine_oauth`, `oauth`) and may sit behind a private CA with a client certificate, in any combination. The add-server form offers all five. Switching modes deletes the old mode's secrets, and another origin discards every kind of secret unless replaced.
- **A migration hazard was found and fixed before release:** two of these migrations both rewrite the database's list of allowed auth modes, and applied naively the later one would have dropped the earlier one's value. Each now adds its value to whatever the list currently holds, and a test applies them in both orders.

## Upgrading

1. Pin the new image (verify its signature first, see [Verifying the images](v0.1.0.md#verifying-the-images)). The init container applies `00024`, `00025` and `00026`; all only add tables or widen checks, so the previous image keeps working against the new schema while no server uses a new mode. **Do not use `goose down` for a rollback** once a server uses a new mode; pin the previous image. (The down migrations move such a server to `static_header` if it has a static credential, else to `none`.)
2. A review request that is open during the upgrade gets one `409 changed_since_review`, because the review digest now covers the CA and client-certificate fingerprints, the person-secret placement and the machine client.
3. `mcp_health_checks.error_class` stops being an enumerated list (a length bound replaces it), so new error classes need no migration; the new class `tls` is used for certificate problems.

## Verification

- Go tests with the race detector against PostgreSQL, run on each branch and again on the merged tree; the web tests; the route, authorization and token matrices; migration tests including `TestAuthModeConstraintAcceptsEveryMode`; `govulncheck` and `npm audit`; the Prometheus rule tests; the Kubernetes smoke test in CI.
- Combined tests behind a private CA with mutual TLS exercise every mode (create, Test, refresh, health, edit, call), mode switches, origin changes, relayed agent calls, key rotation of every new column, and one scan of every secret kind through responses, logs, audit, call records, recorded payloads and spans.
- A browser check of the add-server form (all five modes offered; the machine-OAuth fields and their warning that everyone who calls the server shares the portal's token), with the app started on the existing development database so migrations `00024` to `00026` ran on a database that already had data and the allowed auth modes list came out with all five values.
- Not done: **a browser look at the person-secret pages, the TLS card and the Health expiry warnings** (covered by web and integration tests), a real authorization server (Entra ID, Okta, Keycloak, Auth0) for machine OAuth, a real MCP server that wants a per-person key or a client certificate, and a rotation of `ENCRYPTION_KEY` over real servers.

## Known limitations

Carried over from v0.3.1 unless marked new:

- **Client certificates are not used for the OAuth metadata and token endpoints (new):** a server in `oauth` mode behind a private CA can't be set up yet. CRL and OCSP are not checked.
- **A team's static credential echoed back by its own server reaches the caller in the tool result (new, documented as UM-5):** it is redacted from logs, error messages and recorded payloads.
- **A person's key is as safe as the server that receives it (new):** it is sent in the clear to that server (over TLS); a query-string key is also visible in URLs.
- **Not run against a live Pi Durable Platform;** VS Code and Cursor not run; no real Google or Microsoft provider, Slack webhook, mail server, collector or authorization server run.
- Remote servers only (no stdio); development software that has not run in production.
