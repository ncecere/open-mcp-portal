# Open MCP Portal v0.3.1

The first credential and operations work of the v0.3 line, after [v0.3.0](v0.3.0.md): who may use an auth provider and how much of a person's token a server gets, a server's own credential as several parts, and OpenTelemetry tracing with dashboards and alert rules. It adds three migrations (`00021`, `00022`, `00023`, all expand-only). **Nothing changes for existing providers or servers until an admin opts in**, except that credentials you save from now on may be stored in the new form.

## What changed

- **A per-provider access list** (#27, decision 69; closes the open residual of finding F-3). An auth provider created from now on starts **restricted**: only servers of the teams you list, or servers you name, may require it and receive people's tokens. Existing providers stay **open** and show a warning on Admin › Auth providers › Access. The list is checked when a requirement is saved, when a person allows a server (the consent link, the callback and My connections) and on every call, including calls an agent relays.
- **Narrower tokens per call** (#27). A provider that supports it can be set to refresh with only the scopes a call needs; the narrowed token is kept in memory only. Only Microsoft is pre-filled, from its documentation; GitHub, Google, Atlassian, Slack and GitLab document no `scope` on refresh and stay off. It fails closed if the provider refuses the scope. An optional background refresh (`PROVIDER_REFRESH_INTERVAL`, off by default) finds a revoked grant before a call does. My connections shows which token a server gets.
- **A server's own credential as several parts** (#23, decision 70). Headers, a bearer token, Basic auth or a query-string key, each sealed on its own, sent with every request. The rule that another origin never keeps a stored value (F-1) covers every part; a query-string key is warned about in the form. Existing single-header servers keep working with no data change; saving a credential as a list moves it into a new table. If a part sets `Authorization`, the identity token moves to `MCP-Gateway-Identity`.
- **OpenTelemetry tracing, dashboards and alert rules** (#34, decision 71). Off unless an OTLP endpoint is set. One span per `/mcp` request with child spans for authentication, authorization, the provider credential and the call to the server, plus management requests and registry probes; span attributes come from a fixed allow-list (never tokens, content, emails or argument values). Call records carry a trace id (`trace_id`, with an optional link template) and the call page shows it. Five Grafana dashboards, 14 Prometheus alert rules with unit tests and runbook entries (`make prom-check`, also in CI), a `PrometheusRule` and an OTLP egress policy in the example overlay.
- Smaller: the "Static header" choice on the add-server form is now "Static credential".

## Upgrading

1. Pin the new image (verify its signature first, see [Verifying the images](v0.1.0.md#verifying-the-images)). The init container applies `00021`, `00022` and `00023`; all only add tables or nullable columns, so the previous image keeps working against the new schema. Do not use `goose down` for a rollback; pin the previous image.
2. **Existing auth providers stay open to every team.** Decide which to restrict (Admin › Auth providers › Access). New ones start restricted, so a team that expects to use a provider you create needs to be listed.
3. A published server's review request that is open during the upgrade gets one `409 changed_since_review`, because the review digest now covers credential part kinds and names (the digest version changed).
4. Tracing is off. To turn it on, see the Tracing section of the deployment guide. If untrusted clients can reach the portal, use `traceidratio` sampling: the default parent-based sampler lets a client ask for a trace by sending a sampled `traceparent`.
5. The binary is about 3.6 MB larger (the OpenTelemetry exporter pulls in protobuf and gRPC packages).

## Verification

- Go tests with the race detector against PostgreSQL (the three branches were also merged and run together), the web tests, the route, authorization and token matrices, migration tests, `govulncheck` and `npm audit`, the Prometheus rule unit tests, the Kubernetes smoke test in CI.
- New tests cover each change, including that the access list gates agent relays, that narrowing fails closed, that every credential part is redacted from errors, logs, audit and recorded payloads (also URL-encoded and as the Basic base64 form), and that span attributes cannot carry a sentinel secret.
- A browser check of the credential-parts editor on the add-server form and the provider Access tab (the Access tab's "open to every team" warning and options), on the development stack with the three migrations applied to a database that already had data.
- Not done: a run against a real provider (including Microsoft's refresh with `scope`), a real third-party server that wants Basic or a query key, a real OpenTelemetry collector or Tempo (a fake receiver stood in), and a check of the dashboards' queries against live data (Grafana loaded all five from files).

## Known limitations

Carried over from v0.3.0 unless marked new:

- **Not run against a live Pi Durable Platform;** VS Code and Cursor not run; no real Google or Microsoft delegated-credentials provider, Slack webhook or mail server run.
- **A query-string credential travels in the URL** (new): servers, proxies and their logs may record it; prefer a header. The portal redacts it everywhere it handles it.
- **Narrowing is only as good as the provider's support** (new): where a provider ignores `scope` on refresh, the token keeps every scope the person granted.
- **Exemplars are not built** (new); traces and metrics link only through the trace id on the call record.
- Remote servers only (no stdio); development software that has not run in production.
