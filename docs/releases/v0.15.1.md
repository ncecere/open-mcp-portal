This minor release completes audit streaming slice 2 (#38, decision 94; design
[audit-sinks.md](../audit-sinks.md)):

- **Signed checkpoints** let a receiver anchor audit history without trusting the database.
- **Webhook sinks** push the sealed audit stream to a SIEM.

Both are **off until an operator enables them** after every replica runs 0.15.0. It has **two migrations**
(`00063`, `00064`). Read [Rollout](#rollout) before enabling anything.

## Signed audit checkpoints (#38 slice 2a)

- **Key.** A dedicated, install-local Ed25519 key, never the identity key that signs upstream JWTs.
  - It is sealed with `ENCRYPTION_KEY` and covered by `rotate-keys`.
  - Its public half is published at `/.well-known/omp-audit-keys.json`, with the range of sequence numbers the key
    may sign.
  - The new migration-owned schema `omp_audit_ext` holds it, behind a manifest-driven role boundary.
- **When the sealer leader signs.** Every 10,000 entries, or every 15 minutes when there was activity; an idle stream
  writes none.
- **The checkpoint record.** Each one is a chained record whose signed statement binds the stream, epoch, sequence,
  covered chain hash, time and key ids. The database checks the coverage, fences and hashes. Receivers and
  `GET /v1/admin/audit/verify` check the signatures and key authority.
- **Rotation.** `open-mcp-portal audit-stream rotate-checkpoint-key` is one atomic handover signed by both keys. It
  closes the old key's authority at the handover.
- **Receiver rules.** These are normative in [audit-record-v2.md](../audit-record-v2.md): pin the stream id and the
  current key, enroll forward-only, walk back through handovers, and preserve forks. The Python reference verifier
  implements them.

## Audit webhook sinks (#38 slice 2b)

- **Delivery.**
  - The portal POSTs sealed records as NDJSON, in sequence order and at least once, HMAC-signed like notification
    webhooks (two signatures while a rotated secret is valid).
  - Every attempt is fenced to the sink's revision, cursor and range, so a stale leader or a mid-flight
    configuration change can never move a cursor past records the receiver didn't acknowledge.
  - No transaction or lock is held during HTTP.
  - Receivers apply records by `seq`, discard only identical duplicates, and keep conflicting hashes as fork evidence.
- **Destinations.**
  - `https` only, plus `http` for allowlisted hosts with `AllowHTTP`. URLs are at most 2,048 characters.
  - The host is resolved when saved and checked again at every dial.
  - No redirects or proxies, and TLS is always verified.
  - Destinations are restricted by the new, empty-by-default `AUDIT_STREAM_ALLOWED_NETWORKS`, which is separate
    from the notification allowlist.
- **Retention.**
  - **Required** sinks hold audit retention at their cursor, even while disabled.
  - **Optional** sinks don't. They stop with `range_expired` if they fall behind, until an admin resumes them. Resume
    sends a signed, advisory `audit.gap` request with the exact missing range.
  - A required full-profile sink stops at a row too large for the 16 MiB line until an admin acknowledges it, after
    retrieving it.
- **Admin › Audit stream.** Platform admins manage sinks from a browser session; auditors see them read-only.
  - **Sink actions:** create (the signing secret is shown once), edit, test, rotate secret, resume, acknowledge
    oversized rows, delete.
  - **Status:** stream and checkpoint status (including whether the sealer is on for the replica that answered), each
    sink's lag, last success and retention effect, and pull consumers.

  Platform admins get `audit.sink_failing` notices at the third consecutive failure and `audit.sink_recovered` on
  recovery.

## Rollout

- **Migrations `00063` and `00064`** are expand-only. `omp_audit` keeps exactly the shape v0.14.0 expects. The new
  objects live in `omp_audit_ext`, whose grants v0.14.0's reconciler leaves alone. The purge function is restated
  with the same signature and settings, so a v0.14.0 retention loop obeys required sinks too.
- **Upgrading needs nothing extra.** Checkpoints and sinks stay off; everything else behaves as in v0.14.0. v0.14.0
  replicas keep working against the new schema during a rolling upgrade. That was tested with the actual v0.14.0
  executable at schemas 63 and 64, in both reconcile orders and in required split-role mode.
- **Enabling checkpoints** (`audit-stream enable-checkpoints --min-reader-version-ack`, migration role) is a
  **one-way minimum-reader-version step**: v0.14.0 cannot read checkpoint records and answers a partial `200` on
  them. Enable only after every replica runs 0.15.0. After that, never roll back below 0.15.0. The command refuses to
  run from any build that isn't a clean release newer than 0.14.0.
- **Enabling sinks** (`audit-stream enable-sinks --min-reader-version-ack`) has the same guard. Older releases'
  notification dispatchers silently mark unknown events as delivered, which was tested with the real v0.14.0 and 2a
  executables. To roll back below 0.15.0 after enabling: run `audit-stream disable-sinks`, stop senders, and let
  0.15.0 drain pending sink notifications first.
- **Encryption-key rotation.** Older `rotate-keys` utilities do not know the checkpoint-key or sink ciphertext. Don't
  retire a previous `ENCRYPTION_KEY` using a v0.14.0 utility once either exists.
- See [deploy.md](../deploy.md) and [audit-sinks-operations.md](../audit-sinks-operations.md) for the runbook and
  receiver verification.

## Evidence

### Implementation proof

- **Design reviews.** The design went through three independent adversarial reviews, recorded in sections 4.6 and 9
  of the design.
- **Compatibility.** The actual v0.14.0 executable was tested at schemas 63 and 64:
  - reconcile in both orders, and startup in required split-role mode;
  - its sealer, pull and retention, with retention obeying the sink cap;
  - its key-rotation utility leaves extension ciphertext untouched;
  - its notification dispatcher drops sink events, which is the hazard the gate exists for. A 2a build does the same.
- **Checkpoints.** Tests cover:
  - the manifest boundary, including excess and inherited privileges;
  - the first-key race;
  - every checkpoint rejection;
  - rotation under concurrent sealing;
  - cadence, including idle, stale-state, epoch and rebase cases;
  - `verify` catching bad signatures, transplanted statements and out-of-range keys.

  Real stream output is accepted by the Python reference verifier.
- **Sinks.** Tested against an HMAC-verifying fake receiver:
  - a crash between the 2xx and `finish`, after which the identical range is resent;
  - lost leadership mid-request, and a stale request arriving after a newer range;
  - a purge between snapshot and begin;
  - 4–16 MiB envelopes, and the oversized hold and acknowledgement;
  - declared epoch gaps, and undeclared holes failing closed;
  - expiry, resume and gap retry;
  - atomic notification streaks;
  - SSRF cases: private, mixed and mapped addresses, redirects and proxies;
  - a sentinel showing URLs and secrets never leak.
- **UI.** 19 tests with axe checks. A real-browser check at 1280×800 and 390×844 found 0 violations and no overflow.
- **Review fixes before merge.**
  - The oversized flag ignored the repeated summary fields, which could stall a required sink.
  - `enable-checkpoints` could record 0.14.0 from a development build.
  - Audit target labels were missing.
  - A typecheck failure in a test.

### Published-image runtime acceptance

The published image ran by digest with a read-only root, UID 65532, all capabilities dropped, `no-new-privileges` and host networking. It used a fresh owned database with NOINHERIT owner and runtime roles. **This exercised the new features with the released binary for the first time.** All of the following passed:
- **Version and migrate.** It reports `open-mcp-portal 0.15.1 (8fafa1ea4e7d)`. `migrate`, run as the owner, applied `00001`–`00064` and reconciled grants.
- **Serve.** It became ready with `DB_REQUIRE_SPLIT_ROLES=true`, `AUDIT_STREAM_ENABLED=true` and `AUDIT_STREAM_ALLOWED_NETWORKS=http:172.17.0.1/32`. Status showed the sealer on, with sinks and checkpoints off by default.
- **Enabling.** `audit-stream enable-checkpoints` and `enable-sinks` (migration role, `--min-reader-version-ack`) were accepted and recorded minimum reader version `0.15.1`.
- **Sink management.**
  - A sink created through the API showed its secret once.
  - The response carried only the host hint, and the secret was not visible on read.
  - A destination outside the allowlist was refused at save.
- **Delivery.** A fake receiver verifying `X-OMP-Signature` got HMAC-valid, in-order batches covering seq 1–6, including a live `auth.login`.
- **Checkpoints.** `audit-stream rotate-checkpoint-key` created the first key on demand and appended a handover checkpoint. `/.well-known/omp-audit-keys.json` served one active and one retired Ed25519 key with ranges. The stream contained the signed checkpoint envelope, and `verify` reported 1–8 valid.
- **Protection.** The runtime role was refused a direct write to a sink cursor.
- **Logs.** The sink secret never appeared in the logs, and there were no error lines.

The script is kept with the verification evidence. The disposable database and roles were dropped afterwards. One acceptance-script bug was found and fixed: the secret check misread a secret starting with `-` as a grep option.
