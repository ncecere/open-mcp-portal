# Open MCP Portal v0.4.0

Scoped credentials, curated tools, team-owned provider connections and separate database roles.
**Breaking:** external agent-platform trust and person impersonation are retired. Ordinary MCP clients,
OAuth, API keys, service accounts and outbound portal-signed identity remain supported.

## What changed

- **Credential tool scopes (#29).** Personal keys, service accounts, service-account keys, gateway grants
  and MCP OAuth grants can restrict tools by owner-set class or exact exposed name. Matching grants
  combine; independent credential, account and grant ceilings all apply. `null` is unrestricted at that
  layer; `{}` allows no tools. Read-only excludes unclassified tools unless an exact name allows them.
  Names preserve case, whitespace and commas. Prompts and resources are unchanged. Consent can narrow
  an OAuth grant; refreshing or a remembered approval cannot silently widen it.
- **Per-selection tool curation (#30).** Give a selected tool a gateway-specific name and description,
  fix argument values, hide fixed properties and narrow the client input schema. The approved source
  definition remains unchanged. Edits bind to its fingerprint and the gateway revision; stale overlays
  fail closed. Conflicting fixed values are rejected, and injected arguments bind retries and recorded
  digests. Live policy is checked before every forwarding attempt, including an upstream-auth retry.
- **Shared service connections (#26).** Team owners/admins connect an upstream account explicitly for
  service accounts, separately from their personal connections. They assign accounts and allow
  destination servers, origins and scopes. Delivery checks the connector's current authority and the
  live provider, assignment and destination policies. A personal caller never borrows a shared account.
  Consent state is separate, encrypted values participate in key rotation, and local revocation commits
  before best-effort upstream revocation. Shared completion pages explain assignment and destination
  grants instead of sending people to their personal connections.
- **Migration/runtime database roles (#44).** `DATABASE_MIGRATE_URL` can use the schema owner while
  `DATABASE_URL` uses `DB_RUNTIME_ROLE`; `DB_REQUIRE_SPLIT_ROLES` requires the separation. Runtime has
  only the needed application privileges. Retention uses constrained owner-definer functions with fixed
  search paths and UTC arithmetic, minimum elapsed floors, effective retention and purge watermarks.
- **MCP-only product boundary (#68, decision 81).** Removed trusted external issuers/JWKS verification,
  relay impersonation, agent-presence controls, personal-connection agent switches and their management
  routes/UI. Migration `00034` disables trusted issuers and marked relay accounts, revokes their keys
  and fences authority-restoring writes from older replicas. Marks and historical attribution remain;
  retired accounts cannot be edited, given keys or deleted through the new API. Obsolete inbound
  `MCP-Gateway-Identity` is refused, including an explicitly empty header. The same header's legitimate
  **outbound** use remains when an upstream credential owns `Authorization`.

## Upgrading

1. Back up first, then apply migrations **`00029` through `00034`** using the normal migration step.
   Do not edit old migrations or downgrade the schema when rolling back an image.
2. Read [platform retirement](../platform-retirement.md) before upgrading a deployment that used relay
   accounts. Retirement is intentional: do not clear old relay marks or restore their keys into ordinary
   service-account authority. Replace legitimate automation with newly provisioned, normally scoped
   service accounts. The pi coding client is an ordinary MCP client, not Pi Durable Platform.
3. Remove retired API routes/fields from management clients. Review any upstream integration that
   expected an `act` claim; new calls never impersonate a person through an external platform.
4. Existing scopes are unrestricted and curation starts absent. Finish rolling out new replicas before
   relying on new scope, curation or shared-connection enforcement: older application images do not
   implement those policies. Schema compatibility is not policy compatibility.
5. Classify tools before switching credentials to read-only. Exact names mean the **curated exposed
   name**, not an upstream name or a previous alias. Renaming a tool can therefore stop a named scope
   from matching. See [credential scopes](../credential-scopes.md) and [curation](../gateway-curation.md).
6. Shared connections are opt-in and never migrate a person's credentials. Connect a shared account,
   assign its service accounts and explicitly allow eligible destinations before use. See
   [shared service connections](../service-connections.md).
7. Separate database logins are opt-in unless required by configuration. Follow
   [database roles](../database-roles.md), apply grants through the migration step, then give serving
   replicas only the runtime URL. An owner login remains powerful; this is not protection from a database
   owner. Never give a serving replica the migration credential merely to fix a readiness failure.

## Verification

The release gates include generation, lint/build, required-PostgreSQL Go tests and race suites in both
legacy and genuinely authenticated split-role configurations, all web checks, deployment validation and
kindnet/Calico smoke checks. GitHub Actions records CI, image scans, signing and publication; preparing
these notes does not itself assert that publication succeeded. See [status](../status.md) for results.

Desktop browser checks use owned disposable databases and fake MCP/OAuth servers: literal-name scope
entry, fixed-argument curation, shared consent, explicit assignments/destination grants, and ordinary
personal-connection isolation. Direct legacy and modern MCP calls verify shared credential delivery and
portal-signed identity against the scratch portal's JWKS. These are not real-provider or IDE acceptance.

## Known limitations

Classification is an owner's assertion, not proof of a tool's effects. Sensitive-call approvals (#31)
are not implemented by scopes or curation. Live third-party provider/client reports, a team pilot, load
and long wall-clock refresh/expiry evidence remain separate work. Existing upstream-auth limitations
remain; see [v0.3.2](v0.3.2.md). External-platform follow-ups #62/#63 were withdrawn, not successfully
verified or implemented.

See [implementation order](../implementation-order.md) for remaining work. Report vulnerabilities
privately using [SECURITY.md](../../SECURITY.md).
