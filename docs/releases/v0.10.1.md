# v0.10.1 — Consistent invite-acceptance lock order

**Published and independently verified.** [v0.10.1](https://github.com/ncecere/open-mcp-portal/releases/tag/v0.10.1) was published on2026-10-30T21:11:24Z. This patch is a prerequisite found while reviewing #36's future identity lifecycle; it implements no SCIM functionality. v1.0.0 remains the owner's explicit decision.

## Fix

Sign-in used to lock open email invites first, then insert a team membership. The membership's foreign-key check can wait for the team row. Manual invite revocation takes the team first and then its invite: the opposing order could deadlock sign-in against revocation. A real PostgreSQL lock barrier reproduced `ERROR: deadlock detected (SQLSTATE 40P01)`; this is not inferred from a timeout.

Acceptance now discovers candidate teams without retaining invite locks, locks all of them in stable UUID order, and only then locks and consumes each team's current invites. It rechecks revocation, role and expiry after waiting; a materialized locked-row query uses the database clock for expiry. Existing memberships keep their current roles. An invite for a newly discovered team arriving after discovery waits until the next sign-in rather than being consumed without its team lock.

This adds no migration, API operation, credential, token scope or ownership bypass. Existing owner-counting, verified-email gating, bootstrap policy, invitation audit and transactional acceptance remain. It does not retroactively change memberships already granted by an earlier binary. Older replicas still have the previous lock order; drain them to rely on the fix across all sign-ins.
