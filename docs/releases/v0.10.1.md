# v0.10.1 — Consistent invite-acceptance lock order

**Candidate, not yet released or verified.** The latest independently verified release is v0.10.0. This patch is a prerequisite found while reviewing #36's future identity lifecycle; it implements no SCIM functionality. v1.0.0 remains the owner's explicit decision.

## Fix

Sign-in used to lock open email invites first, then insert a team membership. The membership's foreign-key check can wait for the team row. Manual invite revocation takes the team first and then its invite: the opposing order could deadlock sign-in against revocation. A real PostgreSQL lock barrier reproduced `ERROR: deadlock detected (SQLSTATE 40P01)`; this is not inferred from a timeout.

Acceptance now discovers candidate teams without retaining invite locks, locks all of them in stable UUID order, and only then locks and consumes each team's current invites. It rechecks revocation, role and expiry after waiting; a materialized locked-row query uses the database clock for expiry. Existing memberships keep their current roles. An invite for a newly discovered team arriving after discovery waits until the next sign-in rather than being consumed without its team lock.

This adds no migration, API operation, credential, token scope or ownership bypass. Existing owner-counting, verified-email gating, bootstrap policy, invitation audit and transactional acceptance remain. It does not retroactively change memberships already granted by an earlier binary. Older replicas still have the previous lock order; drain them to rely on the fix across all sign-ins.

## Evidence and remaining gates

- The deterministic original acceptance/revocation negative reproduced40P01 before the fix. Repeated focused race tests passed in both actual PostgreSQL owner/split-role modes after the fix.
- Retained real-database regressions cover concurrent revocation, fresh role/expiry after lock waits, direct trace assertions that all sorted teams lock before membership writes, multiple-team/manual-member concurrency, and unchanged existing memberships. A separately investigated shared-journal-row deadlock hypothesis did **not** reproduce; the journal appends independent events, and no second defect is claimed.
- Full normal/race suites in both actual database-role modes, complete web/static/deployment/advisory gates, source runtime/browser checks, exact-source GitHub gates, native signed image/six-CLI publication and independent artifact/published-runtime verification are still required. Focused tests alone are not release acceptance.

The owner now requires work directly in the main thread; `AGENTS.md` records that newer instruction. No subagents are to be started unless requested again. SCIM's earlier drafts remain unaccepted; no decision90 or migration51 is allocated by this patch. Real-client/provider/pilot, whole-product security/accessibility, other-OS execution and previous release caveats remain separate.
