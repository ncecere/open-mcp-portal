# Open MCP Portal v0.6.0

Gateway access requests (#32, decision 83), with optional expiring gateway grants. Access approval is
separate from approval of an exact sensitive tool call; neither workflow bypasses credential scopes,
curation, provider consent, destination protections or normal authentication.

## What changed

- **Explicit discoverability.** Platform gateways may opt into a browser-only requestable list showing
  their name and description, not their selections or upstreams. The default is off. Team gateways do
  not accept requests, and `/mcp/{slug}` still hides gateways the caller cannot use.
- **Private user/team requests.** Active people request for themselves or teams they currently own or
  administer, with a required reason. Duplicate pending requests and requests for existing access are
  refused. At most 10 requests may be pending per person; denial starts a 24-hour cooldown. A requester
  can withdraw a pending request.
- **Narrow stewardship.** Platform admins may name up to 50 active human stewards for a platform
  gateway. Stewards decide that gateway's requests only: they gain no general admin, direct grant,
  gateway-editing or MCP authority. The requester can never decide their own request, even as a
  platform admin. Reviewer, requester and administered-team authority are rechecked under transaction
  locks. Every new workflow operation requires a browser session, never an automation token.
- **Atomic decisions.** Approval creates a normal user or team grant, the decision and audits in one
  transaction. User requests bind the requester's exact ID, never an ambiguous email lookup. Existing
  active grants are not silently widened or extended. Denial and withdrawal create no grant. A team
  grant intentionally includes current/future members and that team's service accounts.
- **Optional grant expiry.** Approvers and existing grant administrators may choose 1–365
  elapsed UTC days; omitted expiry is permanent. Existing permanent grants stay permanent. Effective
  user, group, team and service-account SQL excludes elapsed grants without waiting for cleanup.
  Temporary-grant transport guards check authoritative database time before and after admission/
  approval consumption, including its commit. A missing clock read refuses dispatch, and no connection
  or authority lock survives into network I/O. Expiry prevents later attempts; it cannot undo an
  already-admitted in-flight operation. A spent call approval is never restored or automatically replayed.
- **Private notices and attention.** Inbox and verified-email notices resolve live eligibility at fan-out
  and queued-email delivery. Payloads contain only the request ID and status; no reasons, notes or
  credentials. These events cannot be subscribed to or delivered by webhooks. Audit records retain
  normal gateway labels, IDs, decisions and expiry, never private reasons/notes. Requester/reviewer
  queues and eligible attention counts remain available if notification delivery fails.

## Upgrade and rollout

1. Back up the database and its matching encryption/pepper/signing material consistently. Git does not
   contain an instance's credentials, keys or data. Do not regenerate keys for an encrypted database,
   reset/reseed an existing instance or apply a development fixture to it.
2. Apply expand-only migrations **`00043`–`00045`** using the normal owner migration step. The runtime
   login receives reconciled operational grants for the new tables; do not give serving containers the
   owner URL to work around a startup check. Historical migrations and append-only audit protections
   remain unchanged.
3. **Finish rollout and drain every older serving and background-worker replica before enabling
   access requests or creating expiring grants.** v0.5.1 can use the expanded schema, but it does not
   enforce grant expiry or deliver the new private notification types. Schema compatibility is not
   enforcement compatibility. The new settings default off and existing grant expiries remain null.
4. Review gateway discoverability and named stewards explicitly. Opting in makes the gateway's name
   and description visible to all active signed-in people; stewardship is a narrowly delegated ability
   to widen that gateway's access through reviewed requests.
5. For upgrades from v0.4.x or earlier, also follow the [v0.5.0 approval rollout](v0.5.0.md). Keep production
   autovacuum enabled. Exact-call approvals still fail closed on conflicting authority/maintenance;
   access requests do not weaken or bypass that fence.

Do not downgrade the schema to roll back an image. An old serving image is not a safe expiry-enforcement
rollback: pause affected execution or explicitly revoke expiring grants before restoring an image that
cannot enforce them. Disable the new request workflow and stop its workers deliberately when rolling back;
do not silently turn temporary access into permanent grants. Preserve history and keys.

No new configuration variable, application dependency or credential/encryption format is introduced.
Request records retain private reasons/notes until their requester, gateway or subject team is deleted;
suspension/archive does not erase history. They do not inherit the separate 90-day sensitive-call receipt policy. General audit retention remains unchanged.

## Verification and limits

The full mandatory-PostgreSQL normal and race suites passed in both legacy and genuinely authenticated
split-role modes with `GOFLAGS='-p=2'` (3,022 seconds). Targeted races cover pending limits, duplicate and
decision concurrency, rollback of partial grant decisions, live team/steward authority, exact requester IDs,
private-notification failure/delivery, all grant subject kinds, database-clock failures, one-connection clock
reads and approval dispatch deadlines. Route, authorization and token matrices include every new operation.
Generation/freshness, lint/build and all web gates passed, including **844 tests**. CI-pinned govulncheck
reports zero reachable vulnerabilities (two module-only advisories); npm audit reports zero vulnerabilities.

Owned disposable browser checks (Chromium 156) exercised requester submission, steward approval, requester
status, auditor denial of private details, and desktop/390px layouts. All seven checked states have no
horizontal overflow and zero axe violations. The request modal retains incomplete `aria-hidden-focus` and
`color-contrast` checks; explicit forward/reverse keyboard traversal and Escape were exercised. This is not
whole-product accessibility acceptance.

The actual immutable published v0.5.1 image ran read-only as `65532:65532`, with a genuinely authenticated
restricted runtime login and no owner secret in its serving container, against schema 45. Health/readiness,
an HTTP authority write, journal advancement and preservation of the new access settings passed. This
proves scoped schema/runtime compatibility, not old-image enforcement of expiry or new-event delivery.

Publication, final CI, deployment smoke and signed-image/SBOM/checksum verification evidence is recorded in
[current status](https://github.com/ncecere/open-mcp-portal/blob/main/docs/status.md). No production deployment,
real IDE/provider/channel acceptance, broad load/soak result or independent whole-product security review
is implied. Those evidence-gated issues remain open. #33 upstream protection follows; see
[implementation order](../implementation-order.md). v1.0.0 remains the owner's explicit decision.
