# v0.14.0 — Definition scanning in shadow, audit stream slice 1

**Not yet published.** This minor release adds two features:

- **Definition scanning** (#72, #73) checks every MCP capability definition at refresh with local heuristics. The results are shown to reviewers in **shadow mode**: nothing is blocked, redacted or approved.
- **Audit streaming** (#38, slice 1) seals the audit log into a gapless, hash-chained stream that a collector can pull off the host. It is **off by default** (`AUDIT_STREAM_ENABLED=false`).

It has **five migrations** (`00058`–`00062`). Read [Rollout](#rollout) before upgrading.

## Definition scanning, shadow only (#72, #73)

- **What runs.** On every refresh, each tool, resource, resource template and prompt definition is scanned in process before the refresh transaction, and the findings are stored with it. Ruleset `v1` has 32 rules in four groups:
  - **secret:** credential shapes from the shared redaction rules;
  - **unicode:** tag characters, bidirectional overrides, invisible and control characters, variation selectors, and mixed-script or confusable names;
  - **poison:** English instruction-phrasing heuristics such as "ignore previous instructions", concealment from the user, sensitive paths, pseudo-tags, cross-tool references, external URLs and encoded blobs;
  - **length:** very long descriptions or schema text.
- **What it does not do.** Findings are evidence for reviewers only. Nothing is blocked, redacted, rewritten or approved, and findings never enter definition fingerprints or approval digests. Nothing is sent anywhere, and the call path (`internal/mcpgw`) is unchanged. Zero findings never means a definition is safe; see [what scanning will not catch](../content-scanning.md#9-what-this-will-not-catch).
- **Where you see it.** Findings appear on a server's **Capabilities** tab and in the publish, approval and capability-change review dialogs. Each finding shows rule, group, severity, count, location, ruleset version and scan time. Incomplete, stale and disabled scans are labelled as such and never look clean. Team editors and platform admins can rescan stored definitions.
- **Settings.** **Admin › Settings › Definition scanning** switches between `off` and `shadow`. The setting is session-only and audited. Auditors can read it, along with the rule catalog.
- **Bounded.** A definition is limited to 64 KiB and 25 ms. Over-limit or over-budget scans are recorded as *incomplete* with a reason. Only rule ids, severities, counts and escaped structural locations are stored; matched text is never stored.

## Audit streaming, slice 1 (#38)

Design: [audit-streaming.md](../audit-streaming.md) (decision 93). Record format: [audit-record-v2.md](../audit-record-v2.md).

- **Sealing.** Every audit row is stamped with its transaction id and an immutable row identity. A trigger sets both, and callers cannot override them. A leader-elected sealer adds rows to a hash chain in a gapless sequence, ordered by an xid snapshot watermark, so rows that commit out of order are never skipped. A protected schema, `omp_audit`, holds the chain, and a hardened database function recomputes and checks every hash.
- **Recovery.** If the database turns out to be a different cluster (a logical restore or cutover), sealing halts until an operator runs `open-mcp-portal audit-stream rebind` (after `pg_upgrade`) or `rebase` (after a restore). A failover or PITR starts a new epoch automatically. `audit-stream status` shows the state. A bounded daily sweep seals anything missed and flags it `late`.
- **Delivery (pull).** These endpoints are open to platform admins and auditors, or to an automation token with `platform:read`:
  - `GET /v1/admin/audit/stream` returns NDJSON, contiguous or `410 range_expired`.
  - `GET /v1/admin/audit/stream/tip`
  - `GET /v1/admin/audit/verify`
  - `GET /v1/admin/audit/entries/{seq}/full`
  - `POST /v1/admin/audit/stream/ack`

  Collectors are managed under **`/v1/admin/settings/audit-consumers`**, which requires a platform-admin browser session. The default profile is a summary, and full rows are opt-in per collector.
- **Retention interlock.** Once streaming has sealed anything, audit rows are purged only as a sealed sequence prefix that every *required* collector has acknowledged.
- **Not yet:** push sinks (webhook, syslog, OTLP), signed checkpoints and bulk exports (slices 2–4).

## Retention changes for everyone (H-10)

These apply whether or not streaming is enabled.

- **Floor and call-metadata minimum.** Audit rows are now kept at least as long as the longest call-metadata period, platform-wide or any team override, and never below `AUDIT_MIN_RETENTION_DAYS`. That variable defaults to 30, today's minimum, and only `migrate` writes it. The database enforces both limits, so they also hold for v0.13.1 replicas during a rolling upgrade.
- **Settings validation.** The settings API refuses an audit period below those values (`422 invalid_period`, reason `audit_interlock`). It also refuses call-metadata periods above the audit period.
- **Strict decoding.** Malformed retention settings now fail closed. Before, they silently fell back to defaults.
- **Before streaming starts, purging is unchanged.** Until the stream has sealed anything and no collector exists, the purge still deletes by age. It only adds the floor and call-metadata minimum above.

## Rollout

- **Migrations `00058`–`00062`.**
  - They add nullable columns to `audit_log`, with no rewrite, plus the stamping trigger.
  - They create the migration-owned `omp_audit` schema and the scanning tables.
  - `00059` builds two indexes `CONCURRENTLY` outside a transaction. It is safe to rerun if interrupted.
  - `00062` replaces `omp_purge_audit_log` in place, keeping its signature and settings.
- **Migration role and runtime grants.** Run `migrate` with the migration role (`DATABASE_MIGRATE_URL`) and `DB_RUNTIME_ROLE` as usual; it reconciles the runtime grants for `omp_audit`. Set `AUDIT_MIN_RETENTION_DAYS` in the migrate job's environment if you want a floor above 30.
- **Rolling upgrade and rollback.** v0.13.1 replicas keep working against the new schema. The actual v0.13.1 executable was tested at every new schema version in required split-role mode: its writes are stamped, and its retention loop obeys the new purge rules. Rolling back to v0.13.1 after migrating is supported. If you had enabled streaming, a rollback pauses audit purging (nothing new is sealed), which fails safe at a storage cost.
- **Definition scanning starts in `shadow` on upgrade.** A leader-elected backfill scans the definitions you already have. To opt out, set **Admin › Settings › Definition scanning** to `off`.
- **Settings conflict on upgrade.** If any call-metadata period (platform or a team override) is already longer than audit retention, the next retention settings change is refused until you raise audit retention or lower the override. The database keeps audit rows that long either way.
- **Enabling streaming.** Set `AUDIT_STREAM_ENABLED=true`, register a collector, and follow the collector and recovery runbooks in [deploy.md](../deploy.md). After a logical restore, cutover or `pg_upgrade`, run the recovery command before serving writes.
- **New dependency:** `github.com/mtibben/confusables` (MIT), for confusable-name detection. Its notice is in `docs/licenses/`.

## Evidence

### Implementation proof

- **Sealing order.** A proof program, now a retained test against the real sealer, shows that tailing by id loses a row under out-of-order commit. The watermark sealed every committed row exactly once under 24 writers × 400 transactions with savepoints, aborts and commit delays.
- **Independent reviews.** Two independent adversarial reviews of the design came first. Every finding is recorded and resolved in the design's section 10.
- **Physical failover.** A real streaming replica was promoted with `pg_ctl promote` in four phases. A rebase that was killed mid-run resumed exactly once.
- **Seal checks.** The database function rejects a wrong summary or chain hash, a reused identity, a gap, skipped rows, and a fast-path batch during a rebase.
- **Retention.** The purge removes only a sealed, acknowledged prefix, and it fails closed on missing or malformed settings. A hostile session time zone doesn't change it. It was tested with 10,000 teams.
- **Previous release.** The v0.13.1 executable migrates, reconciles and serves at schemas 58–62.
- **Scanning privacy and limits.** Privacy sentinels check that matched text never reaches the database, logs, metrics, audit or API. Other tests cover metric-label bounds, refresh non-interference, panic and budget handling, authorization, and token-scope matrices.
- **UI.** The scanning panels have 19 UI tests with axe checks, covering the "found nothing does not mean safe" wording, every scan state and inert rendering of hostile locations.
- **Review fixes before merge.**
  - `seal_batch` could be made to skip rows.
  - Three queries scanned the whole table every second.
  - The scanning migration number was out of order.
  - A load-dependent scanner test was flaky.
  - The new purge would have stopped audit retention on installs without streaming enabled.
