## What changes

### Accountable servers and lifecycle policy (#40, decision 88)

Servers can name an accountable person and a private on-call contact. A registering person is the default owner; existing and token-created servers start ownerless. Contacts are selectable plain text, not automatic links, paging integrations or notification destinations. Team owners/admins manage governance in a browser session; editors, ordinary members, non-member platform staff and automation tokens cannot. Platform admins retain the separately audited force-transfer operation.

- Sensitivity is `public`, `internal`, `confidential` or `restricted`. A gateway's ceiling defaults to `restricted` (no ceiling). A server above it is unavailable even in its own team's gateway, with reason `sensitivity_exceeds_gateway`.
- `internal` is only a default until a team owner/admin explicitly confirms a label, including the unchanged value. Migration 50 adds a nullable first-confirmation timestamp with **no default or backfill**. Metadata edits, publishing, refresh, registration and tokens never confirm. Published unconfirmed servers appear in informational attention; the marker never grants access or blocks publication. Confirmation is revision-bound and audited; like other metadata edits, its revision bump fences older exact snapshots.
- Deprecation remains served with a banner. A sunset stops new dispatch at its cutoff without waiting for cleanup. Availability, gateway counts and the final approval check mirror the rule.
- Re-review intervals default to never for public/internal, 180 days for confidential and 90 for restricted. Overdue review notifies and appears in attention. Automatic return to review is separately opt-in and off by default. Raising a published label re-enters review under `approval_required`; lowering does not.
- A receiving team's owner accepts a transfer. The server keeps its selected capabilities, gateway grants and sealed credentials; server approval rules move to the receiving team. Published transfers re-enter review according to the receiving team's policy. A restricted-provider combination that would stop calls is refused.
- A bounded five-minute leader loop sends deduplicated private inbox/email governance notices, never webhooks. Its leadership gauge reports the latest run, not exactly one simultaneous gauge across replicas. The load smoke now requires a governance leader signal; its short external-lock test still covers notifications/retention, while governance lock exclusion is database-tested.

The review digest becomes `omp-review-v6`. Reload a review opened before the upgrade.

### Final dispatch deadlines

Every transport freezes the earliest credential, gateway-grant or server-sunset deadline. The database clock is checked after quota admission and after any approval/input-attempt commit, including tools, prompts, resources, task operations, protocol setup and retries. Time passing need not change an authority epoch to refuse a late dispatch. **A refusal never restores committed approval or task-input spend.** An already spent approval with no confirmed upstream result remains uncertain/spent, not permission to replay.

This is admission control, not a guarantee that upstream work already dispatched has stopped.

### CLI and public Go client (#46, decision 89)

`omp` supports `whoami`, shared-vector `connect` snippets, server list/get/register/test/refresh/publish/unpublish and declarative export/import plans. It uses existing automation tokens only. There is no CLI sign-in flow, `omp keys`, new credential kind, new server endpoint or token-scope widening. `pkg/ompclient` is generated for token-callable operations and remains a pre-1.0 `v0` public API.

`omp/v1` configuration uses natural-key slugs and environment-variable names for authentication secrets. Optional omissions preserve existing settings. Explicit capability/grant lists are authoritative, so removals require care.

- Tool curation, grant scope and exact absolute grant deadlines survive round trips. Curation is comparison-only; a token cannot write it. Temporary-grant mutations needing a new absolute deadline are refused before any mutation because the relative-day API cannot preserve one independently of clock skew. Permanent-grant scope replacement remains non-atomic, with honest failure reporting and no authority-restoring rollback.
- Server governance, the optional confirmation marker and gateway ceilings are comparison-only. Differences, unreadable declarations, new governed-server clones and new gateways requiring non-default ceilings are refused before any mutation. No token request writes session-only governance or implicitly confirms a label. UUID references are not authentication or portable identity mappings.
- Exported private contacts and fixed curation values may be sensitive. `-o FILE` atomically writes owner-only permissions where supported and rejects symlinks/directories/special files; omit `-o` or use `-o -` for stdout. Atomic visibility is not a crash-durability guarantee.
- Config files are private, TLS is verified, redirects are refused, and plain HTTP is limited to loopback. Output and stable exit codes are documented in [cli.md](../cli.md).

The release workflow builds six CLI targets (Linux/macOS/Windows, amd64/arm64), attaches checksums and keyless cosign bundles, and offers the Dockerfile's `omp` target. **All six genuine binaries/bundles passed independent tag-specific keyless signature/checksum verification and byte-identical pinned-Go rebuilds.** Linux execution passed. Cross-compilation/signatures/reproduction do not prove macOS or Windows execution.

## Upgrade and rollback

1. Back up the database and the matching encryption keyring/API-key pepper. Never regenerate keys for an existing encrypted database.
2. Apply expand-only migrations **49 and 50** using the migration owner, then serve with the restricted runtime role. Applied migrations remain immutable.
3. **Drain every older serving and background-worker replica before relying on governance enforcement or delivery.** Schema compatibility does not make an older binary enforce ceilings, sunsets, transfers or the new workflow. Older binaries leave the confirmation marker unchanged: absent markers stay absent, already confirmed rows retain theirs.
4. Review ownerless/unconfirmed attention and explicitly name owners/check labels where appropriate. Nothing is backfilled as a human decision.

The example Kubernetes overlay is pinned to the independently verified v0.10.0 index above; verify it yourself and replace every example value before deployment. The v0.9.0 immutable index is `sha256:8a620e21c84786b9d8f6c326c19003a118456f17c322898174f008122f46f115`; that actual published image passed schema-50 doctor/health/readiness and revision-checked metadata compatibility, preserving new governance fields and credential ciphertext. This is compatibility, not old-image enforcement. Older code may be schema-compatible on rollback but cannot be used as a governance-policy rollback without removing reliance on those controls.
