## SCIM 2.0 provisioning (#36)

An identity provider can create, update, deactivate and delete people and groups at `/scim/v2`; see [SCIM provisioning](../scim.md).

- **Set-up:** Admin › Provisioning binds one directory to the configured OIDC issuer, turns it on or off and chooses optional or required enrollment. Provisioning tokens (`ompscim_`) are shown once, expire within 365 days, are revocable, belong to the directory rather than their creator, and work only at `/scim/v2` (never `/v1` or `/mcp`).
- **Linking:** a provisioned account links to someone only when its `externalId` equals their verified OIDC subject. New people enroll at their first sign-in; people who already signed in are adopted explicitly by an admin. Email and `userName` never link. Ambiguous or inactive matches, and (with required enrollment) unprovisioned new identities, are refused before any user, invite, bootstrap or session is created.
- **Protected people:** platform admins and team owners are never directory managed; database guards refuse adopting them or promoting a managed person, and a bootstrap administrator never enrolls as managed.
- **Lifecycle:** deactivation suspends at once without deleting sessions or credentials; earlier sessions stay ended after reactivation, while unrevoked keys and connections work again for new requests. Deletion suspends at once and a bounded, retried clean-up removes sessions, OAuth grants, personal connections and secrets, memberships and user grants and revokes API keys; it completes only when a recount finds nothing left. Re-enrollment is an admin action after clean-up.
- **Separate standing:** manual and directory restrictions are kept apart; lifting one never lifts the other. The effective status every existing check reads is derived from both by the database, so a status write by an older replica counts as a manual decision.
- **Groups:** directory groups can be mapped to a team role (admin, editor or member). The directory manages only memberships it created; a manual membership is never changed. Gateway grants to SSO groups still use the OIDC `groups` claim.
- **Protocol:** Users and Groups (group names unique ignoring case) with atomic, ordered PATCH (case-insensitive `op`, string booleans, member and email filter paths, and the authentik dialect without a top-level `schemas` member), `eq` filters on `userName`, `externalId`, `id` and `displayName`, pagination, weak ETags with `If-Match`, `excludedAttributes=members` and discovery. No bulk, sorting or password change. Writes are audited as `scim.*` system entries naming the token.

## Lifecycle prerequisites

- **Request epochs (decision 90):** a request queued across a suspend/reactivate cycle can't create a personal API key with the new authority (`409 request_authority_changed`).
- **Browser-session generations (decision 91):** a non-deleting fence ends existing cookies and original personal/shared connection consents; reactivation does not revive them.
- **Transaction-scoped key eligibility:** gateway-limited key creation reads eligibility on its own transaction.
- **Personal disconnect ordering:** local deletion and audit commit before best-effort provider revocation.
- **OAuth consent approval** refuses an account suspended while it waited.

## Rollout

Migrations `00051`–`00056` are expand-only; the previous release keeps working against them. Older replicas have no `/scim/v2`, no enrollment gate and ignore session generations and request epochs: **finish the rollout before enabling provisioning** or relying on the new fences. Never reset an encrypted database or regenerate its keys to update the binary.

Provider note: in our authentik 2025.8 test, deleting a user did not send a SCIM `DELETE`. Deactivate people before deleting them in authentik.

## Evidence

### Implementation proof

- **End-to-end SCIM tests** (`internal/httpapi/scim_integration_test.go`) drive enrollment, adoption, protected principals, group mappings, deactivation fencing, deletion, clean-up contention and re-enrollment through real sign-ins and HTTP, plus the deactivation-versus-enrollment race at a `pg_blocking_pids` barrier. They pass normal and race in both authenticated PostgreSQL role modes, with `OMP_TEST_REQUIRE_DB=1`, `GOFLAGS=-p=2` and the unchanged 20-minute per-package budget.
- **Prerequisites:** request epochs passed four adjacent packages normal/race in both roles plus six queued suspend/reactivate races. Session generations passed six adjacent packages normal/race in both roles; real blocked-exchange personal and shared callbacks refused a late commit, with a causal negative (the same schema with the consent predicate removed connected late in every mode).
- **Previous-release compatibility:** the actual immutable v0.11.0 image (`sha256:1dc3b19…`, UID 65532, read-only, no capabilities or mounts, runtime role only) ran against new restricted schema52, schema53 and schema54 databases. It reopened source sessions, made genuine CSRF/If-Match writes, preserved key digests, and decrypted a source-created provider secret in a real connect. On schema54 its admin "reactivate" left a directory-deactivated person suspended. Clean-up ran from the server loop. The old image serves its web app, not SCIM, at `/scim/v2`.
- **Real client:** a disposable local authentik 2025.8.4 pushed to the portal over loopback in four rounds: users, OIDC-subject enrollment, adoption, deactivation/reactivation, attribute updates, group membership add/remove driving a team role, manual membership preservation and duplicate-create refusal. It found three interoperability gaps that are fixed: PATCH without a top-level `schemas` member, empty groups omitting `members`, and concurrent duplicate group creates. Authentik did not send `DELETE` for deleted users (a provider limitation, documented). Synthetic users and loopback only: not production authentik, Entra or Okta, or a human pilot.
- **Independent security review:** a fresh-context reviewer reproduced three defects with deterministic tests: a stale role after concurrent removals from different groups, an adoption/owner-promotion deadlock, and a lost status-only manual suspension. A follow-up review confirmed those fixes and found a mapping/group-PATCH deadlock through an implicit foreign-key lock, plus a wording gap in the status-write rule. Each defect has a retained regression that failed before its fix and passes after, normal and race, in both roles. A third confirmation round on the final fix was refused by the review agent's model-provider content filter and produced no report; it is not credited. In its place, the reviewer's own deadlock schedule is the retained regression. The parent also traced every SCIM writer for an implicit team or user lock taken before reconcile locks. Group writes touch only directory rows first, mapping writes now lock first, enrollment and adoption act on not-yet-linked people, and unlink, user writes and clean-up don't reconcile and take only `KEY SHARE`-compatible or time-bounded locks.

One `retention: clean-up failed — Approval is unavailable` warning coincided with that clean-up. A deterministic pair on the same published image confirms the cause. With a no-op write lock held on `users`, both retention ticks logged the warning; the first tick after release completed with no errors. This is the existing fail-closed approval-context lock (`NOWAIT`) described below. The next cycle recovers, and the other retention hooks still run.

### Not covered

Real-time IdP sign-out without a directory push, remote revocation at upstream providers, more than one directory, correlation by any claim other than the OIDC subject, production identity providers and human pilots. Approval maintenance skips a pass (and retries later) when it meets any concurrent authority writer, including a clean-up pass; this fail-fast behavior is unchanged.
