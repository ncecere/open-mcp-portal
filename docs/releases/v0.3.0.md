# Open MCP Portal v0.3.0

The first release of the **v0.3** line: the portal can now trust an external **agent platform** (the first is [Pi Durable Platform](https://github.com/ncecere/pi-durable-platform)) to say *which person* an agent is acting for, and then treats the agent's calls as that person's, within strict limits. It adds one migration (`00020`, expand-only) and a new trust boundary, so read [Upgrading](#upgrading) and [Limits you should know](#known-limitations) first. **Nothing changes until a platform admin adds a trusted platform and marks a relay service account.**

## What changed

- **Trusted agent platforms** (#55). Admin › Trusted agent platforms lets a platform admin trust an external platform as an issuer of short-lived signed identity tokens: its issuer, the address of its signing keys (https only), and the audience the portal expects. Keys are fetched through the same address guard as MCP servers, cached, and refetched at most twice a minute for an unknown key. Only ES256 is accepted.
- **Relay service accounts** (#56). A platform admin marks one team service account as the relay for a platform. A call on that account that carries a valid token naming a person is **that person's call**: their gateway access *intersected with* the relay's (the lower role decides), their own delegated credentials, their identity in the call log with the agent and platform named. A token on any other credential is ignored and counted; a bad token on a relay's request refuses the request; a token is single-use; a person who is suspended or removed loses access through agents on the next call. A call with no person stays the service account's own.
- **Agents never get a consent link** (#57). A relayed person call that needs a connection the person hasn't made returns a tool error that says where to connect (never a link), and each server or capability can **require a present person**: calls an agent relays when nobody is watching (scheduled work) are refused, as are relay calls that name nobody.
- **Allow a server from My connections** (#60). Because an agent can't open a consent link, a person can now allow a server to use their connected account from Account › My connections (and revoke it there), with the same bindings to the server's address and scopes as the consent page.
- **The server behind the gateway learns it was an agent** (#58). The identity token the portal sends on carries an `act` claim naming the agent (RFC 8693 style) on relayed person calls, and never otherwise. `cmd/fakemcp`'s `whoami` shows it. [docs/agent-platforms.md](../agent-platforms.md) is the administrator's guide to setting up Pi Durable Platform with the portal end to end.
- **An independent security review of this work** (no Critical or High findings) was applied: the token's `tool` claim is bound to the tool called; "require a present person" also covers relay calls that name nobody; the keys address must be https; the migration avoids a long table lock; the review digest covers the present-person requirement; agent names are stripped of control and formatting characters.
- **Contract fixtures:** tokens and key sets produced by Pi Durable Platform v0.4.0's real signing code are checked into `internal/agentidentity/testdata/pdp/` and verified by a test with a fixed clock.

## Upgrading

1. Pin the new image (verify its signature first, see [Verifying the images](v0.1.0.md#verifying-the-images)). The init container applies migration `00020`, which adds tables and nullable columns only; the previous image keeps working against the new schema. **Do not use `goose down` to roll back**: it would drop the trusted platforms, relay marks and the agent columns of the call history; pin the previous image instead.
2. Nothing else changes for existing installs. The new surfaces are off until an admin configures them.
3. To use it with Pi Durable Platform, follow [agent-platforms.md](../agent-platforms.md). Pi Durable Platform's `identityAudience` must be set to the portal's `APP_URL`.
4. Removed in this release as announced in v0.2.2: the portal no longer accepts the old (non-`__Host-`) sign-in state cookie name on https.

## Verification

- Go tests with the race detector against PostgreSQL, web tests, the route and authorization-matrix tests, migration up-and-down tests, `govulncheck`, `npm audit`, and the Kubernetes smoke test in CI.
- **A contract check against the real platform's signer:** 19 tokens and 5 key sets produced by Pi Durable Platform v0.4.0's own signing and key-serving code were fed to the portal's verifier; every accept and reject matched the platform's design note.
- **An independent security review** (read-only, with proof-of-concept tests): 0 Critical, 0 High, 2 Medium (both fixed or documented), 4 Low, 9 Info; see the threat model, section 6.8.
- **A browser check** of Admin › Trusted agent platforms (the empty state and the add dialog, where a plain-`http` keys address is refused with an explanation), with the app started on the existing development database (so migration `00020` ran on a database with data). The relay control on service accounts, the present-person switches and the Allow dialog on My connections are covered by web and integration tests but were **not** looked at in a browser.
- **Not done:** a run against a live Pi Durable Platform (its gateway and runtime end to end, with real DNS, TLS and its identity provider's real issuer spelling); the manual procedure is in the guide. If Pi Durable Platform puts a different name in the token's `tool` claim than the name the client called, every tool call is refused as `tool_mismatch`, and the guide's check step shows it.

## Known limitations

Carried over from v0.2.2 unless marked new:

- **The platform is trusted to name people only from its own records (new).** A compromised platform signing key can speak as any person with a portal account, within the relay's reach, using their delegated tokens. Pi Durable Platform's own rules limit this; the threat model describes what an operator should require of it.
- **The token is bound to the platform-wide audience, not to the relay credential or the gateway (new, accepted).** A team admin of the platform who can set a server's `identityAudience` to the portal's audience could capture a token meant for another server; it is single-use and short-lived, and the platform-side mitigation is that only platform admins set that audience.
- **A person removed at the identity provider stays reachable through agents until suspended in the portal (new, same as other credentials).** SCIM is on the roadmap.
- **A server with Send identity off** receives the person's provider token on relayed calls and no `act` claim (new, documented).
- **VS Code and Cursor have not been run** against a gateway; neither has a real Google or Microsoft provider, a real Slack webhook or a real mail server.
- Remote servers only (no stdio); development software that has not run in production.
