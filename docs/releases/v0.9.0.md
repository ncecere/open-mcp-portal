# Open MCP Portal v0.9.0

The first stage of **#35, the released `io.modelcontextprotocol/tasks` extension** (decision 86), together with
the **Kubernetes release gates of #43** and the **content-scanning design of #52** (decision 87; design only).
It follows verified [v0.8.0](v0.8.0.md). Publication and verification evidence is recorded in
[status](../status.md) once the release exists. v1.0.0 remains the owner's decision.

## What changes

- **Task handles for long-running tools (modern era only).**
  - Modern `server/discover` advertises the extension.
  - A `tools/call` that **itself declares** the extension can be answered with an opaque portal task handle.
    This applies only when all of these hold:
    - the server's canonical primary advertised the extension (recorded as read-only `McpServer.supportsTasks`);
    - the call is **ungoverned**;
    - it is not a streamed (progress over SSE) request;
    - it is not the retry of an upstream input request.
  - The client then uses `tasks/get`, `tasks/update` and `tasks/cancel`. Each must declare the extension again
    (`-32021` otherwise), and `Mcp-Name` must equal the handle.
  - The portal relays a server's durable task. It runs no worker, queue or workflow engine, and it does not
    implement `tasks/list`, `tasks/result`, notifications or subscriptions.
- **Exact approvals are unchanged.** A call that needs approval is never negotiated as a task. A lifecycle
  operation runs a read-only no-rule check: a rule that now applies refuses the operation, and it never creates
  or spends an approval request. An unexpected task after spending remains an uncertain, spent attempt.
- **Every operation is re-authorized.** A handle is a lookup key, not a credential. Each operation:
  - authenticates normally;
  - finds the task only for the same principal and **starting credential root** (API key, stable OAuth grant,
    or service-account key);
  - re-resolves the exact offer: allowed, same capability, server revision, full URL, definition, tool class
    and curation;
  - acquires fresh credentials and identity for the actual URL, and requires the same dependency identity.

  Unknown, foreign, expired or no-longer-authorized handles all receive the same `-32602 Task not found`.
  Editing a server ends its in-flight tasks: they fail closed instead of following a changed configuration.
- **One send, never repeated.** Creation and every lifecycle operation are a single exchange to the recorded
  primary:
  - no retry (even for read tools), failover endpoint, protocol re-negotiation resend or legacy fallback;
  - no automatic 401 renew-and-resend.

  A lost response may hide upstream work; the portal never claims it was cancelled. Server quotas and the
  replica-local cap and breaker apply to each exchange.
- **Bounded, sealed, durable state.**
  - Capacity is reserved before dispatch: `TASKS_MAX_OPEN_PER_PRINCIPAL`, default 100, range 1–1000, shared
    across all of a principal's keys and gateways and across replicas.
  - The mapping is committed before a handle is revealed.
  - The upstream task ID, effective arguments and redaction-only credential values are sealed with
    `ENCRYPTION_KEY`, bound to the row and handle, and included in key rotation.
  - The local lifetime is bounded by `TASKS_MAX_TTL` (default 24h, range 1m–24h) and never extended by the
    upstream. Expiry denies access on its own; the retention loop prunes expired rows in bounded batches.
  - Invalid limit settings stop startup; neither can mean unlimited.
- **Input is single use.** Input keys are stable portal keys mapped to the server's private keys. A
  `tasks/update` response is consumed before its single send and is never restored, even if the send or its
  acknowledgement is lost. Unknown or already-answered keys are acknowledged but never forwarded. Input
  requests are rebuilt at the client's **current** declared elicitation capability.
- **Nothing private leaks.**
  - Results, status messages, input requests and errors are scrubbed of the upstream task ID, the original
    credentials and the fresh credentials of that exchange. A response that still contains one is refused.
  - Call records keep the original tool and server identity, with methods `tasks/get|update|cancel`, and no
    audit event per poll. Metrics stay bounded.
  - Task results and lifecycle payloads are never captured; the creating call is captured like any call.
- **Kubernetes release gates (#43).**
  - New smoke scenarios: upgrade from the previous release (plus a canary that a breaking migration must
    fail), ingress/TLS/OIDC through Dex, `pg_dump` restore, and a three-replica load test.
  - New `k8s-upgrade` and `k8s-load` workflows; ShellCheck and an assertion self-test run in CI.
  - **ingress-nginx is retired upstream**, so the tested controller is Envoy Gateway (Gateway API). The
    example `Ingress` remains for clusters that still run ingress-nginx.
- **Content-scanning design (#52, decision 87).** `docs/content-scanning.md` proposes shadow-mode detection
  first, with no hosted model. **Nothing is implemented.** First-slice follow-ups are #70–#73.

## Upgrade and rollback

1. Back up the database and its matching keys consistently. Do not reset or reseed an existing instance, or
   regenerate keys for its encrypted data.
2. Apply the new expand-only **migration 48** using the migration owner. It adds:
   - the `mcp_tasks` table: sealed state, bounded lifetime, revision and operation fences;
   - `mcp_servers.supports_tasks`, default false;
   - the `tasks/*` methods in the `mcp_calls` method check.

   No earlier migration is edited. Its rollback is expand-only: mappings and ciphertext are retained.
3. **Drain every older serving or background-worker replica before relying on tasks.** An older image ignores
   the new table and column, never negotiates tasks, answers the task methods as unknown, does not rotate the
   new cipher column and does not prune task rows. Expanded-schema compatibility is not enforcement.
4. Tasks become available once a server's primary is read again (refresh or health check) and advertises the
   extension, and a client declares it. Set `TASKS_MAX_TTL` and `TASKS_MAX_OPEN_PER_PRINCIPAL` only if you need
   narrower bounds than the defaults.
5. Do not downgrade the schema to roll an image back. An older image leaves live task handles unusable (unknown
   method) and does not stop upstream work.

No new application dependency is introduced. New settings: `TASKS_MAX_TTL` and `TASKS_MAX_OPEN_PER_PRINCIPAL`.

## Validation before publication

All four complete PostgreSQL suites passed on the frozen candidate: normal and race in both actual
legacy and authenticated split-role modes, mandatory database, every test retained and the same
20-minute per-package budget. Interrupted background runs are not acceptance. Repeated task races passed
in both modes. Remaining web/deployment/advisory and GitHub/publication results are recorded in
[status](../status.md) as they finish; this section is not a claim that publication has happened.

The actual published v0.8.0 digest passed doctor, health/readiness, login, reads and a metadata write on
schema48 as read-only UID65532 with the restricted runtime and no owner/migration URL or mounts. Its
write preserved the task-support flag and an actual sealed task row's ciphertext/status/revision/expiry;
the candidate store reopened that state. Expanded-schema compatibility is not old-image task enforcement.

Source real-HTTP smoke covered task creation, polling, single-use input, completed tool `isError`, cancel
acknowledgement, private credential-root isolation, ID/secret scrubbing and handle recovery after a full
serving-process restart. Six Chromium156 desktop/390px owner/editor/admin states had no axe violations
or overflow; **editor-mobile contrast remains incomplete**. The upstream was an owned protocol fixture,
not a real external Tasks client/server, and no natural-expiry or whole-product accessibility claim is made.

## Retained caveats

- **Not tasked:** governed (approval-required) calls, streamed calls, MRTR continuations, and legacy or
  undeclaring clients. Supporting governed asynchronous work needs a separately reviewed lifecycle-approval
  model.
- **Capacity:** at the cap, a declared call to a task-capable server is refused even if the server would have
  answered synchronously. An undeclared call is unaffected.
- **Busy tasks:** a poll that cannot claim the task (another exchange holds it, or the interval has not
  elapsed) is answered from the stored status only while it is `working`. Otherwise it gets a retryable
  `task_busy` error.
- **Consent:** a lifecycle poll for a delegated connection that has lapsed may record a provider consent
  request, but its answer is still the uniform not-found.
- **Cancellation:** a cancellation acknowledgement, expiry or revocation never proves upstream work stopped.
- **Real-world evidence:** no real MCP client or server that implements the released Tasks extension has been
  exercised. Evidence comes from released-schema fixtures and an owned fake upstream over real HTTP.
