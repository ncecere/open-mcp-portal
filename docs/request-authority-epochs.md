# Admitted request authority versus reusable credentials

**Decision90; first key-creation fence implemented and scoped-tested, not SCIM support.** This is a prerequisite of [#36's lifecycle work](scim-provisioning-preflight.md), not allocation of provisioning resources, directory tokens or routes. The owner requests one further verified pre-1.0 release after SCIM is complete, then a stop; this prerequisite does not receive a standalone release.

## Contract

A fresh authenticated request and its reusable credential have different lifetimes. Manual suspension refuses use while suspended. Reactivation may allow a **new** request with an otherwise eligible unrevoked key/connection. A request admitted before the suspend/reactivate cycle must not quietly inherit that new authority merely because it reaches a final write after the account is active again.

`users.request_epoch` is a dedicated positive monotonic counter. Migration51 adds it with initial value1 and a BEFORE UPDATE trigger; forward correction52 preserves the existing closed approval catalog by moving the non-approval helper to `public` with unchanged owner/OID/ACL, SECURITY INVOKER and pinned search path. Neither the old approval allowlist nor runtime grants are broadened. The trigger's semantics are: changes to manual status or platform role advance it, including change-and-revert and writes by a previous binary. An unchanged profile touch does not advance it. An explicit future lifecycle fence may increase it; decreases refuse. Approval-journal coverage retains all existing user authority fields, including email, and adds explicit epoch-only advances. This is not the profile revision, a session-revocation generation, a deletion/enrollment lifetime, or a group-policy generation.

Authentication snapshots the epoch into the user actor **before waiting** for a writer's resources. The first integrated writer is personal API-key creation. It retains its current USER lock, fresh active-standing checks, caps and audit, with gateway/team/membership/grant checks on the same registered owning transaction rather than a pool-backed callback, and compares the nonzero admitted epoch to the locked user's current epoch before inserting a key. Stale or absent admission returns a fixed request-authority-changed refusal, no key/secret/create audit and no automatic retry. A service must not fetch a fresh epoch after the wait as a fallback for an incomplete actor.

Key authentication still resolves current standing. The stored reusable key is not permanently bound to a transient request epoch: a fresh request after reversible reactivation receives the current admitted snapshot. Direct service fixtures/callers must construct a genuine admitted actor; a zero epoch is not a trusted-system bypass.

## Current executable baseline and acceptance

The private exact-v0.11.0-follow-up experiment held a pre-cycle `auth.Identity.Actor` key create at an explicit independently authenticated pool barrier, committed real `platform.UpdateUser` suspend/reactivate transactions, verified their audit pair, then released it. The old implementation minted a key: the future-refusal assertion failed in three race repetitions in both real PostgreSQL modes. Existing-key denial while suspended, preservation after reactivation, fresh-request success and the original queued-suspension regressions passed. That is the retained **before** result, not a passed future invariant or an allegation that the old reversible-suspension policy already promised this fence.

The corrected application snapshot passed all four adjacent packages (`apikeys`, `auth`, `platform`, `store`) in both mandatory authenticated PostgreSQL modes, normal/race with unchanged20-minute per-package budgets: role0 normal96.305s/race190.535s and role1 normal92.973s/race179.651s. All eight required regressions passed, including exact stale/missing admission refusal before mint/audit, original lock-wait status refusal, preserved-key/fresh-request controls, monotonic/change-and-revert/no-op behavior, explicit epoch journal invalidation, overflow refusal and the unchanged closed approval boundary. Three additional actual-service queued-cycle race repetitions per role passed. These are complete adjacent-package receipts, not full-portal/SCIM acceptance or evidence that every writer now has epoch protection.

## Compatibility and limits

Migrations51/52 add one non-key column, a pure row trigger, expanded existing approval-journal coverage and the helper relocation; they do not reencrypt credentials or rewrite identity keys. The first disposable-test attempt passed the initial application tests in legacy mode but correctly failed the existing split-role catalog boundary on schema51. That failed run is retained, migration51 is immutable, and52 is the forward correction. Older code omits/defaults the column and must continue to execute against final schema52; schema51 alone is not accepted compatibility. An independent source→actual-v0.11.0-image→source test passed against a new owned schema52 PostgreSQL17 database and authenticated restricted runtime. The immutable image reopened the source-created session, executed genuine CSRF/CAS role/no-op/suspend/reactivate and key writes, advanced epochs on access changes, preserved existing key IDs/digests, and did not revive the revoked session; source reopened an old-image session and created a fresh key. All1,601 candidate manifest files were unchanged. The old doctor's newer-schema informational result is not credited as a role/decryption check; no ciphertext fixture or decryption proof was executed. Full-product/local/CI/release acceptance remains separate. That is bounded schema compatibility, **not old-image request fencing**: older serving/background writers do not carry this admission field, and consistent enforcement requires draining them.

The global authority transaction primitives remain unwired at this stage. OAuth code/token/grace repeat, callbacks, refresh/cache/transport, personal secrets, approvals, access requests, task/input and remaining policy writers still require their own original-epoch/lifetime/current-standing integration and actual-service barriers. Browser-cookie revocation across reactivation needs a separate durable session generation; irreversible deletion needs a separate immutable lifetime and stable child-aware cleanup barrier. No claim about those follows from this first key-creation consumer.

Provisioning correlation remains verified issuer/subject plus explicit issuer-bound claim/adoption, never email fallback. Effective manual/directory/group provenance and the RFC7643/7644 token/resource profile remain separate integration gates. Do not expose discovery or a usable SCIM bearer surface based on this schema or the transaction primitives alone.
