# Gateway tool curation (#30; decision 80)

Curation belongs to one gateway selection, not the server catalog. It never changes a capability's stored definition, fingerprint or approved definition. Team gateway owners/admins and platform admins edit through the existing session-only selection routes. A catalog tool's description may be rewritten within a gateway; management views flag the edit and retain the original definition. Text is untrusted, not an authorization policy.

## Contract and concurrency

Selection items accept `curation` and `expectedFingerprint`, alongside the gateway `If-Match`. Omission preserves policy (including when editing minimum roles); explicit null clears it; an object replaces the whole policy. Every explicit edit, including clearing, must name the current capability fingerprint, otherwise `409 changed_since_review`. Removing a selection deletes its policy. Existing automation-token selection provisioning remains supported, but an explicit curation edit (including null) requires a browser session. The gateway row lock serializes whole-selection validation and writes, including name collisions and atomic name swaps. Names must remain unique across all selected tools, even unavailable ones (`409 name_taken`). Prompts and resources cannot be curated.

A policy has nullable `nameOverride` (the complete exposed name) and `descriptionOverride` (at most 2000 characters), plus `constraints`: an object keyed by top-level argument, each with exactly one `fixed` JSON value or a nonempty `allowed` JSON array. Fixed null is a value, not omission. Policies retain the base fingerprint, curator and timestamp. Audit includes bounded names and description/constraint counts and digests, never raw descriptions, fixed or allowed values, which may contain secrets. Policy JSON is readable through management selection views and is not an encrypted credential vault. My gateways returns the effective definition and an edited indicator without hidden fixed values or the original definition.

## Safe schema subset

Constraints require an object input schema with explicit top-level properties. Composition, references, dependencies, conditionals and other keywords whose projection cannot be proved sound are rejected, not ignored. Rename/description-only policies work independently of this restriction. Bounds are 50 constrained arguments, 100 allowed values per argument, 256 KiB per input schema, 64 KiB per policy, and 8 KiB / 256 JSON nodes per constraint value. Schema traversal allows depth 16 and 2000 schema/enum/required nodes, with at most 1000 entries in an original enum. JSON values allow depth 32. Each projection also has cumulative budgets: 8192 compiled value nodes, 100000 validation work units and 16 Mi arithmetic work units (charged before rational allocation or arithmetic, using decimal-size or operand-bit-product bounds). Exhausting a budget rejects the whole policy, never a partially narrowed allowed list. Enum membership uses locally compiled canonical keys; schema values, numbers and patterns are not reparsed for each allowed candidate. Larger or more complex policies are refused, never partially applied.

Constraint numbers, recursively inside fixed and allowed values, must be finite and exactly round-trippable in value through standard JSON binary64 parsing and serialization. Integral values must be safe integers (absolute value at most 9007199254740991). Ordinary decimals such as `0.1` and `1e-1` are accepted without changing their stored spelling; high-precision fractions such as `9007199254740990.5` or `0.10000000000000001`, overflow and underflow are rejected by both API and UI. The check compares bounded decimal spellings (at most 256 bytes), without constructing huge exponent powers. Validation-bearing schema numbers must meet these same limits when narrowing; rename/description-only policies do not restrict the original schema. Unconstrained runtime argument numbers are not globally restricted. Values are validated against supported original property schemas. All property schemas are checked, including unconstrained siblings: a nested reference there could otherwise point at a fixed property removed by projection. References (`$ref` and `$dynamicRef`) never cause network loading; there is no schema compiler or external resolver. Allowed lists intersect original enums and types and must leave at least one value. Equality is type-aware, uses normalized exact decimals rather than rounded floating-point values, and recursively compares arrays/objects. Supported numeric schema arithmetic uses bounded exact rationals.

List projection copies the definition, removes fixed properties and their required entries, and narrows allowed properties to enums. Catalog data and other gateways are untouched. Owner classification hints are overlaid as before. A base fingerprint mismatch or invalid policy is `curation_stale`, before the own-team approval shortcut: reapproval alone does not restore service; an owner must resave against the fresh fingerprint.

## Execution and retries

Resolve the effective exposed name first. Validate modern client parameter headers against the narrowed definition and client arguments. Then reject conflicting fixed values or out-of-list allowed values with `-32602` and an argument-specific message, before consent, target resolution or forwarding. Equal fixed values are accepted and missing fixed values injected. Headers cannot bypass constraints. Rewrite only `arguments` in the request envelope, preserving `_meta`, `requestState` and `inputResponses`; consent/relay request-state digests bind merged arguments. Equal fixed versus omitted fixed produce the same merged binding. A changed fixed policy cannot reuse an old binding. Upstream parameter headers use the ORIGINAL definition and MERGED arguments, including fixed header properties removed from the model-facing schema. Live availability/access/fingerprint/policy is checked immediately before every forwarding attempt, including retries after a blocked machine-token renewal or personal OAuth refresh. A changed overlay aborts the call rather than forwarding arguments merged under the obsolete policy. Retry and consent digests remain bound to the originally merged arguments, never silently rebound to a replacement policy. No list snapshot is trusted.

## UI and verification

The capability tab/picker offers name, description and top-level Fix/Allow controls, with typed scalar inputs and JSON fallback for supported complex values. The dialog checks numeric lexemes before parsing; the server enforces the same exact JSON round-trip and safe-integral limits for API-authored policies so later UI edits cannot silently round stored values. Show the model-facing definition preview, original definition and edited/stale indicators. Saves and clears carry the dialog's fingerprint and gateway revision; stale errors require reloading rather than silently overwriting.

Tests cover projection and exact equality, policy preservation/clearing, collisions/swaps, stale definitions after reapproval, authorization, both protocol eras, header rules, refusal before consent/upstream, merged retry bindings and audit non-disclosure. PostgreSQL tests use throwaway databases on the configured test server, never the development database. No dependencies are added.

## Compatibility and limits

Migration `00030_gateway_tool_curation` is expand-only. Older binaries ignore policy columns and therefore do not enforce curation: do not route curated gateways through an older binary during rollback or mixed-version deployment. Constraints are guardrails over named arguments, not a guarantee that a server has no alternate way to access the same resource. No nested argument paths, regex/range authoring, per-person values, prompt/resource curation or tool grouping is included. Credential tool scopes (#29) must match the effective exposed name, not the original catalog name.
